# 30. tokenizer 的词表大小和模型规模有什么关系？为什么不能无脑增大词表？

## 结论先行

词表越大，越有机会把高频文本编码成更少 token，但输入 embedding 和输出分类层会变大，低频 token 更难学充分，softmax 与分布式通信成本也可能增加。模型越大通常更能承载较大词表，却不存在固定比例；合理词表大小由模型维度、训练 token 数、语言/代码分布、权重共享和部署瓶颈共同决定。

## 参数量怎么计算

设词表大小为 $V$，隐藏维度为 $D$，输入 embedding 矩阵形状为：

$$
E \in \mathbb{R}^{V \times D}
$$

参数量约为 $VD$。若语言模型输出层为：

$$
W_{out} \in \mathbb{R}^{D \times V}
$$

且不与输入 embedding 权重共享，还要再增加约 $VD$ 个参数。举例，$D=4096$ 时，词表从 50k 增到 100k，单个 embedding/LM head 就多约 $50{,}000\times4096=2.048$ 亿参数；参数精度、优化器状态和是否分片会进一步决定显存成本。

权重共享能避免重复保存一套矩阵，但输出 logits 仍要覆盖 $V$ 个类别，训练时的投影、softmax、显存带宽和跨卡通信不会凭空消失。

## 大词表的收益

- 高频词、中文词组、代码模式可成为完整 token，平均序列缩短；
- 固定上下文 token 数下能容纳更多原始信息；
- attention 与 KV cache 的成本随序列缩短而下降；
- 多语言和专业领域可获得更充分的词表槽位；
- 单步生成可能输出更长文本片段，减少 decode 步数。

这些收益取决于新增词条是否真实高频。若新词条很少命中，既不缩短序列，又持续占用模型参数。

## 大词表的代价

### 1. embedding 与 LM head 膨胀

对小模型尤其明显：若主体 Transformer 只有几亿参数，一个很大词表可能吞掉大量参数预算，却没有增加层数、宽度或推理能力。矩阵尺寸还会影响量化、checkpoint 体积和设备间切分。

### 2. 输出空间更大

每个位置都要对更大的词表计算或处理 logits。虽然现代内核会优化矩阵乘法，词表投影仍可能成为训练和低 batch 解码的显著成本。

### 3. 低频 token 学不充分

把罕见整词加入词表后，它不再共享更常见子词的全部训练信号。出现次数太少时，其输入向量和输出概率都可能质量很差；组合式子词反而更能泛化。

### 4. 词表容量被污染

训练语料中的模板、乱码、随机 id、隐私片段或重复内容可能被合成长 token。词表看似压缩率更高，实际却把固定参数浪费在不可泛化模式上。

## 小词表也不是越好

词表过小会使文本接近字符或字节级，序列显著增长。self-attention 的训练成本常随长度近似二次增长，推理 KV cache 随长度线性增长；同样上下文窗口能容纳的信息减少，长文更容易被截断。因此选择词表是在**词表维度成本**与**序列维度成本**之间做系统级权衡。

可以粗略理解为：

$$
\text{总成本} = \text{embedding/softmax 成本}(V,D)
+ \text{序列计算成本}(n)
+ \text{数据与兼容成本}
$$

增大 $V$ 可能降低序列长度 $n$，但两项的变化没有通用固定比例。

## 模型规模之外还要看什么

1. 训练语料总量：更大词表需要足够样本训练每个 token。
2. 语言与代码覆盖：多语言模型通常需要在更多文字系统间分配容量。
3. hidden size：同样增加 10k 词条，在更宽模型上增加的参数更多。
4. 权重共享与并行策略：决定参数、显存和通信代价。
5. 服务形态：长上下文 prefill、低 batch decode 或边缘部署的瓶颈不同。
6. 兼容要求：改变词表会牵动 checkpoint、LoRA、量化和 chat template。

## 怎么选择

在多个候选 $V$ 上训练 tokenizer，先比较真实语料分桶压缩率、长尾 token 频次和覆盖；再做小规模等计算量预训练，测验证 loss、下游任务、训练吞吐和推理延迟。最终寻找 Pareto 前沿，而不是预设“参数越多词表就必须越大”。

## 面试回答要点

先给公式 $V\times D$，说明若输入输出不共享可能付两次；再说明大词表缩短序列，小词表提升组合与参数效率。结论是词表大小与模型规模相关但没有固定比例，必须用真实语料和端到端成本选择，不能只优化 token 数。
