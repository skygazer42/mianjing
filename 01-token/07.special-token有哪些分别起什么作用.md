# 07. special token 有哪些，分别起什么作用？

## 回答

special token 是由模型和 tokenizer 预先约定、用于表达控制信息的 token。它们不一定对应自然语言里的词，但会影响序列如何开始、结束、补齐、训练或被模型解释。

- `<bos>` / `<eos>`：分别表示序列开始和结束，生成模型常以它们界定一段文本。
- `<pad>`：把不同长度的样本补成同一长度；配合 attention mask 和 loss mask，避免补齐位参与计算或损失。
- `<unk>`：无法被词表覆盖的内容。现代 byte-level 或带回退机制的 tokenizer 会尽量减少它。
- `<cls>`、`<sep>`、`<mask>`：常见于 BERT 类模型，分别用于汇总分类信息、分隔句段和掩码语言建模。
- 聊天模型还会有角色、消息边界、工具调用等控制 token，用来区分 system、user、assistant 或结构化字段。

## 面试要点

不能把 special token 当普通文本随意拼接。不同模型的 token 名称、ID 和含义并不通用；训练、推理和模板必须使用该模型官方定义的约定。






对于大模型来说，**special token（特殊标记）**不是普通文本内容，而是用于表达结构、边界、角色、任务模式或控制信号的 token。

不同模型的特殊 token **名称、字符串形式和 token ID 都不相同**。下面按功能分类说明。

## 1. 序列边界 token

| 类型 | 常见写法 | 作用 |
| --- | --- | --- |
| BOS | `<bos>`、`<s>` | 表示一个序列或一轮生成的开始 |
| EOS | `<eos>`、`</s>` | 表示序列结束，模型生成到它时通常停止 |
| EOT | `<eot>`、`<\|eot_id\|>` | 表示一条消息或一轮对话结束 |
| EOD | `<eod>` | 表示一个完整文档结束 |

### BOS 和 EOS 的区别

例如：

```text
<BOS> 今天天气不错 <EOS>
```

* `BOS` 告诉模型：新序列开始了。
* `EOS` 告诉模型：内容已经结束。

在生成任务中，`EOS` 尤其重要。模型每次预测下一个 token 时，也会预测“是否该结束”。

---

## 2. 补齐和未知字符 token

| 类型  | 常见写法            | 作用                        |
| --- | --------------- | ------------------------- |
| PAD | `<pad>`、`[PAD]` | 将不同长度的序列补齐到相同长度           |
| UNK | `<unk>`、`[UNK]` | 表示 tokenizer 无法识别或无法编码的内容 |

### PAD

批量训练时，不同句子的长度不同：

```text
句子 A：我喜欢猫
句子 B：我非常喜欢可爱的小猫
```

为了组成同一个张量，短句会被补齐：

```text
我 喜欢 猫 <pad> <pad> <pad>
我 非常 喜欢 可爱 的 小猫
```

通常还会通过 `attention_mask` 告诉模型不要关注 `<pad>`。

### UNK

早期词级或子词 tokenizer 经常使用 `[UNK]`：

```text
未收录的词 → [UNK]
```

现代 GPT 类模型通常使用 byte-level BPE 或 byte fallback，理论上可以编码任意字节，因此不一定经常产生 `<unk>`。

---

## 3. 分类与分隔 token

这类 token 在 BERT 等编码器模型中很常见。

| 类型  | 常见写法    | 作用                    |
| --- | ------- | --------------------- |
| CLS | `[CLS]` | 放在输入开头，聚合整个序列的信息，用于分类 |
| SEP | `[SEP]` | 分隔句子、段落或输入部分          |

例如 BERT 的句子对输入：

```text
[CLS] 今天天气怎么样 [SEP] 北京今天晴天 [SEP]
```

* `[CLS]` 对应的隐藏状态可用于分类。
* `[SEP]` 分隔问题和回答，或句子 A 和句子 B。

---

## 4. 遮盖 token

| 类型   | 常见写法              | 作用                   |
| ---- | ----------------- | -------------------- |
| MASK | `[MASK]`、`<mask>` | 遮住部分内容，让模型预测原始 token |

例如 BERT 的预训练：

```text
巴黎是法国的 [MASK]。
```

模型需要预测：

```text
首都
```

这叫 **Masked Language Modeling，MLM**。

GPT 类自回归模型通常不依赖 `[MASK]` 训练，因为它们采用“根据前文预测下一个 token”的训练方式。

---

## 5. 对话角色 token

聊天模型需要区分：

* system
* developer
* user
* assistant
* tool

常见形式可能类似：

```text
<|system|>
<|user|>
<|assistant|>
<|tool|>
```

或者：

```text
<|start_header_id|>user<|end_header_id|>
```

它们的作用是告诉模型：

```text
这是系统规则
这是用户请求
这是助手之前的回答
这是工具返回结果
```

一个经过聊天模板处理后的输入，概念上可能是：

```text
<system>
你是一个编程助手。
<eot>

<user>
解释一下快速排序。
<eot>

<assistant>
```

最后的 `<assistant>` 标记表示：接下来应该生成助手内容。

### 为什么角色 token 很重要

如果不区分角色，模型看到的可能只是：

```text
你是一个编程助手。
解释一下快速排序。
```

模型无法可靠判断：

* 哪部分是规则；
* 哪部分是用户输入；
* 哪部分是助手输出；
* 当前应该由谁说话。

---

## 6. 消息边界 token

聊天模型经常区分：

* 一条消息开始；
* 消息头结束；
* 消息正文结束；
* 一轮对话结束。

常见概念包括：

| 类型               | 作用          |
| ---------------- | ----------- |
| Start-of-message | 一条消息开始      |
| End-of-message   | 一条消息结束      |
| Header start/end | 包围角色名或消息元数据 |
| Turn end         | 当前对话轮次结束    |

例如：

```text
<message_start>
<role:user>
你好
<message_end>
```

有些模型将角色和边界合成一个 token，有些模型使用多个 token 表达。

---

## 7. 工具调用和函数调用 token

支持工具调用的模型通常有专门控制标记，用于区分自然语言和结构化调用。

概念上可能是：

```text
<tool_call>
{"name":"get_weather","arguments":{"city":"北京"}}
</tool_call>
```

以及工具结果：

```text
<tool_result>
北京当前 25°C
</tool_result>
```

它们可以帮助模型学习：

1. 什么时候调用工具；
2. 调用哪个工具；
3. 参数应该如何组织；
4. 工具结果和普通用户文本有什么区别。

实际 API 中，这些内容可能由协议层处理，不一定直接以可见文本暴露。

---

## 8. Fill-in-the-Middle token

代码模型经常使用 **FIM，Fill-in-the-Middle** 特殊 token。

| 类型         | 常见概念 | 作用          |
| ---------- | ---- | ----------- |
| FIM_PREFIX | 前缀   | 表示光标之前的代码   |
| FIM_SUFFIX | 后缀   | 表示光标之后的代码   |
| FIM_MIDDLE | 中间   | 表示需要模型补全的位置 |

例如原始代码：

```python
def add(a, b):
    # 光标位置
    return result
```

转换后可能类似：

```text
<FIM_PREFIX>
def add(a, b):

<FIM_SUFFIX>
    return result

<FIM_MIDDLE>
```

模型生成：

```python
    result = a + b
```

与普通从左到右生成相比，FIM 更适合代码编辑器中的“光标中间补全”。

## 10. 多模态占位 token

多模态模型需要在文本 token 序列中表示图片、音频或视频。

常见概念包括：

```text
<image>
<audio>
<video>
```

或者一组视觉 token：

```text
<image_start>
<image_patch>
<image_patch>
...
<image_end>
```

处理流程通常是：

```text
图片
  ↓
视觉编码器
  ↓
视觉特征向量
  ↓
映射到语言模型的输入空间
  ↓
与文本 token 一起处理
```

这里的 `<image>` 可能只是一个占位符，也可能被替换为数百个视觉 embedding。

---

## 11. 控制生成行为的 token

部分模型使用控制 token 指定任务、语言、风格或输出形式。

例如：

```text
<translate_en_to_zh>
<summarize>
<answer>
<reasoning>
<final>
<zh>
<en>
```

用途包括：

* 指定翻译方向；
* 指定输出语言；
* 指定摘要任务；
* 区分内部推理与最终回答；
* 指定正式、简洁或代码模式。

T5 的任务前缀：

```text
translate English to German:
summarize:
```

有时是普通文本 token；有时也可以设计成真正的 special token。

---

## 12. Sentinel token

T5 等模型使用 sentinel token 表示被删除或需要补全的文本片段。

常见写法：

```text
<extra_id_0>
<extra_id_1>
<extra_id_2>
```

例如原文：

```text
The cat sat on the mat.
```

遮盖后：

```text
The <extra_id_0> sat on the <extra_id_1>.
```

目标输出：

```text
<extra_id_0> cat <extra_id_1> mat <extra_id_2>
```

它不仅要求模型预测被遮盖内容，还要求模型识别多个缺失片段的顺序。

---

## 13. Byte fallback token

一些 tokenizer 会为原始字节保留特殊表示，例如概念上的：

```text
<0xE4>
<0xB8>
<0xAD>
```

这些 token 用于编码词表中没有直接对应项的字符或字节。

作用是保证：

```text
任意 Unicode 字符串 → 都可以编码 → 也可以无损解码
```

这类 token 是否被定义为“special token”，取决于具体 tokenizer 的实现。

# 几类 token 容易混淆

## Special token 和普通 token

普通 token：

```text
hello
中国
ing
空格
标点
```

特殊 token：

```text
<bos>
<eos>
<pad>
<|user|>
```

普通 token 表达内容；特殊 token 主要表达结构和控制信息。

## Special token 和 reserved token

**Reserved token** 是提前保留但暂时未赋予明确功能的 token，例如：

```text
<reserved_0>
<reserved_1>
```

以后可以将它们用于新功能，而不必重新修改整个词表。

## Special token 和 added token

**Added token** 是后来手动加入 tokenizer 的 token。

```python
tokenizer.add_special_tokens({
    "additional_special_tokens": ["<tool_call>"]
})
```

它可以被标记为 special token，但“新增 token”和“特殊 token”不是完全相同的概念：

* added token：描述它是后来加入的；
* special token：描述它具有特殊语义或处理规则。

# 常见模型中的例子

## BERT

典型特殊 token：

```text
[PAD]
[UNK]
[CLS]
[SEP]
[MASK]
```

主要用于编码、分类和遮盖预测。

## GPT 类模型

常见类型：

```text
BOS
EOS
EOT
角色 token
消息边界 token
工具调用 token
```

主要用于自回归生成和聊天协议。

## Llama 类聊天模型

通常包含：

```text
BOS
EOS
消息头边界
角色标记
EOT
```

具体字符串取决于模型版本和对应的 chat template。

## T5

常见特殊 token：

```text
<pad>
</s>
<unk>
<extra_id_0> ... <extra_id_99>
```

主要用于文本到文本任务以及 span corruption。

# 在代码中如何查看一个模型的特殊 token

使用 Hugging Face Transformers 时：

```python
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("模型名称")

print(tokenizer.special_tokens_map)
print(tokenizer.all_special_tokens)
print(tokenizer.all_special_ids)
```

查看聊天模板：

```python
print(tokenizer.chat_template)
```

查看某个特殊 token 的 ID：

```python
token_id = tokenizer.convert_tokens_to_ids("<具体token>")
print(token_id)
```

检查真实编码结果：

```python
text = "你好"

encoded = tokenizer(
    text,
    add_special_tokens=True,
    return_special_tokens_mask=True,
)

print(encoded["input_ids"])
print(encoded["special_tokens_mask"])
```

这里：

```text
special_tokens_mask = 1
```

通常表示对应位置是特殊 token。

# 最关键的一点

不存在一份适用于所有大模型的统一 special token 列表。

一个模型的真实特殊 token 必须从以下内容读取：

```text
tokenizer_config.json
special_tokens_map.json
tokenizer.json
generation_config.json
chat_template
模型官方代码或配置
```

不能根据模型家族名称直接猜 token 字符串或 token ID，因为不同版本、不同微调模型和不同推理框架都可能使用不同配置。
