# 16. 为什么 LLM 更偏向 subword tokenization，而不是纯 character-level 或纯 word-level？

## 回答

纯 character-level 的词表很小、几乎没有 OOV，但序列太长，Transformer 的计算和上下文成本很高；纯 word-level 的序列较短，却需要巨大词表，并且难以覆盖词形变化、新词、拼写变体和多语言文本。

subword 位于两者之间：高频词、常见词根和代码片段可以整体编码，罕见词则拆成可复用的更小单元。这样既控制了序列长度，又能较好覆盖长尾词和跨语言字符。

## 面试要点

subword 不是语言学意义上的“分词”，而是面向压缩效率、覆盖率和模型计算成本的工程折中。



LLM 偏向 subword tokenization（子词切分），主要因为它在“词表大小”和“序列长度”之间取得了较好的平衡。

LLM 并不直接处理字符串，而是经过下面的转换：

```text
文本 → tokenizer 切分 → token ID → embedding → Transformer
Transformer 输出 → token ID 概率 → 解码 → 文本
```

## 词表是什么

词表（vocabulary）是一张有限的映射表：

```text
token 片段 ↔ 整数 ID
```

词表中通常包含：

* 高频词或词组
* 子词、字符或字节片段
* 标点、空格及换行片段
* 数字和代码片段
* `<BOS>`、`<EOS>` 等特殊 token

例如，某个 tokenizer 可能将一个英文长词拆为“前缀 + 词干 + 后缀”。具体如何拆分完全取决于模型使用的 tokenizer，不能仅根据文本确定。

词表本身不是模型的知识库。它只规定“哪些文本片段可以作为基本单位，以及对应哪个 ID”。这些 token 的含义由模型训练得到的 embedding 和网络参数承载。

词表大小记为 (V)，隐藏维度记为 (d)，仅输入 embedding 矩阵通常就需要大约：

[
V \times d
]

个参数。词表越大，embedding 和输出层通常也越大。

## Tokenization 的作用

Tokenization 是利用词表和切分算法，把任意文本转换成 token ID 序列。

它承担四个关键作用：

1. **把离散文本转换成模型可计算的整数序列**
2. **控制序列长度**
3. **确定模型输入和输出的基本单位**
4. **让有限词表覆盖大量甚至任意文本**

Tokenization 会直接影响：

* 上下文窗口能放多少内容
* 推理速度和显存占用
* API 按 token 计费时的成本
* 多语言、代码、数字和专有名词的处理效果
* 模型生成一次需要预测多少步

## 为什么不用完整单词作为 token

纯 word-level tokenization 存在明显问题。

### 词表会非常大

自然语言中的词几乎没有封闭边界，例如：

* 单复数和时态变化
* 派生词和复合词
* 人名、地名、产品型号
* 拼写错误
* 不断出现的新词
* URL、代码和随机字符串

如果每个完整单词都是一个 token，词表可能达到数百万甚至更大，使 embedding 和输出层变得昂贵。

### 会出现未登录词

词表之外的单词只能映射成统一的未知 token。这样，不同的生僻词可能丢失原始拼写信息。

子词切分可以把未见过的词拆成已知片段，保留更多信息。采用 byte fallback 的 tokenizer 甚至能通过字节片段表示任意输入。

### 相似词无法充分共享信息

如果每个完整词都是独立 token，相关词形之间没有直接的组成关系。子词可以让多个词共享常见片段，从而提高数据利用率。

但需要注意：BPE 等算法主要根据频率学习片段，并不保证切分结果符合真正的词根、词缀或语言学边界。

## 为什么不全部按字符或字节切分

字符级和字节级 tokenization 的词表很小，也几乎不存在未登录输入，但会产生更长的序列。

例如，一个高频词如果作为整体只需要 1 个 token，按字符或 UTF-8 字节处理时可能需要多个 token。序列长度记为 (L)，标准注意力计算量大致随：

[
O(L^2)
]

增长。序列变长会带来：

* 注意力计算量增加
* 占用更多上下文窗口
* 生成需要更多步骤
* 长距离信息更难处理
* 推理延迟和成本上升

## Subword 为什么是折中方案

三种方案可以这样比较：

| 方案     | 词表大小 | 序列长度 | 未登录词  | 主要问题      |
| ------ | ---: | ---: | ----- | --------- |
| 单词级    |   很大 |   较短 | 严重    | 新词和稀有词难处理 |
| 字符/字节级 |   很小 |   很长 | 很少或没有 | 计算和上下文成本高 |
| 子词级    |   中等 |   中等 | 很少    | 切分不一定符合语义 |

因此，subword 提供了一个工程上的“甜点区”：

* 高频词可以整体进入词表，减少序列长度。
* 低频词拆成更小片段，避免无限扩张词表。
* 不同词可以共享子词表示。
* 能处理多语言、代码、符号和新造词。
* 将 embedding、输出层和注意力的成本控制在可接受范围。

更直观地说，模型同时承受两类成本：

[
\text{词表相关成本} \propto V
]

[
\text{注意力相关成本} \propto L^2
]

完整单词方案倾向于增大 (V)，字符或字节方案倾向于增大 (L)，subword 则试图同时控制二者。

## 常见的子词方法

* **BPE**：反复合并训练语料中高频的相邻片段。
* **WordPiece**：根据语言模型相关目标选择合并片段。
* **Unigram**：先建立候选子词集合，再删除贡献较低的子词。
* **Byte-level BPE**：以字节为基础学习高频组合，可以覆盖任意字节输入。
* **SentencePiece**：一种 tokenizer 实现框架，常用于 BPE 或 Unigram，并可直接处理原始文本。

现代 LLM 经常采用“子词算法 + 字节级基础或回退机制”，所以它们并非严格意义上的传统词级分词。

## Tokenization 的局限

Subword 是效率折中，并不代表它天然理解语言：

* token 边界不等于词或语义边界。
* 同一个词在不同上下文或空格条件下可能切分不同。
* 低资源语言可能被切成更多 token，计算成本更高。
* 数字、专有名词和拼写变体可能被不理想地拆分。
* token 数过多会更快耗尽上下文窗口。
* 一个字符可能跨多个 token，一个 token 也可能包含多个词或字符。

所以，token 是模型的计算单位，不是稳定的语言学单位；词表和 tokenizer 的设计，本质上是在覆盖能力、序列长度、模型参数量以及多语言公平性之间做取舍。
