# 12. 为什么中文常常看起来“字少，但 token 不一定少”？

## 回答

中文没有天然空格，tokenizer 不能简单依赖词边界；它会根据词表和统计规律把文本切成汉字、常见词片段或字节片段。若词表对中文覆盖不足，一个汉字或常用多字词都可能被拆成多个 token。

英文中许多高频词会与前导空格一起被收录为一个 token；而中文短句虽然字符少，如果常见词没有被完整收录，token 数未必比英文低。emoji、罕见姓名、繁体字、混合英文和标点也会影响切分结果。

## 面试要点

不要用“一个汉字等于一个 token”估算成本。应使用目标模型的官方 tokenizer 对真实输入编码后再统计。

# 12. 为什么中文字符少，但 Token 不一定少？

因为：

> **字符数是人类看到的文本长度，而 Token 数是 tokenizer 根据词表和切分规则得到的序列长度。两者没有固定比例。**

中文看起来通常比英文紧凑，但这不代表中文一定会被编码成更少的 token。

---

# 一、先看一个直观例子

中文：

```text
我喜欢机器学习
```

一共 7 个汉字。

英文：

```text
I like machine learning
```

一共有 23 个字符，包括空格。

从字符数看，英文明显更长。

但某个 tokenizer 可能把英文切成：

```text
["I", " like", " machine", " learning"]
```

只有 4 个 token。

中文可能切成：

```text
["我", "喜欢", "机器", "学习"]
```

也是 4 个 token。

也可能切成：

```text
["我", "喜", "欢", "机", "器", "学", "习"]
```

变成 7 个 token。

如果某些汉字不在词表中，还可能退回字节编码，token 数甚至超过字符数。

所以：

```text
中文字符更少
≠
中文 token 一定更少
```

---

# 二、Tokenizer 不按“视觉字符”计数

模型不会直接读取：

```text
我 喜 欢 机 器 学 习
```

它读取的是 tokenizer 产生的 token ID。

流程是：

```text
Unicode 文本
↓
规范化或预处理
↓
子词或字节切分
↓
Token ID
```

Tokenizer 关心的是：

* 词表中是否有这个汉字；
* 是否有多个汉字组成的词；
* 这个片段在训练语料中是否足够常见；
* 是否需要退回到字节级表示。

它不关心人类看起来用了多少个方块字符。

---

# 三、一个英文单词经常可以是一个 Token

英文虽然字符多，但高频单词可能整体进入词表。

例如下面只是概念示例：

```text
"the"        → 1 token
"computer"   → 1 token
" learning"  → 1 token
```

一个英文 token 可能包含：

* 几个字母；
* 一个完整单词；
* 前导空格加完整单词；
* 常见词根或后缀。

例如：

```text
internationalization
```

有 20 个字母，但可能被切成少量子词：

```text
["international", "ization"]
```

即 2 个 token。

因此英文经常出现：

[
1\text{ token} > 1\text{ character}
]

也就是一个 token 覆盖多个字符。

---

# 四、中文经常接近“一字一 Token”

中文没有天然的空格分词边界。

例如：

```text
自然语言处理
```

人类可以理解为：

```text
自然语言 + 处理
```

或者：

```text
自然 + 语言 + 处理
```

但 tokenizer 不一定按人类词语切分。

它可能编码为：

```text
["自然", "语言", "处理"]
```

也可能是：

```text
["自", "然", "语", "言", "处", "理"]
```

如果大部分汉字各自占一个 token，那么中文大致表现为：

[
1\text{ 个汉字}\approx1\text{ token}
]

这时一句 20 个汉字的中文，可能接近 20 个 token。

而一段含 50 个英文字母的英文，可能只有十几个 token。

---

# 五、罕见汉字可能占多个 Token

中文字符在 UTF-8 中通常使用多个字节表示。

一个常见汉字可能已经作为完整 token 存在于词表中：

```text
中 → 1 token
```

但罕见汉字、古文字、生僻字或特殊符号可能没有完整词表项。

Tokenizer 可能退回到底层字节：

```text
某个生僻汉字
→ 字节片段 1
→ 字节片段 2
→ 字节片段 3
```

于是视觉上的一个汉字可能对应：

[
1\text{ character}\rightarrow2\sim3\text{ tokens}
]

具体数量取决于 tokenizer，不能对所有模型统一断言。

---

# 六、Emoji 更能说明“字符数”和 Token 数不是一回事

例如：

```text
👨‍👩‍👧‍👦
```

人眼看起来是一个家庭 Emoji。

但它在 Unicode 中实际上由多个码点组成，包括：

* 多个人物 Emoji；
* 多个零宽连接符；
* 可能还有肤色修饰符。

因此它可能被编码成很多 token。

类似地：

```text
🇨🇳
```

看起来是一个国旗字符，但底层由两个区域指示符组成。

所以：

```text
视觉上一个字符
≠
Unicode 一个码点
≠
Tokenizer 一个 token
```

---

# 七、中文词语是否能合并，取决于训练语料

假设 tokenizer 训练语料中经常出现：

```text
人工智能
机器学习
自然语言处理
中华人民共和国
```

它可能为这些高频片段分配较大的 token：

```text
["人工智能"]
["机器学习"]
["自然语言", "处理"]
```

这样中文 token 数会明显下降。

但如果 tokenizer 的训练数据主要是英文，中文得到的词表容量较少，那么同样内容可能被切成：

```text
["人", "工", "智", "能"]
["机", "器", "学", "习"]
```

所以中文 token 效率在很大程度上取决于：

* 中文在 tokenizer 训练语料中的比例；
* 词表大小；
* 子词算法；
* 是否使用 byte fallback；
* 是否为常见中文词组分配词表项。

---

# 八、词表容量是有限的

假设 tokenizer 的词表大小是：

[
V=50{,}000
]

这 50,000 个位置需要同时覆盖：

* 英文；
* 中文；
* 日文；
* 韩文；
* 阿拉伯文；
* 代码；
* 数字；
* 标点；
* Emoji；
* 特殊 token。

如果大量词表位置被用于英文高频单词：

```text
" the"
" and"
" information"
" development"
```

那么留给中文多字词的空间就会变少。

结果可能是：

```text
英文：一个 token 覆盖多个字母或一个单词
中文：一个 token 只覆盖一个汉字
```

因此，即使中文字符更少，token 数也可能与英文接近，甚至更多。

---

# 九、英文空格反而可以帮助 Tokenizer

很多 GPT 类 tokenizer 会把前导空格和后面的单词一起编码。

例如可能存在：

```text
"apple"
" apple"
```

这两个不同 token。

英文天然有空格，单词边界清晰：

```text
I like machine learning
```

Tokenizer 很容易统计：

```text
" like"
" machine"
" learning"
```

这些高频单位。

中文通常连续书写：

```text
我喜欢机器学习
```

没有显式边界。

Tokenizer 必须从统计中自己判断：

```text
喜欢
机器
学习
机器学习
```

哪些组合值得成为 token。

这会使中文多字词的合并更依赖训练数据规模和质量。

---

# 十、中文“信息密度高”和“Token 少”不是同一概念

中文一个汉字通常携带的语义比一个英文字母多。

例如：

```text
猫
```

一个字符就能表达一个完整概念。

英文：

```text
cat
```

需要三个字符。

所以中文在**字符层面**信息密度较高。

但模型处理的单位不是英文字母和汉字，而是 token。

如果：

```text
猫 → 1 token
cat → 1 token
```

那么在模型看来，两者长度相同。

再例如：

```text
机器学习 → 4 个汉字
machine learning → 16 个字母加空格
```

若切分结果是：

```text
机器学习 → ["机", "器", "学", "习"]       4 tokens
machine learning → [" machine", " learning"] 2 tokens
```

那么英文字符更多，但 token 更少。

---

# 十一、中文标点、数字和英文混排也会增加 Token

现实中文文本经常包含：

```text
请访问 https://example.com，在2026年7月13日前完成。
```

其中包括：

* 中文；
* 英文 URL；
* 数字；
* 标点；
* 斜杠；
* 点号；
* 日期。

Tokenizer 会对这些不同结构分别切分。

例如数字可能被切成：

```text
2026
```

或者：

```text
20 + 26
```

或者：

```text
2 + 0 + 2 + 6
```

URL、代码和特殊格式也可能产生大量 token。

因此不能只根据汉字数量估计整段中文的 token 数。

---

# 十二、繁体字、异体字和 Unicode 规范也会影响结果

例如：

```text
后
後
```

语义相关，但 Unicode 字符不同。

又如：

```text
里
裏
裡
```

不同写法可能对应不同 token。

如果某种写法在训练语料中较少，可能被拆得更细。

类似问题还包括：

* 全角数字和半角数字；
* 中文引号和英文引号；
* 全角空格；
* 组合字符；
* 异体字；
* 古汉字；
* 日文汉字。

所以即使视觉和语义相似，底层 token 数也可能不同。

---

# 十三、一个详细对比例子

考虑下面两句话：

中文：

```text
大型语言模型正在改变软件开发。
```

英文：

```text
Large language models are changing software development.
```

假设只看字符：

* 中文明显更短；
* 英文包含大量字母和空格。

但可能出现三种情况。

## 情况一：中文优化较好的 tokenizer

可能切成：

```text
["大型", "语言", "模型", "正在", "改变", "软件", "开发", "。"]
```

共 8 个 token。

英文可能切成：

```text
["Large", " language", " models", " are",
 " changing", " software", " development", "."]
```

也是 8 个 token。

---

## 情况二：偏英语的 tokenizer

中文可能切成：

```text
["大", "型", "语", "言", "模", "型",
 "正", "在", "改", "变", "软", "件",
 "开", "发", "。"]
```

共 15 个 token。

英文仍可能是 8 个 token。

此时：

```text
中文字符少
但 token 更多
```

---

## 情况三：英文中出现生僻长词

假设英文包含罕见术语：

```text
electroencephalographically
```

它可能被拆成多个子词。

此时中文翻译虽然有若干汉字，但 token 反而可能更少。

因此语言之间没有固定结论，必须用具体 tokenizer 实测。

---

# 十四、不同 Tokenizer 的中文效率可以差很多

同一段中文交给不同模型，可能得到完全不同的结果：

```text
Tokenizer A：100 个汉字 → 105 个 token
Tokenizer B：100 个汉字 → 70 个 token
Tokenizer C：100 个汉字 → 160 个 token
```

这些数字只是说明差异形式，不代表任何具体模型。

影响结果的因素包括：

1. tokenizer 算法；
2. 词表大小；
3. 中文训练语料比例；
4. 是否允许多汉字 token；
5. Unicode 预处理方式；
6. 字节回退机制；
7. 特殊符号处理；
8. 文本是否包含代码、数字和英文。

所以“中文大约一个汉字一个 token”只能作为粗略经验，不能作为精确换算公式。

---

# 十五、这对上下文长度有什么影响？

假设模型上下文窗口是：

[
128{,}000\text{ tokens}
]

如果一种语言平均每个 token 覆盖：

* 4 个字符；
* 另一种语言每个 token 只覆盖 1 个字符；

那么两种语言能装入的字符数可能相差约 4 倍。

因此同样是 128K 上下文：

```text
128K token
≠
固定的 128K 字符
≠
固定页数
≠
固定字数
```

Tokenizer 效率较低的语言会面临：

* 同一内容消耗更多上下文；
* Prefill 计算更多；
* KV Cache 更大；
* 生成步骤更多；
* API token 成本可能更高。

---

# 十六、这对生成速度也有影响

模型通常一次生成一个 token。

假设表达同一句话：

```text
语言 A：需要 20 token
语言 B：需要 35 token
```

即使每个 token 的解码速度相同，语言 B 也需要更多解码步骤。

因此 tokenizer 对某种语言切得更细时，可能导致：

* 首字之后整体生成耗时更长；
* 输出 token 数更多；
* KV Cache 增长更快；
* 计费 token 更多。

---

# 十七、如何精确判断一段中文有多少 Token？

必须指定具体模型和 tokenizer，然后实际编码。

以 Hugging Face tokenizer 为例：

```python
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("具体模型名称")

text = "大型语言模型正在改变软件开发。"

encoded = tokenizer.encode(text, add_special_tokens=False)

print("Token IDs:", encoded)
print("Token 数:", len(encoded))
print("Token 切分:", tokenizer.convert_ids_to_tokens(encoded))
```

还可以比较中英文：

```python
texts = [
    "大型语言模型正在改变软件开发。",
    "Large language models are changing software development.",
]

for text in texts:
    token_ids = tokenizer.encode(text, add_special_tokens=False)
    tokens = tokenizer.convert_ids_to_tokens(token_ids)

    print("文本:", text)
    print("字符数:", len(text))
    print("Token 数:", len(token_ids))
    print("Tokens:", tokens)
    print()
```

不能拿一个模型的 token 结果推断另一个模型，因为各模型的：

* 词表；
* token ID；
* 合并规则；
* 特殊 token；

都可能不同。

---

# 十八、核心结论

中文字符少但 token 不一定少，主要有五个原因：

1. **模型按 token 而不是字符处理文本。**
2. **英文高频单词常能整体成为一个 token。**
3. **中文经常接近一字一 token，甚至一个生僻字多个 token。**
4. **中文多字词能否合并，取决于 tokenizer 的训练语料和词表容量。**
5. **字符数衡量视觉长度，token 数衡量模型实际序列长度，两者不是同一种单位。**

最简洁地说：

[
\boxed{
\text{中文字符的信息密度高}
\not\Rightarrow
\text{Tokenizer 对中文的压缩效率一定高}
}
]

因此，判断上下文占用时，应查看具体 tokenizer 的实际编码结果，而不能只数汉字。
