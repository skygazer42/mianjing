# 06. 一个模型的词表（vocab）是怎么设计出来的？

模型的词表通常由训练语料和分词算法共同决定。先准备大规模文本语料，再选择 BPE、WordPiece、Unigram / SentencePiece 等 tokenizer 算法，根据词频和子词合并规则生成固定大小的 vocab。最终 vocab 会包含常见词、子词、字符、符号、特殊 token 等。词表一旦确定，模型的 embedding 层和输出层大小也就确定了。  

一个模型的 词表 vocab，本质上就是模型“认识的最小文字积木清单”。  

你可以把它理解成：模型不会直接读“自然语言”，它读的是一串数字。  
而 vocab 就是：  
也就是：哪些文本片段可以被映射成数字 ID？  

例如一个很小的 vocab 可能长这样：  
ID 0: <pad>  
ID 1: <unk>  
ID 2: 我  
ID 3: 喜欢  
ID 4: 吃  
ID 5: 苹果  
ID 6: app  
ID 7: le（后缀片段）  

那么句子：  
我喜欢吃苹果  

可能会被切成：  
我 / 喜欢 / 吃 / 苹果  

再变成：  
[2, 3, 4, 5]  

词表不是人手一个个写出来的  
现代大模型的 vocab 通常不是人工手写的，而是用大量文本数据自动训练出来的。  

大致流程是：  
大量语料  
  ↓  
统计文本里哪些字符、词、片段经常一起出现  
  ↓  
合并高频片段  
  ↓  
得到一个固定大小的词表  

比如模型设计者会先决定：  
我要一个 32K 词表  

也就是大概 32,000 个 token。  

然后 tokenizer 训练算法会从海量文本里学习：  
哪些字、词、子词、符号值得放进词表  

为什么不直接用“字”？  
比如中文可以按字切：  
我 / 喜 / 欢 / 吃 / 苹 / 果  

优点是简单，几乎不会遇到生词。  

但缺点是句子会变长。模型处理的是 token 数量，token 越多，计算越慢、上下文占用越大。  

例如：  
中华人民共和国  

按字切是：  
中 / 华 / 人 / 民 / 共 / 和 / 国  

但如果这个词很常见，放进 vocab 里就可以变成一个 token：  
中华人民共和国  

这样更省 token。  

为什么不直接用“词”？  
英文按词好像很自然：  
I / love / programming  

但问题是词太多了。  

比如：  
program  
programs  
programming  
programmer  
programmable  

如果每个词都放进 vocab，词表会爆炸。  

而且遇到新词怎么办？比如：  
ChatGPTify  
superprogramming  

所以现代模型通常用 子词 subword。  

子词是折中方案  
子词介于“字”和“词”之间。  
例如：  
programming  

可能被切成：  
program / ming  

或者：  
programm / ing  

再比如：  
unbelievable  

可能被切成：  
un / believable  

或者：  
un / believe / able  

这样做的好处是：  
常见词：尽量整个保留  
罕见词：拆成小片段  
新词：也能拆出来  

所以 vocab 里既有：  
我、的、是、了  

也有：  
中国、模型、训练、token、function、ing、tion  

还会有：  
空格、换行、标点、代码符号、emoji  

常见 vocab 训练算法  
主要有这几类：  
1. BPE  
Byte Pair Encoding，很多 GPT 系模型用过类似思路。  

它的想法很简单：  
一开始把文本拆得很细，比如字符或字节：  
l o w  
l o w e r  
n e w e s t  

然后统计最常一起出现的相邻片段。  

假设：  
l + o  

经常一起出现，那就合并成：  
lo  

再发现：  
lo + w  

经常一起出现，就合并成：  
low  

不断合并，直到词表达到目标大小。  

所以 BPE 的核心是：高频相邻片段不断合并。  

2. WordPiece  
BERT 里常见。  

它也会拆子词，但更偏向选择能够提高语言建模概率的片段。  

例如：  
playing  

可能被切成：  
play / ing（后缀）  

这里的 ing 表示它不是一个独立词，而是接在前面的后缀。  

3. Unigram / SentencePiece  
很多多语言模型会用 SentencePiece。  

它会先准备一堆候选子词，然后通过概率模型逐渐删掉不重要的，留下最有用的一组。  

它的特点是对中文、日文、英文、空格处理都比较统一。  

vocab 里面通常有什么？  
一个真实模型的 vocab 通常包含：  
1. 特殊 token  
   <pad>, <unk>, <bos>, <eos>, <mask>  

2. 高频字符  
   中、国、我、你、的、a、b、c  

3. 高频词或子词  
   模型、训练、数据、tion、ing、pre、auto  

4. 标点符号  
   ，。！？,.!?  

5. 空格和换行  
   " ", "\n", "\t"  

6. 代码符号  
   { } [ ] ( ) => == != import def class  

7. 数字  
   0 1 2 3 或者 2024、100、000 等片段  

8. 多语言片段  
   中文、英文、日文、韩文、法语等  
代码模型的 vocab 里，代码相关 token 会更多，比如：  
def  
class  
return  
import  
self  
function  
const  
async  
await  

词表大小怎么决定？  
词表不是越大越好，也不是越小越好。  
vocab 太小  
比如只有 几千个 token，那么很多文本会被切得很碎：  
internationalization  

可能变成：  
i / n / t / er / n / at / ion / al / iz / at / ion  

问题是：  
序列变长  
计算变慢  
上下文浪费  

vocab 太大  
比如几十万 token，很多词可以直接表示，但问题是：  
embedding 参数变多  
输出层参数变大  
训练成本增加  
罕见 token 学不好  

因为每个 token 都要有自己的向量。  

所以常见大模型词表大小大概在：  
几十K 到二十几万  

比如 32K、50K、100K、128K、150K 都很常见。  

用一个比喻理解  
你可以把 vocab 想象成一盒乐高积木。  

如果积木太少：  
什么都能拼，但每个东西都要拼很久。  

如果积木太多：  
很多成品块都有了，但盒子巨大、管理成本高，而且很多块很少用。  

好的 vocab 设计就是：用有限数量的积木，尽可能高效地拼出世界上大多数文本。  

最核心的一句话  
模型的 vocab 是通过大量文本自动统计/训练出来的一套“常用文本片段清单”。  
它的目标不是符合人类语言学里的“词”，而是让文本变成 token 时：  
尽量短  
尽量稳定  
尽量覆盖多语言和代码  
尽量少遇到未知字符  
训练和推理成本可控  

所以你看到的 token，有时候像一个字，有时候像一个词，有时候像半个词，有时候甚至只是空格或标点。
