# 20. tokenizer 里的 normalization 和 pre-tokenization 分别在做什么？为什么重要？

## 回答

normalization 在模型编码前统一文本形式，例如 Unicode 规范化、全半角转换、大小写处理、空白符处理或重音符号处理。它减少了同一语义的多种写法，但某些操作会损失原始信息。

pre-tokenization 则先按较粗的边界切开文本，例如识别空格、标点、数字、代码符号或特殊模式，再交给 BPE、WordPiece 等子词算法细分。它决定哪些字符可以跨边界合并。

二者会影响 token 数、ID、可逆性和模型行为。训练、评估、索引与在线推理若不一致，即使原始文本相同，也可能产生不同输入序列。

## 面试要点

normalization 解决“文本先变成什么样”，pre-tokenization 解决“先按哪些边界拆”；两者都属于 tokenizer 契约的一部分。


在 tokenizer 流程中，二者的位置通常是：

```text
原始文本
  → Normalization
  → Pre-tokenization
  → BPE / WordPiece / Unigram
  → token ID
```

核心区别：

* **Normalization：修改或统一文本的表示形式**
* **Pre-tokenization：确定后续子词算法处理哪些文本区间**

## 1. Normalization：文本规范化

Normalization 接收原始字符串，输出另一个规范化后的字符串。

常见操作包括：

* Unicode 规范化：NFC、NFD、NFKC、NFKD
* 大小写统一
* 去除重音符号
* 统一全角和半角字符
* 清理控制字符
* 统一空白字符
* 替换某些特殊字符
* 在特定字符周围插入空格

例如，某个 tokenizer 的 normalizer 可能进行：

```text
原始文本：Ｈéllo
规范化后：hello
```

这里只是说明可能的处理；是否转换全角、转小写或去重音，由具体 tokenizer 配置决定。

### Unicode 规范化的作用

视觉上相同的字符可能有不同的底层 Unicode 表示。例如，“é”既可以表示为：

```text
单个码点：é
```

也可以表示为：

```text
e + 组合重音符号
```

如果不规范化，它们可能得到不同的 token 序列。Normalization 可以把它们转换成统一形式。

### Normalization 可能有损

例如：

* 转小写会丢失大小写信息
* 去重音会让不同拼写变得相同
* NFKC 可能合并视觉或语义相近的兼容字符
* 清理控制字符可能丢失原始内容

所以代码、数学表达式、实体名称等任务不一定适合激进规范化。

## 2. Pre-tokenization：预切分

Pre-tokenization 将规范化后的字符串划分成若干文本区间，供 BPE、WordPiece 或 Unigram 继续处理。

常见切分依据包括：

* 空格
* 标点
* 数字与字母边界
* 正则表达式
* 换行
* 语言相关边界

例如：

```text
输入：Hello, world!
```

某个 pre-tokenizer 可能得到：

```text
["Hello", ",", "world", "!"]
```

之后，子词算法才会继续处理这些片段。例如，WordPiece 可能进一步把某个单词切成多个子词。

因此，pre-tokenization 的结果通常还不是最终 token，也没有完成 token ID 映射。

## 3. Pre-tokenization 不等于分词

“pre-tokenization”容易被理解成传统意义上的中文分词，但它不一定识别语言学上的词。

例如，它可以只是：

* 按空格和标点切分
* 使用正则划分字符类型
* 记录空格属于后一个片段还是前一个片段
* 将文本转换成字节级表示
* 阻止 BPE 跨越指定边界合并

以 BPE 为例，如果 pre-tokenizer 先得到：

```text
["New", "York"]
```

后续 BPE 通常只在各自区间内部应用合并规则，不会把跨空格的 `New York` 合成一个 token。实际能否跨边界取决于 tokenizer 的具体实现和配置。

## 4. 二者的本质区别

| 维度            | Normalization | Pre-tokenization      |
| ------------- | ------------- | --------------------- |
| 输入            | 原始字符串         | 规范化后的字符串              |
| 输出            | 新字符串          | 一组字符串区间或 span         |
| 主要目的          | 统一文本表示        | 建立后续切分边界              |
| 是否修改字符        | 经常修改          | 主要划分，也可能加入空格标记或进行字节映射 |
| 是否生成最终 token  | 否             | 否                     |
| 是否使用 BPE 合并规则 | 否             | 否                     |
| 是否使用最终词表      | 通常不使用         | 通常不使用                 |
| 是否影响 offset   | 会             | 会                     |
| 是否可能丢失信息      | 可能            | 通常较少，但取决于实现           |

最简洁的理解是：

```text
Normalization：
“这些字符应该以什么形式出现？”

Pre-tokenization：
“哪些字符应该先放在同一个候选区间里？”
```

而 BPE、WordPiece、Unigram 负责回答：

```text
“每个候选区间最终由哪些词表 token 表示？”
```

## 5. 不同 tokenizer 的常见做法

### BERT WordPiece

典型流程是：

```text
BertNormalizer
→ BertPreTokenizer
→ WordPiece
```

Normalization 可能处理大小写、重音、控制字符；pre-tokenization 通常围绕空格和标点建立边界；最后 WordPiece 在每个预切分结果中做最长匹配。

### Byte-level BPE

常见流程是：

```text
轻量或无 normalization
→ 正则预切分 + ByteLevel 处理
→ BPE
```

Pre-tokenizer 可能保留空格信息，并把 UTF-8 字节映射到可处理的基础符号。这里的“byte-level”不只是 normalization。

### SentencePiece

SentencePiece 通常直接处理原始句子：

```text
SentencePiece normalization
→ 空格元符号处理
→ BPE 或 Unigram
```

它常把空格编码成类似 `▁` 的符号，因此不依赖传统的“先按空格分词”。这也是 SentencePiece 常被称为语言无关 tokenizer 的原因之一。

## 6. 为什么两者必须保持一致

训练与推理阶段必须采用相同的 normalization 和 pre-tokenization 配置。

例如训练时转小写、推理时保留大小写，会改变最终 token 序列；检索系统中，如果文档和查询使用不同的规范化规则，还可能导致关键词匹配和向量表示不一致。

要确定一个具体模型做了什么，必须查看其 tokenizer 配置，例如 `tokenizer.json` 中的 `normalizer`、`pre_tokenizer` 和 `model` 配置；仅根据模型声称使用 BPE 或 WordPiece，无法推出前两个阶段的具体行为。
