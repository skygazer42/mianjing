# 09. token 太细和 token 太粗各有什么问题？

## 回答

token 设计是在序列长度与词表规模之间取折中。

- token 太细，例如接近逐字符或逐字节切分：词表小、覆盖新词容易，但序列会很长。长序列会增加 attention 计算、KV cache 显存和上下文占用，也更难把高频短语作为整体学习。
- token 太粗，例如大量整词、整段或领域短语直接进词表：序列较短，但词表、embedding 和输出层都会变大；低频 token 的训练样本稀少，参数难学好，还会遇到长尾词和 OOV 问题。

subword tokenizer 的目标就是让高频片段尽量整体保留，把罕见词拆成可复用的小片段。

## 面试要点

评价“粗细”不能只看平均 token 数，还要同时看词表参数量、长尾覆盖率、下游任务效果、多语言公平性和编码速度。






## 09. Token 太细和太粗各有什么问题

Token 粒度本质上是在权衡两件事：

```text
序列长度
vs.
词表大小与泛化能力
```

* **Token 太细**：一个 token 表示的内容很少，例如字符、字节。
* **Token 太粗**：一个 token 表示的内容很多，例如完整单词、长短语。

---

# 一、Token 太细的问题

例如把英文按字符切分：

```text
unbelievable
→ u n b e l i e v a b l e
```

本来一个词，变成了 12 个 token。

## 1. 序列会变得很长

同一段文本需要更多 token 表示。

例如：

```text
artificial intelligence
```

按单词或子词切分，可能只需要几个 token；按字符切分则需要二十多个 token。

这会导致：

```text
相同上下文窗口中能容纳的实际内容更少
```

假设模型上下文窗口是 1000 token：

* 平均每个单词 1.3 token，可以放约 770 个单词；
* 平均每个单词 5 token，只能放约 200 个单词。

---

## 2. 计算成本更高

Transformer 按 token 位置进行计算。

Token 越多：

* 前向计算次数越多；
* 注意力计算越重；
* KV Cache 占用越大；
* 推理延迟越高。

传统全注意力的计算复杂度通常与序列长度平方相关：

```text
O(n^2)
```

如果 token 数从 1000 增加到 4000，注意力矩阵规模理论上会变成原来的：

```text
(4000 / 1000)^2 = 16
```

实际系统还受 FlashAttention、稀疏注意力、带宽等因素影响，但序列变长通常仍会显著增加成本。

---

## 3. 模型需要更多步骤才能理解一个词

例如：

```text
internationalization
```

如果拆得太细，模型需要组合许多 token，才能形成完整词义。

这会增加学习难度：

```text
字符 → 字符组合 → 词素 → 单词 → 语义
```

模型需要用更多层和更多注意力操作，才能恢复高层语义。

---

## 4. 长距离依赖变得更难

假设两个词在文本中相隔 100 个单词。

如果每个单词平均：

* 1.5 token，那么距离约为 150 token；
* 5 token，那么距离约为 500 token。

Token 太细会把语义单位之间的距离拉长，使模型更难建立远距离关系。

---

## 5. 生成更容易在词内部出错

当一个词需要逐字符或逐字节生成时，模型可能生成：

* 拼写错误；
* 非法字节组合；
* 不完整 Unicode 字符；
* 错误的词缀组合。

例如模型可能把：

```text
necessary
```

错误生成成：

```text
neccessary
```

如果整个常见词是一个 token，这类词内错误通常更少。

---

## 6. 输出速度更慢

大模型生成通常是逐 token 进行的。

如果相同一句话需要更多 token：

```text
生成 token 数增加
→ 解码步骤增加
→ 响应更慢
```

即使每一步耗时相同，字符级 tokenizer 也可能需要显著更多生成步骤。

---

# 二、Token 太粗的问题

例如把整个单词作为 token：

```text
unbelievable
→ ["unbelievable"]
```

甚至把长短语作为单个 token：

```text
machine learning model
→ ["machine learning model"]
```

这样虽然序列变短，但也会带来其他问题。

---

## 1. 词表会非常大

自然语言中的单词数量几乎没有固定上限，因为还包括：

* 人名；
* 地名；
* 专业术语；
* 新词；
* 拼写变化；
* 数字；
* URL；
* 代码标识符；
* 多语言词汇。

如果希望每个完整单词都成为一个 token，词表可能达到数百万甚至更大。

词表越大，通常意味着：

* embedding 矩阵更大；
* 输出分类层更大；
* 参数量增加；
* 显存占用增加；
* 每步计算所有候选 token 的成本更高。

输出层通常需要计算：

```text
logits = hW
```

其中 (W) 的列数与词表大小相关。词表过大会增加输出层计算量。

---

## 2. 生词和罕见词难处理

假设词表中没有：

```text
microarchitectural
```

如果按完整单词切分，模型只能：

* 使用 `<unk>`；
* 临时退回字符或字节；
* 或完全无法编码。

这会造成信息损失。

子词 tokenizer 则可以拆成类似：

```text
micro + architect + ural
```

即使没有见过完整单词，也能组合出它的表示。

---

## 3. 泛化能力变差

考虑以下词：

```text
play
playing
played
player
replay
```

如果每个都是独立 token，模型必须分别学习它们。

它很难直接共享这些词之间的结构：

```text
play
-ing
-ed
-er
re-
```

采用子词 token 后，词根和词缀可以共享表示，模型更容易理解词形变化。

---

## 4. 低频 token 学习不充分

词表越大，很多 token 出现频率越低。

例如某个罕见专有名词可能在整个训练集中只出现几十次。它对应的 embedding 缺少足够训练，质量会很差。

这会形成所谓的长尾问题：

```text
少量高频 token 被充分训练
大量低频 token 训练不足
```

---

## 5. 相似文本可能被编码成完全不同的 token

例如：

```text
color
colour
Color
COLOR
colors
```

如果粒度过粗，它们可能分别对应不同 token。

虽然含义高度相关，但 tokenizer 层面无法共享内部结构，模型需要自己从数据中学习它们之间的关系。

对于代码也很明显：

```text
getUserName
getUsername
get_user_name
getUserNames
```

完整标识符 token 化会产生严重的词表爆炸和数据稀疏问题。

---

## 6. 拼写错误处理能力差

例如：

```text
environment
enviroment
environmnet
```

如果完整单词是 token，后两个拼写错误可能不在词表中。

使用子词或字节级 token 时，即使拼写错误，也能被编码，并保留大部分字符信息。

---

## 7. 多语言覆盖困难

如果按整词建立词表，需要同时覆盖：

* 英语单词；
* 中文词语；
* 日语词语；
* 阿拉伯语词形；
* 德语复合词；
* 各种专业和地域用语。

例如德语复合词理论上可以不断组合，无法穷举。

Token 太粗时，多语言词表很容易失控。

---

# 三、两者的核心矛盾

| 粒度  | 优点             | 问题             |
| --- | -------------- | -------------- |
| 字节级 | 几乎能表示任意内容，词表很小 | 序列长，语义单位被拆散    |
| 字符级 | 无词外问题，拼写结构清晰   | 序列仍然很长         |
| 子词级 | 词表和序列长度较平衡     | 切分结果不总符合自然语言直觉 |
| 单词级 | 序列短，语义单位完整     | 词表巨大，生词严重      |
| 短语级 | 序列更短           | 数据稀疏、泛化差、词表爆炸  |

---

# 四、为什么大模型通常使用子词 token

现代大模型通常选择中间方案：

```text
常见词或常见片段 → 较大的 token
罕见词 → 拆成较小的子词或字节
```

例如：

```text
unhappiness
→ un + happiness
```

或者：

```text
tokenization
→ token + ization
```

这种设计可以同时获得：

1. 常见文本的序列不会太长；
2. 生词仍然能够编码；
3. 词根和词缀可以共享；
4. 词表大小可控；
5. 可以支持多语言、代码和特殊符号。

# 五、一个直观例子

假设需要编码：

```text
The tokenizer misclassified ChatGPT2026.
```

## 粒度太细

```text
T h e _ t o k e n i z e r ...
```

问题：

* token 数很多；
* 上下文浪费；
* 生成速度慢。

## 粒度太粗

```text
["The", "tokenizer", "misclassified", "ChatGPT2026", "."]
```

问题：

* `ChatGPT2026` 可能不在词表；
* `misclassified` 可能是低频 token；
* 相似词之间无法共享结构。

## 较合理的子词切分

```text
["The", " tokenizer", " mis", "classified", " Chat", "GPT", "2026", "."]
```

它既不会过细，也不要求每个完整词都提前存在于词表中。

---

# 核心结论

**Token 太细：**

```text
词表小、覆盖强
但序列长、计算贵、上下文利用率低
```

**Token 太粗：**

```text
序列短、单个 token 语义完整
但词表大、生词多、数据稀疏、泛化能力差
```

理想 tokenizer 的目标不是让 token 尽可能大或尽可能小，而是寻找一个平衡点：

```text
较短的序列
+
可控的词表
+
较强的生词泛化能力
```
