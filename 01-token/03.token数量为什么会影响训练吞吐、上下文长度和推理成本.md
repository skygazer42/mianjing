# 03. token 数量为什么会影响训练吞吐、上下文长度和推理成本？

这里的上下文长度，可以理解为：  
上下文窗口 = 输入 tokens + 已经生成的输出 tokens  

训练吞吐一般指模型单位时间内能处理多少 token。token 数量越多，模型要处理的数据量就越大，训练吞吐通常会下降。上下文长度指模型一次前向传播最多能处理多少 token；如果 token 数超过窗口上限，模型就无法完整接收这些内容。推理成本则指推理阶段处理 token 需要的计算、显存和时间。token 越多，推理通常越贵。  

## 03.1 先看一个直观例子

比如两批数据：  
A: 每句话 100 tokens  
B: 每句话 1000 tokens  

如果 batch size 都是 8：  
A: 一批 = 8 × 100 = 800 tokens  
B: 一批 = 8 × 1000 = 8000 tokens  

B 这一批要处理的 token 是 A 的 10 倍，计算量和显存都更大  

## 03.2 为什么 attention 对 token 数特别敏感

Transformer 里面最核心的结构是 self-attention。  
它会让每个 token 看其他 token。  

如果一句话有 5 个 token：  
每个 token 看 5 个 token  
总关系数量 = 5 × 5 = 25  

如果一句话有 1000 个 token：  
总关系数量 = 1000 × 1000 = 1,000,000  

所以注意力计算大致和：  
seq_len²  

有关。  

这就是为什么 token 数变长以后，训练吞吐会明显下降。  

模型每秒能训练多少 token  

batch_size = 8  
seq_len = 2048  
step_time = 0.5 秒  

每步 token 数 = 8 × 2048 = 16384 tokens  
 16384 / 0.5 = 32768 tokens/s  

那是不是每个模型吞吐是固定的？  
不是。  

同一个模型，在不同硬件、不同 batch size、不同 seq_len、不同精度下，吞吐都不一样。  

比如同一个 7B 模型：  
| 条件 | 吞吐 |
| --- | --- |
| 4090 单卡 fp16 | 一个吞吐 |
| A100 单卡 bf16 | 另一个吞吐 |
| 8 卡 A100 | 更高吞吐 |
| seq_len=512 | 一个吞吐 |
| seq_len=8192 | 又变了 |
| batch_size 太小 | GPU 吃不满，吞吐低 |
| batch_size 太大 | 显存爆，跑不了 |


所以训练吞吐不是模型的固定属性，而是：  
模型 + 硬件 + batch_size + seq_len + 精度 + 框架优化  

共同决定的。  

训练耗时 = attention 耗时 + MLP 耗时 + backward 耗时 + 通信耗时 + 显存读写耗时  

## 03.3 从标准 Transformer 的计算过程看

以 标准 Transformer 为例，可以这样理解：  
token 数量 S  
↓  
决定 Transformer 一次要处理多长的序列  
↓  
影响三个东西：  
1. 训练吞吐：每秒训练多少 token  
2. 上下文长度：一次最多能看多少 token  
3. 推理成本：处理输入 + 生成输出要花多少算力/显存/钱  
先定义几个变量：  
B = batch size，一次喂几条样本  
S = seq_len，每条样本多少 token  
D = hidden size，隐藏维度  
L = layers，Transformer 层数  
H = attention heads，注意力头数  

## 03.4 训练吞吐：每秒训练多少 token

训练吞吐通常是：  
training throughput = tokens / second  

也就是：  
训练吞吐 = 每 step 训练的 token 数 / 每 step 用时  

每 step 训练的 token 数是：  
B × S  

比如：  
```python
B = 8
S = 2048
step_time = 0.5

tokens_per_step = B * S
throughput = tokens_per_step / step_time

print(tokens_per_step)  # 16384
print(throughput)       # 32768 tokens/s
```

所以吞吐不是“模型最多能吃多少 token”，而是：  
这个模型在这个硬件和训练配置下，每秒实际消化多少 token。  

但是注意：同样 token 数，seq_len 不同，计算量不同  
比如这两种：  
A: B = 16, S = 512  
B: B = 1,  S = 8192  

它们每 step 都是：  
16 × 512 = 8192 tokens  
1 × 8192 = 8192 tokens  

但计算量不一样。  

因为 self-attention 是每条样本内部做的，大约是：  
attention 计算量 ≈ B × S²  

算一下：  
```text
a = 16 × 512^2
b = 1 × 8192^2

print(a)
print(b)
print(b / a)
```

结果：  
4194304  
67108864  
16.0  

意思是：  
同样都是 8192 tokens，  
1 条 8192 长文本 的 attention 计算量，是 16 条 512 短文本 的 16 倍。  

所以训练吞吐不是只看总 token 数，还要看这些 token 是怎么分布的。  

Transformer 训练计算大致分两块  
一层 Transformer 主要有：  
1. Attention：大约 O(B × S² × D)  
2. MLP/FFN：大约 O(B × S × D²)  
所以：  
短上下文时：  
MLP 可能更重  

长上下文时：  
attention 的 S² 会越来越明显  

因此：  
S 越长  
→ 每个 token 越贵  
→ step_time 变长  
→ tokens/s 下降  

这就是 token 数影响训练吞吐的核心。  

## 03.5 上下文长度：一次最多能看多少 token

上下文长度是：  
context length = 模型一次最多能接受多少 token  

比如模型上下文是：  
8192 tokens  

意思是：  
输入 prompt + 历史对话 + 要生成的输出  
总共不能超过 8192 tokens  

不是 8192 个字，也不是 8192 个词，而是 tokenizer 切完后的 token。  

例如：  
系统提示词：1000 tokens  
历史对话：5000 tokens  
用户问题：1000 tokens  

那已经用了：  
1000 + 5000 + 1000 = 7000 tokens  

如果上下文窗口是 8192，那么理论上最多还能生成：  
8192 - 7000 = 1192 tokens  

为什么 Transformer 上下文长度有限？  
因为 attention 要算 token 两两关系：  
attention matrix shape = [B, H, S, S]  

比如 S = 2048：  
每个 head 要看 2048 × 2048 个关系  

如果 S = 8192：  
8192 × 8192  

关系数量变成 16 倍。  

用代码看：  
```python
for S in [1024, 2048, 4096, 8192]:
    attention_pairs = S * S
    print(S, attention_pairs)
```

输出：  
1024 1048576  
2048 4194304  
4096 16777216  
8192 67108864  

所以：  
上下文越长  
→ attention 矩阵越大  
→ 显存越大  
→ 计算越慢  

这就是标准 Transformer 的长上下文瓶颈。  

## 03.6 推理成本：输入成本 + 输出成本

推理分两段：  
1. prefill：处理输入 prompt  
2. decode：一个 token 一个 token 生成输出  
  prefill：处理输入 token  
假设你的输入有 S = 8000 tokens。  

模型要先把这 8000 个 token 全部读进去，建立上下文。  

这一步叫：  
prefill  
prefill 的 attention 还是接近：  
O(S²)  

所以输入越长，prefill 越慢。  

比如：  
输入 1000 tokens：还好  
输入 10000 tokens：明显慢  
输入 100000 tokens：非常吃显存和算力  

  decode：生成输出 token  
生成时，Transformer 通常是一个 token 一个 token 往外吐：  
第 1 步：生成 token_1  
第 2 步：生成 token_2  
第 3 步：生成 token_3  
...  

如果没有 KV cache，每次都重新算全部历史，会非常慢。  

所以推理时会用：  
KV cache  

可以理解成：  
模型把之前 token 的中间结果缓存起来，生成下一个 token 时不用完全重算。  

但是 KV cache 也要占显存。  

KV cache 大小大约是：  
KV cache ≈ 2 × L × B × S × D × bytes  

其中 2 是因为有 K 和 V 两份。  

比如：  
```python
def kv_cache_mb(B, S, L, D, bytes_per_element=2):
    total_bytes = 2 * L * B * S * D * bytes_per_element
    return total_bytes / 1024 / 1024

for S in [1024, 4096, 8192, 32768]:
    mb = kv_cache_mb(
        B=1,
        S=S,
        L=32,
        D=4096,
        bytes_per_element=2,
    )
    print(S, f"{mb:.1f} MB")
```

大概输出：  
1024 512.0 MB  
4096 2048.0 MB  
8192 4096.0 MB  
32768 16384.0 MB  

也就是：  
上下文 1024 tokens：KV cache 约 512MB  
上下文 8192 tokens：KV cache 约 4GB  
上下文 32768 tokens：KV cache 约 16GB  

这还只是 batch size = 1。  

如果并发是 8：  
16GB × 8 = 128GB  

所以推理长上下文和高并发很容易吃满显存。  

## 03.7 推理成本为什么和 token 数有关？

API 计费一般看：  
输入 token 数 + 输出 token 数  

但从计算角度看，输入和输出不完全一样。  

输入 token：prefill 阶段，prompt 越长，首 token 延迟越高  
输出 token：decode 阶段，生成越长，总耗时越长  
历史 token：KV cache 越长，显存越高  
并发 token：batching 越多，KV cache 越大  

举个例子：  
输入：8000 tokens  
输出：1000 tokens  

成本来自：  
1. 读 8000 tokens 的 prefill 成本  
2. 生成 1000 tokens 的 decode 成本  
3. 保存 9000 tokens 历史的 KV cache 显存成本  
所以不是只有输出贵，长输入也很贵。  

## 03.8 三者放在一起看

假设标准 Transformer：  
B = batch size  
S = seq_len  
D = hidden size  
L = layers  

核心关系是：  
训练每 step token 数 = B × S  

训练吞吐 = B × S / step_time  

attention 计算量 ≈ B × L × S² × D  

MLP 计算量 ≈ B × L × S × D²  

KV cache ≈ 2 × B × L × S × D  

因此：  
S 越长：  
attention 更贵  
上下文占用更大  
KV cache 更大  
推理更慢  

B 越大：  
每 step token 更多  
GPU 利用率可能更高  
但显存占用也更高  

## 03.9 最重要的区别

你可以这样记：  
训练吞吐：问的是每秒训练多少，单位是 tokens/s，通常越高越好  
上下文长度：问的是一次最多能看多少，单位是 tokens，是模型窗口上限  
推理成本：问的是跑一次要花多少，体现为 token 数、时间、显存和费用，输入/输出 token 越多越贵  

## 03.10 一句话总结

以 Transformer 为例：  
训练吞吐 是模型每秒处理多少 token，受 B × S 和 step time 影响；  
上下文长度 是单条序列最多能放多少 token，受 attention 和位置编码/KV cache 限制；  
推理成本 来自输入 prefill、输出 decode 和 KV cache，输入越长、输出越长、并发越高，成本越高。  

最关键的是：  
token 多 ≠ 一定吞吐高  

batch_size 变大：  
可能提高吞吐  

seq_len 变长：  
attention 是 S²，通常会降低吞吐、增加上下文和推理成本  

## 03.11 为什么长输入推理更贵：KV cache

KV cache  

模型把之前 token 的中间结果缓存起来，生成下一个 token 时不用完全重算。但是 KV cache 也要占显存。  
模型生成下一个 token 时，需要回看前面所有 token。KV cache 就是把前面 token 的 Key 和 Value 存下来，避免每生成一个 token 都重新算一遍历史。  

KV cache 大小大约是：  
KV cache ≈ 2 × L × B × S × D × bytes  

1. Transformer 里为什么有 K/V？  
Self-attention 里面每个 token 会生成三个东西：  
Q = Query  
K = Key  
V = Value  

可以粗略理解：  
Q：我现在这个 token 想找什么信息  
K：历史 token 提供什么索引  
V：历史 token 真正携带的信息  

attention 大概是：  
Attention(Q, K, V) = softmax(QKᵀ) V  

生成时，当前 token 的 Q 只需要当前这一步算；  
但是历史所有 token 的 K 和 V 每一步都会用到。  

所以推理时缓存的是：  
历史 tokens 的 K  
历史 tokens 的 V  

这就是 KV cache。  

2. 没有 KV cache 会怎样？  
假设 prompt 有 7000 tokens，现在要生成第 1 个 token。  

没有 KV cache：  
每生成一个新 token，都重新计算前面 7000 个 token 的 K/V  

生成第 2 个 token 时，又重新算：  
7001 个 token 的 K/V  

生成第 100 个 token 时，又重新算：  
7099 个 token 的 K/V  

这会非常浪费。  

有 KV cache 后：  
prompt 的 7000 个 token 的 K/V 算一次，存起来  
生成新 token 时，只算新 token 的 K/V，然后追加到 cache 里  

所以 KV cache 用显存换速度。  

3. KV cache 的核心形状  
对每一层 Transformer，K cache 和 V cache 的形状通常是：  
K cache: [batch_size, seq_len, num_kv_heads, head_dim]  
V cache: [batch_size, seq_len, num_kv_heads, head_dim]  

或者框架里也可能排成：  
[batch_size, num_kv_heads, seq_len, head_dim]  

顺序可能不同，但元素数量一样。  

关键变量：  
B = batch size / 并发数  
S = 当前上下文 token 数，包括输入 + 已生成输出  
L = Transformer 层数  
H_kv = KV heads 数量  
D_head = 每个 head 的维度  
bytes = 每个元素占多少字节，fp16/bf16 通常是 2 bytes  

4. KV cache 公式  
因为有 K 和 V 两份，所以乘 2。  

KV cache bytes =  
2 × B × S × L × H_kv × D_head × bytes  

这就是最准确的基础公式。  

如果是普通 Multi-Head Attention，通常：  
H_kv = num_attention_heads  
H_kv × D_head = hidden_size  

那公式可以简化成：  
KV cache bytes =  
2 × B × S × L × hidden_size × bytes  

但是很多新模型用 GQA / MQA，这时候不能直接用 hidden_size。  

## 03.12 完整链路示例：vocab → token → id → embedding → KV cache

下面用一个完整玩具例子，从头到尾走一遍。  

### 0. 先造一个小词表 vocab

真实大模型词表可能有几万到几十万个 token。我们这里造一个超小词表：  
```python
vocab = {
    "<bos>": 0,
    "I": 1,
    " love": 2,
    " 我": 3,
    " AI": 4,
    " you": 5,
    ".": 6,
}
```

注意这里有些 token 前面带空格：  
" love"  
" 我"  
" AI"  
" you"  

这是正常的。很多 tokenizer 会把空格和后面的词绑在一起。  

反向词表：  
```python
id_to_token = {
    0: "<bos>",
    1: "I",
    2: " love",
    3: " 我",
    4: " AI",
    5: " you",
    6: ".",
}
```

### 1. 一句话先变成 tokens

假设输入文本是：  
I love 我  

tokenizer 可能切成：  
```python
tokens = ["<bos>", "I", " love", " 我"]
```

注意不是：  
["I", "love", "我"]  

而是：  
["I", " love", " 我"]  

因为空格可能被合进 token。  

### 2. tokens 变成 token ids

查词表：  
"<bos>" → 0  
"I"     → 1  
" love" → 2  
" 我"   → 3  

所以：  
token_ids = [0, 1, 2, 3]  

到这里，大模型看到的是：  
[0, 1, 2, 3]  

不是原始字符串。  

### 3. token ids 变成 embedding

我们给每个 token 一个 2 维 embedding。真实模型可能是 4096 维、8192 维，这里为了好算只用 2 维。  

```python
import numpy as np

embedding_table = np.array([
    [0.0, 0.0],  # id 0: <bos>
    [1.0, 0.0],  # id 1: I
    [0.0, 1.0],  # id 2: love
    [1.0, 1.0],  # id 3: 我
    [2.0, 1.0],  # id 4: AI
    [1.0, 2.0],  # id 5: you
    [0.5, 0.5],  # id 6: .
])
```

现在输入：  
```python
token_ids = [0, 1, 2, 3]

查 embedding：
X = embedding_table[token_ids]

print(X)
```

得到：  
[  
  [0.0, 0.0],  # <bos>  
  [1.0, 0.0],  # I  
  [0.0, 1.0],  # love  
  [1.0, 1.0],  # 我  
]  

也就是：  
token id 0 → [0, 0]  
token id 1 → [1, 0]  
token id 2 → [0, 1]  
token id 3 → [1, 1]  

所以：  
token ids: [0, 1, 2, 3]  

变成 embedding:  

```text
X =
[
  [0, 0],
  [1, 0],
  [0, 1],
  [1, 1]
]
```

形状是：  
[seq_len, hidden_size] = [4, 2]  

### 4. embedding 继续变成 Q/K/V

Transformer attention 不直接用 X，而是通过三个矩阵变成：  
Q = X @ Wq  
K = X @ Wk  
V = X @ Wv  

我们设置三个简单权重矩阵：  
```python
Wq = np.array([
    [1.0, 0.0],
    [0.0, 1.0],
])

Wk = np.array([
    [1.0, 0.0],
    [1.0, 1.0],
])

Wv = np.array([
    [1.0, 1.0],
    [0.0, 1.0],
])
```

算：  
```python
Q = X @ Wq
K = X @ Wk
V = X @ Wv

print("Q:")
print(Q)

print("K:")
print(K)

print("V:")
print(V)
```

得到：  
Q =  
[  
  [0, 0],  
  [1, 0],  
  [0, 1],  
  [1, 1]  
]  

K =  
[  
  [0, 0],  # <bos> 的 K  
  [1, 0],  # I 的 K  
  [1, 1],  # love 的 K  
  [2, 1],  # 我 的 K  
]  

V =  
[  
  [0, 0],  # <bos> 的 V  
  [1, 1],  # I 的 V  
  [0, 1],  # love 的 V  
  [1, 2],  # 我 的 V  
]  

### 5. KV cache 存的就是 K 和 V

现在输入 [0, 1, 2, 3] 已经处理完了。  

KV cache 里面存：  
```text
K_cache = [
    [0, 0],
    [1, 0],
    [1, 1],
    [2, 1],
]

V_cache = [
    [0, 0],
    [1, 1],
    [0, 1],
    [1, 2],
]
```

对应关系是：  
<bos>：id=0，embedding=[0,0]，K=[0,0]，V=[0,0]  
I：id=1，embedding=[1,0]，K=[1,0]，V=[1,1]  
love：id=2，embedding=[0,1]，K=[1,1]，V=[0,1]  
我：id=3，embedding=[1,1]，K=[2,1]，V=[1,2]  

这句话最重要：  
KV cache 存的不是 token id，也不是 embedding，而是每一层 attention 里算出来的 K 和 V。  

### 6. 现在用最后一个 token 预测下一个 token

当前输入是：  
<bos> / I / love / 我  

也就是：  
[0, 1, 2, 3]  

模型要预测下一个 token。  

最后一个 token 是：  
" 我"  

它的 query 是：  
q_我 = [1, 1]  

现在它拿这个 q_我 去和所有历史 K 做匹配：  
q_我 · k_<bos> = [1, 1] · [0, 0] = 0  
q_我 · k_I     = [1, 1] · [1, 0] = 1  
q_我 · k_love  = [1, 1] · [1, 1] = 2  
q_我 · k_我    = [1, 1] · [2, 1] = 3  

所以 attention scores 是：  
[0, 1, 2, 3]  

实际会除以 sqrt(head_dim)，这里 head_dim = 2：  
scores / sqrt(2)  
≈ [0.000, 0.707, 1.414, 2.121]  

softmax 后：  
attention weights ≈ [0.065, 0.131, 0.266, 0.539]  

意思是模型现在更关注：  
" 我"    权重 0.539  
" love"  权重 0.266  
"I"      权重 0.131  
"<bos>"  权重 0.065  

然后用这个权重加权 V：  
context =  
0.065 * V_<bos>  
+ 0.131 * V_I  
+ 0.266 * V_love  
+ 0.539 * V_我  

代进去：  
context =  
0.065 * [0, 0]  
+ 0.131 * [1, 1]  
+ 0.266 * [0, 1]  
+ 0.539 * [1, 2]  

得到大约：  
context ≈ [0.670, 1.474]  

这个 context 后面会过 MLP / 输出层，最后得到每个词表 token 的概率。  

假设模型最后选择了：  
id 4 = " AI"  

于是模型生成了新 token：  
" AI"  

现在完整上下文变成：  
<bos> / I / love / 我 / AI  

对应 ids：  
[0, 1, 2, 3, 4]  

### 7. 重点来了：生成了 " AI" 后，KV cache 怎么更新？

新 token 是：  
id 4 = " AI"  

先查 embedding：  
id 4 → [2, 1]  

所以：  
x_AI = [2, 1]  

现在只需要给这个新 token 算 Q/K/V。  

  算新 token 的 Q  

q_AI = x_AI @ Wq  
     = [2, 1]  

  算新 token 的 K  

k_AI = x_AI @ Wk  

也就是：  
[2, 1] @ [  
  [1, 0],  
  [1, 1]  
]  

算出来：  
k_AI = [3, 1]  

  算新 token 的 V  

v_AI = x_AI @ Wv  

也就是：  
[2, 1] @ [  
  [1, 1],  
  [0, 1]  
]  

算出来：  
v_AI = [2, 3]  

### 8. 把新 K/V 追加到 KV cache

原来的 cache 是：  
K_cache =  
[  
  [0, 0],  
  [1, 0],  
  [1, 1],  
  [2, 1],  
]  

V_cache =  
[  
  [0, 0],  
  [1, 1],  
  [0, 1],  
  [1, 2],  
]  

生成 " AI" 后，追加：  
k_AI = [3, 1]  
v_AI = [2, 3]  

所以新的 cache 是：  
K_cache =  
[  
  [0, 0],  # <bos>  
  [1, 0],  # I  
  [1, 1],  # love  
  [2, 1],  # 我  
  [3, 1],  # AI，新追加  
]  

V_cache =  
[  
  [0, 0],  # <bos>  
  [1, 1],  # I  
  [0, 1],  # love  
  [1, 2],  # 我  
  [2, 3],  # AI，新追加  
]  

这就是 KV cache 的更新：  
旧的 K/V 不动  
新的 token 只算一次 K/V  
然后 append 到 cache  

### 9. 下一步预测时，用新 token 的 Q 看所有 K

现在要继续预测下一个 token。  

当前最后一个 token 是：  
" AI"  

它的 query 是：  
q_AI = [2, 1]  

它要和所有历史 K 做 attention：  
q_AI · k_<bos> = [2, 1] · [0, 0] = 0  
q_AI · k_I     = [2, 1] · [1, 0] = 2  
q_AI · k_love  = [2, 1] · [1, 1] = 3  
q_AI · k_我    = [2, 1] · [2, 1] = 5  
q_AI · k_AI    = [2, 1] · [3, 1] = 7  

除以 sqrt(2) 后：  
scores ≈ [0.000, 1.414, 2.121, 3.536, 4.950]  

softmax 后：  
attention weights ≈ [0.005, 0.022, 0.044, 0.182, 0.747]  

然后加权 V：  
context =  
0.005 * [0, 0]  
+ 0.022 * [1, 1]  
+ 0.044 * [0, 1]  
+ 0.182 * [1, 2]  
+ 0.747 * [2, 3]  

得到：  
context ≈ [1.698, 2.671]  

然后模型继续通过输出层预测下一个 token。  

### 10. 完整 NumPy 代码

你可以直接跑：  
```python
import numpy as np

np.set_printoptions(precision=3, suppress=True)

# 1. 词表
vocab = {
    "<bos>": 0,
    "I": 1,
    " love": 2,
    " 我": 3,
    " AI": 4,
    " you": 5,
    ".": 6,
}

id_to_token = {v: k for k, v in vocab.items()}

# 2. embedding 表，形状 [vocab_size, hidden_size]
embedding_table = np.array([
    [0.0, 0.0],  # 0: <bos>
    [1.0, 0.0],  # 1: I
    [0.0, 1.0],  # 2: love
    [1.0, 1.0],  # 3: 我
    [2.0, 1.0],  # 4: AI
    [1.0, 2.0],  # 5: you
    [0.5, 0.5],  # 6: .
])

# 3. Q/K/V 权重
Wq = np.array([
    [1.0, 0.0],
    [0.0, 1.0],
])

Wk = np.array([
    [1.0, 0.0],
    [1.0, 1.0],
])

Wv = np.array([
    [1.0, 1.0],
    [0.0, 1.0],
])

def softmax(x):
    x = x - np.max(x)
    exp_x = np.exp(x)
    return exp_x / exp_x.sum()

# 4. 输入文本：I love 我
tokens = ["<bos>", "I", " love", " 我"]
token_ids = [vocab[t] for t in tokens]

print("tokens:", tokens)
print("token_ids:", token_ids)

# 5. ids -> embeddings
X = embedding_table[token_ids]
print("\nX embeddings:")
print(X)

# 6. embeddings -> Q/K/V
Q = X @ Wq
K = X @ Wk
V = X @ Wv

print("\nQ:")
print(Q)
print("\nK:")
print(K)
print("\nV:")
print(V)

# 7. 初始化 KV cache
K_cache = K.copy()
V_cache = V.copy()

print("\n初始 K_cache:")
print(K_cache)
print("\n初始 V_cache:")
print(V_cache)

# 8. 用最后一个 token 的 Q 预测下一个 token
q_last = Q[-1]

scores = q_last @ K_cache.T / np.sqrt(2)
weights = softmax(scores)
context = weights @ V_cache

print("\n用最后一个 token 的 q 预测下一个 token")
print("q_last:", q_last)
print("scores:", scores)
print("attention weights:", weights)
print("context:", context)

# 假设模型生成了 id=4，也就是 " AI"
new_token_id = vocab[" AI"]
new_token = id_to_token[new_token_id]

print("\n模型生成:", new_token, "id =", new_token_id)

# 9. 新 token id -> embedding
x_new = embedding_table[new_token_id]

# 10. 只计算新 token 的 Q/K/V
q_new = x_new @ Wq
k_new = x_new @ Wk
v_new = x_new @ Wv

print("\n新 token embedding:", x_new)
print("q_new:", q_new)
print("k_new:", k_new)
print("v_new:", v_new)

# 11. append 到 KV cache
K_cache = np.vstack([K_cache, k_new])
V_cache = np.vstack([V_cache, v_new])

print("\n追加后的 K_cache:")
print(K_cache)
print("\n追加后的 V_cache:")
print(V_cache)

# 12. 用新 token 的 q 继续预测下一个 token
scores = q_new @ K_cache.T / np.sqrt(2)
weights = softmax(scores)
context = weights @ V_cache

print("\n用新 token 的 q 预测下一个 token")
print("scores:", scores)
print("attention weights:", weights)
print("context:", context)
```

## 03.13 你应该抓住这条完整链路

完整链路是：  
原始文本：  
I love 我  

经过 tokenizer：  
["<bos>", "I", " love", " 我"]  

查词表：  
[0, 1, 2, 3]  

查 embedding：  
[  
  [0, 0],  
  [1, 0],  
  [0, 1],  
  [1, 1]  
]  

算 Q/K/V：  
Q = X @ Wq  
K = X @ Wk  
V = X @ Wv  

存 KV cache：  
K_cache = [k_<bos>, k_I, k_love, k_我]  
V_cache = [v_<bos>, v_I, v_love, v_我]  

生成新 token：  
" AI" → id 4  

只算新 token：  
id 4 → embedding [2, 1]  
→ k_AI [3, 1]  
→ v_AI [2, 3]  

追加 KV cache：  
K_cache = [k_<bos>, k_I, k_love, k_我, k_AI]  
V_cache = [v_<bos>, v_I, v_love, v_我, v_AI]  

然后继续生成下一个 token。  

一句话：  
词表负责把 token 变成 id，embedding 负责把 id 变成向量，Wk/Wv 负责把向量变成 K/V，KV cache 负责把历史 token 的 K/V 存起来，下一步直接复用。
