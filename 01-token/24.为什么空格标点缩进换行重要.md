# 24. 为什么空格、标点、缩进、换行在 tokenizer 里也很重要？

## 结论先行

它们不是可以统一删除的“噪声”，而是文本的一部分。自然语言里的空格与标点携带词边界、句法和语气；代码和结构化数据里的缩进、换行、引号、逗号甚至直接决定语法。tokenizer 如何保留和压缩这些符号，会同时影响可逆性、序列长度以及模型对结构的学习。

## 自然语言中的信息

比较下面几组文本：

```text
Let's eat, Grandma.
Let's eat Grandma.

退款，不可以。
退款不？可以。
```

字符主体相近，标点却改变了句法和含义。空格也不仅用于美观：英文里 `therapist` 与 `the rapist` 不能在预处理时被合并为相同字符串；Markdown 中空行可能结束一个段落，换行与列表前缀共同表达层级。

许多 BPE tokenizer 会把**前导空格与后续词片段一起编码**。概念上可能出现：

```text
"hello"  -> [hello]
" hello" -> [▁hello] 或 [Ġhello]
```

这让常见的“空格 + 单词”模式成为一个 token，提升英文压缩率，也让句首和非句首的同一个词可能得到不同 id。

## 代码与结构化文本中的信息

Python 用缩进定义代码块：

```python
if ready:
    run()
cleanup()
```

如果删除换行或把缩进任意归一化，程序语义会改变。其他格式也有类似约束：

- JSON 的引号、逗号和括号决定键值与嵌套；
- YAML 的缩进决定层级，`-` 表示列表项；
- Markdown 的反引号、标题符和空行决定结构；
- shell 的引号、换行和转义可能改变命令边界；
- 数学表达式中的括号和运算符决定求值顺序。

所以代码模型不仅需要“认识关键词”，还需要高效编码连续空格、换行加缩进、常见运算符和注释模式。有些代码 tokenizer 会专门为多空格或常见符号组合分配 token，以避免一行缩进消耗大量序列位置。

## tokenizer 流水线中哪里会出问题

```text
原文 -> normalization -> pre-tokenization -> subword model -> decoder
```

任何一层都可能破坏格式：normalizer 合并连续空格，pre-tokenizer 丢弃分隔符，decoder 自动清理标点前空格，或者业务侧在调用 tokenizer 前执行 `.strip()`。一旦两个不同输入被规范化为相同序列，后续算法再强也无法恢复原文。

需要分别验证：

1. `decode(encode(text)) == text` 是否成立；
2. 特殊 token 被跳过时是否符合预期；
3. 制表符、CRLF、连续空格和 Unicode 空白是否保留；
4. 代码 formatter 或数据清洗是否在 tokenizer 之前改变文本。

## 保留所有格式也有代价

完全逐字符保留不会自动带来好效果。如果每个空格和换行都是单独 token，大量代码序列会被格式符占满。合理设计是在**无损覆盖**与**常见模式压缩**之间折中：保留原始字节信息，同时让高频缩进、换行和标点组合有更短表示。

过度把长格式模板合成单个 token 也有风险：词表槽位被低价值模式占用，轻微格式变化就无法命中，并可能削弱模型对内部结构的组合学习。因此要用真实代码与文档分布评估，而不是凭直觉添加符号 token。

## 面试回答要点

可以从三个场景回答：自然语言中它们表达边界、句法和语气；代码/JSON/YAML 中它们决定语法与层级；在 tokenizer 工程中，它们还影响是否可逆和 token 压缩率。最后强调，处理提示词模板、工具调用和代码时应使用目标 tokenizer 做 encode/decode 往返测试，不能在预处理阶段随意删空白。
