# 05. 中文、英文、代码的 tokenization 难点分别在哪里？

可以，这个问题非常重要。中文、英文、代码的 tokenization 难点不一样。  

一句话先讲：  
中文难在：没有天然空格  
英文难在：词形变化、空格和子词  
代码难在：符号、缩进、变量名、罕见组合很多  
## 05.1 中文 tokenization 难点

中文最大问题是：  
中文没有天然空格  
英文里：  
I love machine learning  

人很容易按空格切：  
["I", "love", "machine", "learning"]  

但中文：  
我喜欢机器学习  

到底怎么切？  

可能是：  
["我", "喜欢", "机器学习"]  

也可能是：  
["我", "喜欢", "机器", "学习"]  

也可能是：  
["我", "喜", "欢", "机", "器", "学", "习"]  

这就是中文的第一个难点：词边界不明显。  

中文还有歧义  
比如：  
南京市长江大桥  

可以理解成：  
南京市 / 长江大桥  

也可能被错误切成：  
南京 / 市长 / 江大桥  

人类知道大概率是“南京市 + 长江大桥”，但 tokenizer 只是根据词表和统计规律切。  

中文 token 数可能偏多  
如果 tokenizer 对中文支持不好，中文会被切得很碎。  

比如：  
我喜欢人工智能  

好的 tokenizer 可能切：  
["我", "喜欢", "人工智能"]  

差一点的可能切：  
["我", "喜", "欢", "人", "工", "智", "能"]  

这样 token 数变多，带来：  
上下文占用更多  
推理更慢  
成本更高  

所以中文 tokenization 的核心难点是：  
没有空格 + 词边界歧义 + 多字词识别  

## 05.2 英文 tokenization 难点

英文看起来简单，因为有空格。  
比如：  
I love machine learning  

但是英文真正难在：  
词形变化很多  

比如：  
run  
runs  
running  
runner  
unbelievable  
tokenization  
internationalization  

如果每个完整单词都进词表，词表会非常大。  

所以 tokenizer 经常会切成子词：  
unbelievable  
→ ["un", "believ", "able"]  

或者：  
tokenization  
→ ["token", "ization"]  

这就是英文的主要难点：词不是无限的，但词形组合非常多。  

英文空格也会进入 token  
很多 tokenizer 会把空格和后面的词绑定。  

比如：  
"I love AI"  

可能切成：  
["I", " love", " AI"]  

注意：  
"love"  

和：  
" love"  

可能是不同 token。  

这就是为什么你前面看到我写：  
" love"  
" AI"  
" 我"  

前面带空格。  

大小写、标点也是问题  

比如：  
Apple  
apple  
APPLE  

可能是不同 token。  

再比如：  
hello  
hello!  
hello.  
hello,  

标点会影响切分。  

所以英文 tokenization 的难点是：  
词形变化 + 子词切分 + 空格绑定 + 大小写/标点  

## 05.3 代码 tokenization 难点

代码比自然语言更麻烦。  
比如：  
```python
def get_user_id(userName):
    return userName.id
```

代码里有很多东西：  
关键字：def, return  
变量名：get_user_id, userName  
符号：(, ), :, ., _  
缩进：空格  
大小写：userName 和 username 不一样  
结构：函数、类、调用、属性访问  

代码难点 1：符号很多  
代码里符号非常关键：  
!=  
<=  
>=  
->  
=>  
::  
.  
,  
:  
;  
{}  
[]  
()  

一个符号错了，语义就变了。  

比如：  
```python
a = b
```

和：  
```python
a == b
```

完全不一样。  

tokenizer 必须对符号敏感。  

代码难点 2：变量名太多  
自然语言词汇虽然多，但代码变量名几乎无限。  

比如：  
user_id  
userId  
getUserID  
get_user_profile_by_token  
calculateBoundingBoxIoU  
__init__  

这些变量名可能词表里没有完整 token，所以要拆。  

比如：  
get_user_profile_by_token  

可能切成：  
["get", "_user", "_profile", "_by", "_token"]  

或者：  
["get", "_", "user", "_", "profile", "_", "by", "_", "token"]  

如果切得太碎，代码会占很多 token。  

代码难点 3：缩进和空格有语义  
Python 里缩进很重要：  
```python
if x > 0:
    print(x)
```

和：  
```python
if x > 0:
print(x)
```

第二个直接语法错误。  

所以代码 tokenizer 不能随便忽略空格。  

自然语言里多个空格通常影响不大，但代码里空格、换行、缩进可能直接决定结构。  

代码难点 4：长尾特别多  
代码里有大量冷门库名、函数名、路径、哈希、UUID、正则表达式。  
比如：  
torch.nn.functional.cross_entropy  

/var/log/nginx/access.log  

^[a-zA-Z0-9_]+@[a-zA-Z0-9]+\.[a-z]+$  

这些东西对 tokenizer 很不友好，经常会被切得很碎。  

## 05.4 三者对比

中文：最大难点是没有空格、词边界不清楚，比如“我喜欢机器学习”  
英文：最大难点是词形变化、空格绑定、子词，比如 tokenization、running  
代码：最大难点是符号、缩进、变量名、长尾组合，比如 get_user_id()、a == b  

## 05.5 用一个例子对比

同样是表达“我喜欢 AI”。  

中文：  
我喜欢人工智能  

可能切成：  
["我", "喜欢", "人工智能"]  

或者：  
["我", "喜", "欢", "人工", "智能"]  

英文：  
I love artificial intelligence  

可能切成：  
["I", " love", " artificial", " intelligence"]  

代码：  
```python
def love_ai(user):
    return user.likes_ai
```

可能切成：  
["def", " love", "_ai", "(", "user", "):", "\n", "    ", "return", " user", ".", "likes", "_ai"]  

代码里面 token 数往往很多，因为符号、缩进、变量名都要算。  
## 05.6 最后总结

中文 tokenization 难在“怎么分词”；英文难在“怎么处理词形变化和空格”；代码难在“怎么保留符号、缩进和变量名结构”。  
你可以这样记：  
中文：边界难  
英文：形态难  
代码：结构难  
而 tokenizer 的目标是：  
切得不要太碎  
词表不要太大  
还能保留足够语义和结构  

所以 tokenization 不是简单“按字切”或“按词切”，而是在 压缩效率 和 语义保留 之间做平衡。
