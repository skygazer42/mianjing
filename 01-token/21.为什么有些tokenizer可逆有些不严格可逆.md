# 21. 为什么有些 tokenizer 是可逆的，而有些不是严格可逆的？

因为 tokenizer 在编码过程中，有些步骤会**丢失原始文本信息**。一旦多个不同输入被映射为同一 token 序列，解码器就无法判断原文是哪一个。

需要区分两种“可逆”：

1. `encode(decode(ids)) == ids`：token 序列层面的可逆
2. `decode(encode(text)) == text`：原始文本层面的严格可逆

通常讨论的是第二种。

### 导致不严格可逆的原因

#### 1. Normalization 丢失信息

例如 tokenizer 会转小写：

```text
"Hello" → "hello"
"HELLO" → "hello"
```

两个输入编码结果相同，解码时只能得到：

```text
"hello"
```

其他有损规范化还包括：

```text
"café" → "cafe"           去除重音
"①" → "1"                NFKC 规范化
"Ａ" → "A"               全角转半角
多个空格 → 一个空格
```

只要 normalization 是多对一映射，严格可逆就不可能。

#### 2. 空白信息被丢弃

传统的按空格预分词可能把：

```text
"a b"
"a  b"
"a\tb"
```

都切成：

```text
["a", "b"]
```

如果 token 序列没有保存空格的类型和数量，解码器只能按固定规则重新插入空格。

Byte-level BPE 或 SentencePiece 会把空白编码为类似 `Ġ`、`▁` 的标记，因此能保留更多空白信息；但如果之前执行了空白规范化，仍然无法恢复原文。

#### 3. 未知字符被映射为同一个 `<unk>`

假设词表不认识多个字符：

```text
"甲" → <unk>
"乙" → <unk>
```

解码时只能得到 `<unk>`，无法判断原始字符。

基于字节的 tokenizer 通常能覆盖任意 UTF-8 输入，因此可以避免这种信息损失。

#### 4. 解码器执行清理规则

某些 tokenizer 解码后会进行清理，例如：

```text
"hello , world !" → "hello, world!"
```

这提高了可读性，却改变了原始空格。常见配置如 `clean_up_tokenization_spaces` 就可能造成这种差异。

#### 5. 特殊 token 被忽略或无法对应原文

编码时可能自动加入：

```text
[CLS] text [SEP]
```

解码时又通过 `skip_special_tokens=True` 删除它们。因此编码后的完整 token 序列与解码文本并非一一对应。

### 为什么 byte-level tokenizer 更容易可逆

Byte-level tokenizer 先把文本表示为 UTF-8 字节，每个字节都有对应表示：

```text
原文 → UTF-8 字节 → token 序列 → 字节 → 原文
```

只要满足以下条件，就能做到严格文本往返：

* 编码前没有有损 normalization
* 所有字节都能被表示，不产生 `<unk>`
* 空白和控制字符没有被丢弃
* 解码时不执行文本清理
* UTF-8 字节序列被完整保留

所以关键不在于使用 BPE、WordPiece 还是 Unigram，而在于整个处理流程是否存在**多对一、有损变换**：

```text
无损的一一映射 → 可以严格可逆
多对一或删除信息 → 只能近似恢复
```
