# 27. 怎么判断一个 tokenizer 设计得好不好？应该看哪些指标？

## 结论先行

没有脱离模型、语料和任务的“最好 tokenizer”。评估至少要同时看四类指标：**覆盖与可逆性、压缩效率与公平性、词表质量与稳定性、端到端模型效果和系统成本**。只看平均 token 数会鼓励过大的词表，也会掩盖低资源语言、异常文本和下游任务退化。

## 1. 覆盖与可逆性

首先确认真实输入能否稳定编码：

- `<unk>` / OOV 比例，最好按语言和数据类型分桶；
- 生僻字、emoji、URL、代码、控制字符和错误编码的处理；
- `decode(encode(text)) == text` 的字节级往返通过率；
- normalization 是否有意地丢失大小写、重音或空白；
- special token 是否可能与普通文本冲突。

如果任务是代码生成、精确引用或结构化输出，可逆性通常是硬要求；若任务是大小写无关分类，某些规范化损失可能可以接受。指标必须服从应用语义。

## 2. 压缩效率

常见统计包括：

$$
\text{tokens per byte} = \frac{\#\text{tokens}}{\#\text{UTF-8 bytes}}
$$

也可观察字符/token、词/token 或每个样本的 token 长度。跨语言比较时，UTF-8 byte 是可复现的底层尺度，但“相同语义翻译的 token 数”更接近用户成本；两者最好一起报告。

不能只看均值，应至少看 P50、P95、P99，并按以下维度拆分：

- 中文、英文、阿拉伯语等语言；
- 自然语言、代码、数学、表格、JSON；
- 正常文本、拼写错误、随机 id、URL 和 emoji；
- 短对话、长文档和真实 chat template。

一个 tokenizer 可能英文平均值很好，却让某种语言或代码的长度翻倍。整体均值会被数据占比掩盖，因此需要报告跨语言效率差距。

## 3. 词表质量

词表不是越大越好。可以检查：

- token 在训练语料中的频次分布，是否存在大量几乎没见过的项；
- embedding 学习样本是否充足，长尾 token 是否成为“僵尸词条”；
- 是否收录大量数据污染、模板串、乱码或隐私片段；
- 常见词素、代码结构和目标领域术语能否合理组合；
- 词表大小变化带来的序列缩短是否抵得过 embedding 与输出层扩容。

设词表大小为 $V$、隐藏维度为 $D$，输入 embedding 参数量约为 $VD$；若输出权重不共享，还可能再付出同量级参数。词表扩大也会增加输出 softmax 的计算与通信。因此“tokens/byte 更低”只是收益的一边。

## 4. 稳定性与确定性

相同配置、相同语料是否能复现相同词表和 merge 顺序？相近输入是否出现过度跳变？normalizer、pre-tokenizer 和 decoder 在不同语言或平台上是否一致？升级 tokenizer 库后 token id 是否变化？

生产系统还要验证：

- encode/decode 吞吐和峰值内存；
- batch 编码能否并行；
- offset mapping 是否正确对齐原文；
- added token 与 special token 的匹配优先级；
- 与训练 checkpoint、chat template、服务端计数的版本一致性。

## 5. 端到端效果与系统成本

最终要在**控制变量**下训练或继续训练模型，比较：

- 验证集 loss/perplexity 和收敛速度；
- 分类、检索、生成、代码等目标任务质量；
- 固定原始文本量下的训练 token 数与训练时间；
- 固定上下文窗口下能放入的有效信息量；
- prefill 延迟、生成吞吐、KV cache 占用和实际费用。

只在同一个已训练模型上替换 tokenizer 再比较是不公平的，因为新 token id 没有匹配的 embedding。严谨实验应重新训练，或采用明确的词表扩展与 embedding 初始化/继续训练方案。

## 一个实际评估流程

1. 从真实流量构建分层、去隐私的代表性语料和压力样本。
2. 固定 normalization 与 special token 需求，训练多个词表大小或算法候选。
3. 输出覆盖、往返、分桶压缩率、长尾词频与速度报告。
4. 淘汰存在硬错误的候选，再做小规模等计算量模型训练。
5. 比较下游质量、吞吐、显存和迁移成本，最后选择 Pareto 更优方案。

## 常见误区

1. **token 越少越好。** 极端情况可以把整段高频文本做成一个 token，但词表会爆炸且泛化很差。
2. **没有 `<unk>` 就足够。** byte 回退能保证覆盖，却可能让某些语言序列非常长。
3. **英文基准能代表多语言产品。** 真实语言和格式分布必须单独评估。
4. **tokenizer 是模型外部可随意替换的组件。** 它与 embedding、输出层和模板是同一个版本契约。

## 面试回答要点

给出一个多目标答案：先看能否无损覆盖，再看分桶压缩率和语言公平性，然后检查词表长尾与编码稳定性，最终用重新训练后的模型质量、吞吐、显存和费用定夺。强调必须在真实语料上看分位数，不能只报平均 token 数。
