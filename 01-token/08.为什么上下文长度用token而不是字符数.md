# 08. 为什么大模型常说“上下文长度是 8k、32k、128k token”，而不是字符数？

## 回答

模型实际接收的是 token id 序列，Transformer 的位置编码、attention、KV cache 和输出预测都以 token 为单位。因此上下文窗口的上限必须写成 token 数，而不是字符数。

同样的字符数在不同语言、不同 tokenizer 下会产生不同数量的 token：英文单词可能被合并为少数 token，中文、emoji、代码或罕见字符串则可能被拆得更细。字符数不能准确反映模型的序列长度和计算成本。

上下文窗口还要同时容纳系统提示词、历史对话、当前输入和待生成输出。例如 8k 窗口已使用 6k 输入 token 时，理论上最多只能再生成约 2k token。

## 面试要点

“128k”表示该模型 tokenizer 切分后的序列上限，不代表 128k 个汉字、单词或字符；实际可用输出长度还会受输入长度和服务端预留策略限制。







因为大模型实际处理的基本单位不是“字符”，而是 **token**。

## 1. 模型看到的是 token ID，不是字符

文本进入模型前，会先经过 tokenizer：

```text
文本 → token 切分 → token ID → embedding → Transformer
```

例如：

```text
我喜欢人工智能
```

可能被切成：

```text
["我", "喜欢", "人工", "智能"]
```

也可能是：

```text
["我", "喜", "欢", "人工智能"]
```

模型真正接收到的是类似：

```text
[1234, 5678, 9012, 3456]
```

因此，上下文长度本质上是：

```text
模型一次最多能处理多少个 token 位置
```

而不是多少个字符。

---

## 2. Transformer 的序列位置按 token 计算

假设模型上下文长度是 128K，通常表示最多能容纳约：

```text
128,000 个 token
```

每个 token 都对应一个序列位置：

```text
位置 1：token A
位置 2：token B
位置 3：token C
...
```

位置编码、注意力计算、KV Cache 等机制，都是围绕 token 位置组织的。

模型没有一个天然的“字符位置序列”。

---

## 3. 计算量和显存消耗取决于 token 数

对于一个包含 `n` 个 token 的序列，模型需要为每个 token 计算隐藏状态、注意力信息以及缓存。

一般来说：

* token 越多，推理时间越长；
* token 越多，KV Cache 占用越大；
* token 越多，注意力计算越重；
* 达到 token 上限后，就无法继续加入更多上下文。

所以真正决定资源消耗的是 token 数，而不是原始字符数。

例如：

```text
aaaaaaaaaa
```

和：

```text
今天天气非常不错
```

字符数可能接近，但经过不同 tokenizer 后，token 数未必相同。

---

## 4. 字符和 token 不是一一对应关系

### 英文示例

```text
unbelievable
```

可能被切成：

```text
["un", "believ", "able"]
```

一个单词有 12 个字母，但可能只有 3 个 token。

常见英文单词也可能整体成为一个 token：

```text
"computer" → 1 token
```

### 中文示例

中文没有天然空格，一个汉字可能对应：

* 1 个 token；
* 多个 token；
* 和相邻汉字合并成一个 token。

例如：

```text
人工智能
```

可能被编码为：

```text
["人工", "智能"]
```

也可能是：

```text
["人", "工", "智能"]
```

取决于具体模型的 tokenizer。

### Emoji 示例

```text
👨‍👩‍👧‍👦
```

视觉上像一个字符，但底层可能由多个 Unicode 码点组成，并被切成多个 token。

因此，“字符数”无法准确表示模型实际需要处理多少个序列单元。

---

## 5. 不同语言的字符/token 比例不同

同样的字符数，在不同语言中可能产生完全不同的 token 数。

大致上：

* 英文常见词可能一个 token 包含多个字母；
* 中文经常一个汉字接近一个 token，但并不固定；
* 罕见汉字可能被拆成多个 token；
* 代码、JSON、数字和特殊符号可能产生较多 token；
* 连续空格、缩进和标点也可能占 token。

例如下面两段字符数相似：

```text
Hello, how are you today?
你好，你今天过得怎么样？
```

它们的 token 数不一定相同。

因此不能说：

```text
128K token = 固定多少字符
```

只能根据语言和文本类型估算。

---

## 6. 上下文窗口限制的是整个 token 序列

上下文长度通常不只计算用户输入，还可能包含：

```text
系统提示词
开发者指令
历史对话
当前用户消息
工具定义
工具调用结果
图片对应的视觉 token
模型即将生成的输出
```

可以近似理解为：

```text
输入 token 数 + 输出 token 数 ≤ 上下文窗口
```

例如上下文窗口为 128K token：

```text
历史消息：100K
系统和工具信息：8K
用户当前输入：5K
留给输出：约 15K
```

实际限制还取决于具体模型和 API 对最大输出 token 的单独约束。

---

## 7. 为什么不直接按字节数计算

字节数适合衡量存储容量，但不适合衡量模型的序列长度。

例如 UTF-8 中：

* 英文字母通常占 1 字节；
* 中文汉字通常占 3 字节；
* Emoji 可能占更多字节。

但模型不是对每个字节都独立执行一次 Transformer 计算。文本会先被 tokenizer 合并成 token。

因此：

```text
字节数 ≠ 模型序列长度
字符数 ≠ 模型序列长度
token 数 = 模型实际输入序列长度
```

---

## 8. 为什么模型要使用 token，而不是直接使用字符

使用 token 是一种计算效率和泛化能力之间的折中。

### 按字符切分

优点：

```text
词表较小
任意文本都容易表示
```

缺点：

```text
序列会非常长
计算成本较高
一个词需要很多步才能表达
```

例如：

```text
internationalization
```

按字符需要约 20 个位置。

### 按完整单词切分

优点：

```text
序列较短
一个词可以直接表示
```

缺点：

```text
词表会极其庞大
无法覆盖新词、错别字和罕见词
```

### 按子词 token 切分

例如：

```text
internationalization
→ international + ization
```

它兼顾了：

* 较短的序列；
* 可控的词表大小；
* 对生词的处理能力；
* 多语言和代码支持。

因此现代大模型通常采用 BPE、SentencePiece、Unigram 或类似的子词 tokenizer。

---

## 核心结论

上下文长度使用 token，而不是字符数，是因为：

1. **模型的直接输入是 token ID。**
2. **注意力、位置编码和缓存都按 token 位置工作。**
3. **计算量和显存消耗主要由 token 数决定。**
4. **字符数无法稳定映射到模型的实际序列长度。**
5. **不同语言、代码和符号的字符/token 比例差异很大。**

可以把它类比为：字符是原材料，token 是模型真正装进“工作台”的零件；上下文窗口限制的是工作台最多能放多少个零件。
