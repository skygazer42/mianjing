# 02. 为什么同一句话在不同模型里 token 数可能不同？

## 结论先行

因为 token 不是文本天然具有的单位，而是**某个具体 tokenizer 根据自己的规范化规则、切分算法和词表**算出来的。同一句原文只要换了 tokenizer，就可能得到不同边界、不同 token id 和不同 token 数；即使两个模型都叫“BPE tokenizer”，训练语料与 merge rules 不同，结果也未必相同。

## 决定 token 数的五个层次

### 1. 文本规范化规则不同

有的 tokenizer 保留大小写和重音，有的会转小写、做 NFKC 规范化或去除重音。例如：

```text
"Café" -> "café" -> "cafe"
```

每一次变换都可能让后续词表匹配发生变化。空格是否合并、全角字符是否转半角、换行是否保留也会影响最终数量。

### 2. 基础编码单位不同

不同系统可能从 Unicode 字符、UTF-8 字节或预分词后的“词”开始。byte-level tokenizer 能覆盖任意字节序列，通常不会因生僻字符直接产生 `<unk>`，但未被词表合并的非 ASCII 字符可能退化成多个字节片段。

### 3. 子词算法不同

- BPE 反复应用训练阶段学到的合并规则；
- WordPiece 常用词内最长匹配，失败时可能得到 `[UNK]`；
- Unigram 为候选切分计算概率，选择总损失更小的路径；
- SentencePiece 是直接从原始文本训练 tokenizer 的工具框架，可搭配 BPE 或 Unigram，并不是与前三者同一层级的单一算法。

算法目标和解码约束不同，同一个片段自然可能被拆成不同数量。

### 4. 训练语料与词表不同

词表本质上是在有限容量内给高频片段分配“快捷编码”。如果训练语料英文和代码很多，`function`、`https://` 或常见缩进模式可能成为完整 token；若中文法律语料很多，“中华人民共和国”等领域片段更可能被整体收录。

即使词表大小相同，语料分布不同也会产生完全不同的 token 集合。词表更大一般有机会缩短序列，但不是单调保证：词表质量、语言覆盖和算法同样重要。

### 5. 模板与特殊 token 不同

真实聊天接口统计的往往不只是用户肉眼看到的句子。系统可能自动加入角色、消息边界、工具调用和起止标记：

```text
<bos><system>...</system><user>你好</user><assistant>
```

两个模型即使正文切分相近，只要 chat template 不同，请求的总 token 数仍可能相差明显。比较时必须说明统计的是“裸文本编码”还是“套模板后的完整请求”。

## 一个简化例子

假设有两个词表：

```text
词表 A：the, tokenizer, is, fast
词表 B：the, token, iz, er, is, fast
```

对 `the tokenizer is fast`：

```text
A -> [the] [tokenizer] [is] [fast]          # 4 个
B -> [the] [token] [iz] [er] [is] [fast]   # 6 个
```

两种切分都能还原文本，也都可能是合法设计；A 对这个句子更省 token，但它为完整的 `tokenizer` 占用了一个词表槽位。是否值得取决于该片段在目标语料中的频率。

## 对工程有什么影响

token 数差异会传导到：

- **上下文容量**：相同文档在低压缩率 tokenizer 下更早达到长度上限；
- **训练吞吐**：固定 token budget 下，每批能容纳的样本数不同；
- **推理延迟和价格**：prefill、decode、KV cache 和按 token 计费都受影响；
- **截断位置**：切分变细后，重要的文档尾部可能被截掉；
- **多语言公平性**：覆盖较弱的语言表达同样语义可能消耗更多 token。

因此不能用“一个英文词约等于多少 token”这样的经验值做精确容量规划。生产系统应使用**目标模型配套的 tokenizer 与真实 chat template**对真实流量做分位数统计，例如观察 P50、P95、P99 输入和输出长度。

## 常见误区

1. **模型架构决定 tokenizer。** 错。相同 Transformer 架构可以配不同 tokenizer，但训练好的 embedding 与词表 id 强绑定，不能随意替换。
2. **都使用 BPE，结果就一样。** 错。训练语料、初始字母表、词表大小、merge rules 和 normalization 都会改变结果。
3. **token id 可以跨模型比较。** 错。同一个整数在不同词表中通常代表不同片段。
4. **只比较正文就能推断 API 账单。** 不完整。还要计入系统提示、对话历史、工具 schema、特殊 token 与输出。

## 面试回答要点

可以按“规则—词表—模板—影响”四步回答：不同模型的 tokenizer 在 normalization、基础单位和 BPE/WordPiece/Unigram 算法上可能不同；不同训练语料又会学出不同词表；实际对话还会加入不同模板与特殊 token。因此同一句正文会产生不同 token 数，并进一步影响上下文、成本与延迟，工程上必须用目标 tokenizer 实测。
