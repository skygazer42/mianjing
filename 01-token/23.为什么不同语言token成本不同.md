# 23. 为什么英文、中文、阿拉伯语在同一个模型里的 token 成本可能差很多？

因为模型计费通常按 **token 数量**，而 token 并不等于“一个字”“一个单词”或“一个字符”。不同语言经过同一个分词器后，切分粒度可能差很多。

## 核心原因：分词器学到的“常用片段”不同

现代大模型通常使用 BPE、Unigram 或类似的子词分词方法。分词器会从训练语料中学习一套固定词表，其中可能包含：

* 完整单词，如 `computer`
* 常见词根或词缀，如 `develop`、`ment`
* 中文单字或多字词，如 `中`、`中国`
* 阿拉伯语词干、前缀或字母组合
* 空格、标点和代码片段

一个片段是否能成为单独的 token，取决于它在构建词表时是否足够常见，而不是取决于它在语言学上是不是一个词。

---

## 1. 英语通常能被压缩成较大的 token

英语在许多模型的训练数据中占比较高，因此词表里往往收录了大量常见英文单词和词根。

例如，概念上：

```text
The company announced a new product.
```

可能被切成：

```text
The | company | announced | a | new | product | .
```

有些较长单词也可能只占一个 token，或者被分成两三个常见词根。

因此，英语经常出现：

* 一个 token 对应一个短单词
* 一个 token 对应多个字符
* 空格和后面的单词被合并成一个 token

这使英文的字符数/token 比通常比较高。

---

## 2. 中文没有空格，但不代表一定更省 token

中文文本的信息密度很高，一个汉字通常比一个英文字母承载更多语义。但分词器可能按单字、双字词或更长词组切分。

例如：

```text
人工智能正在改变世界
```

可能近似切成：

```text
人工智能 | 正在 | 改变 | 世界
```

也可能切得更细：

```text
人 | 工 | 智 | 能 | 正 | 在 | 改 | 变 | 世 | 界
```

具体结果取决于模型的 tokenizer。

较老或偏英文的 tokenizer，中文经常接近：

* 一个汉字一个 token
* 某些汉字甚至需要多个底层片段

较新的多语言 tokenizer 往往会收录常见中文词组，因此中文 token 效率可能明显改善。

所以中文和英语的成本比较不能只看字符数。常见情况是：

* 同样字符数：中文可能使用更多 token
* 同样语义内容：中文可能更短，最终 token 数未必更多
* 同样篇幅的翻译：结果取决于文本类型和 tokenizer

---

## 3. 阿拉伯语受形态变化和词表覆盖影响较大

阿拉伯语有丰富的词形变化。冠词、介词、连词、代词等可以直接附着在词上。

例如，一个阿拉伯语书写单位中可能同时包含：

```text
连词 + 介词 + 冠词 + 词干 + 代词后缀
```

从语言学角度看，它可能包含多个语法成分；但文本中没有用空格将它们全部分开。

如果 tokenizer 没有收录整个词形，就可能切成许多小片段：

```text
前缀 | 前缀 | 词干片段 | 后缀
```

此外，阿拉伯语 token 数还可能受到这些因素影响：

* 训练语料中的阿拉伯语比例较低
* 方言、现代标准阿拉伯语和古典阿拉伯语差异
* 附加符号和元音标记
* 不同 Unicode 字符形式
* 阿拉伯字母与拉丁字母、数字混排
* 同一词根产生大量不同词形

因此，相同语义的阿拉伯语文本有时会比英语产生更多 token。

---

## 4. UTF-8 字节长度也会影响分词效率

很多 tokenizer 在底层采用字节级机制。不同字符在 UTF-8 中占用的字节数不同：

| 字符类型     | 常见 UTF-8 字节数 |
| -------- | -----------: |
| 基本英文字母   |         1 字节 |
| 阿拉伯字符    |      通常 2 字节 |
| 常见汉字     |      通常 3 字节 |
| 部分 emoji |    4 字节或更多组合 |

这不意味着“一个汉字必然等于三个 token”。如果某个汉字或词组已经被收录为词表项，它仍然可以是一个 token。

但对于词表里没有充分覆盖的字符序列，tokenizer 可能退回到较小的字节片段。此时，非 ASCII 文字的 token 数可能迅速增加。

emoji、罕见汉字、组合字符和特殊符号尤其容易出现这种情况。

---

## 5. 词表容量是有限的，语言之间存在资源分配

假设 tokenizer 的词表只有十万多个条目，它必须同时覆盖：

* 英语
* 中文
* 阿拉伯语
* 其他自然语言
* 编程语言
* 数学符号
* URL
* 标点
* emoji

某种语言获得的高频词表项越多，通常压缩效率越好。

如果构建 tokenizer 的语料以英语为主，那么它可能为以下内容分配大量 token：

```text
ing
tion
development
http
function
return
```

与此同时，某些阿拉伯语词形或中文专业词汇可能只能拆成更小片段。

因此，token 成本差异本质上也是一种有限词表容量下的分配结果。

---

## 6. 格式和 Unicode 规范化也会产生额外 token

肉眼看起来相同的文本，底层字符序列可能不同。

例如：

* 全角标点和半角标点
* 阿拉伯语附加符号
* Unicode 组合字符
* 不同形式的空格
* 不可见字符
* 从 PDF 或网页复制出的特殊字符
* 简体、繁体、异体字
* 阿拉伯数字与阿拉伯—印度数字

这些差异可能让原本常见的字符串无法匹配词表中的完整 token，从而被切得更碎。

---

## 一个简化理解

可以把 tokenizer 想象成一本“短语兑换表”：

```text
"the"        → 1 token
"computer"   → 1 token
"人工智能"   → 1 token
"某个罕见词" → 多个 token
```

这本兑换表对不同语言的覆盖程度不同。覆盖越好，相同内容需要的 token 越少。

## 最重要的结论

语言本身没有固定的 token 成本。成本由以下组合决定：

$$
\text{成本}
=
\text{文本产生的 token 数}
\times
\text{模型的每 token 单价}
$$

而 token 数主要取决于：

1. 使用的是哪个 tokenizer
2. 该语言在 tokenizer 训练语料中的覆盖程度
3. 文本中的词汇是否常见
4. 语言的词形结构
5. Unicode、标点和排版形式
6. 比较的是相同字符数、相同字数，还是相同语义

因此，“中文一定比英文贵”或“阿拉伯语一定最贵”都不是普遍成立的结论。必须把具体文本交给目标模型对应的 tokenizer 实际计算。
