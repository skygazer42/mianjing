# 25. 代码模型的 tokenizer 和通用文本 tokenizer，设计重点有什么不同？

## 结论先行

两者仍然追求覆盖率、适当序列长度和稳定解码，但代码 tokenizer 更重视**严格保留格式、压缩符号与缩进、覆盖标识符和多语言混排，以及避免把语法结构切得过碎**；通用文本 tokenizer 则更关注自然语言词素、多语言公平性、标点与常见词组的压缩。区别来自数据分布和下游损失，而不是必须使用不同算法。

## 代码语料有哪些特殊分布

代码中高频内容并不只是 `if`、`class`、`return`：

```text
    缩进
\n  换行
()[]{} 括号
== != <= -> :: 运算符
snake_case camelCase kebab-case 标识符
路径、URL、版本号、十六进制、Unicode 字符串
```

代码还经常把自然语言、SQL、HTML、正则表达式和配置文件嵌在一起。一个只在英文散文上训练的 tokenizer 可能把 `get_user_by_id`、`</div>` 或四个空格拆得很碎，序列长度随即放大。

## 设计重点对比

| 维度 | 通用自然语言 | 代码场景 |
| --- | --- | --- |
| 主要边界 | 词、子词、标点 | 语法符号、缩进、换行、标识符片段 |
| 可逆要求 | 语义任务有时可接受规范化 | 通常要求字节级精确还原 |
| 大小写 | 可按语种考虑 lowercasing | 大小写常改变标识符，必须保留 |
| 空白 | 多余空格有时可合并 | Python/YAML 中可能决定语义 |
| 高频片段 | 常用词、词根、词缀 | 关键字、运算符、常见 API 与格式模式 |
| 长尾 | 人名、术语、低资源语言 | 用户自定义变量、哈希、路径、随机字符串 |

代码模型常采用 byte-level 基础覆盖，因为它能表示任意文件内容并避免 `[UNK]`；但 byte-level 只是底座，还需要从高质量多语言代码中学习 merge rules，才能获得良好压缩率。

## 标识符应该如何切

对 `getUserProfileById`，可能的目标切分是：

```text
get | User | Profile | By | Id
```

而不是逐字符，也不一定值得把整个标识符作为单个 token。保留常见语义片段有利于泛化到 `getOrderById`；把大量项目私有变量完整收入词表，会浪费词表容量并形成低频 embedding。

是否显式做 camelCase 或 snake_case 预分词要实测。纯 BPE 也可能从数据中学到常见边界；硬编码切分有助于组合，但可能破坏严格可逆或与某些语言规则冲突。

## 为什么缩进与运算符压缩重要

若四个空格占四个 token，一个深层代码块会把大量上下文浪费在格式上。词表可学习常见连续空格、`\n    `、`==`、`->` 等组合，从而减少长度。但词表不能只追求压缩：例如把一整段模板代码合成超长 token，会降低组合性，且对一个字符的修改非常脆弱。

评价时应同时看：

- 各编程语言的 token/byte 与 token/line；
- 标识符、注释、字符串、缩进和生成代码的分桶统计；
- encode/decode 字节级往返；
- 语法错误率、代码补全准确率和长文件可容纳范围；
- 自然语言与代码混合提示的多语言公平性。

## special token 与 Fill-in-the-Middle

代码模型常支持 Fill-in-the-Middle（FIM），因此可能增加 prefix、suffix、middle 等控制 token，让模型根据文件前后文补中间片段。它们不是 tokenizer 算法自然产生的，而是模型训练协议的一部分：必须加入词表、正确放入模板，并在训练中见过相同语义。

随意添加 special token 而不扩展 embedding，或只扩展词表却不训练对应向量，都不会自动获得 FIM 能力。

## 工程取舍

直接为现成通用模型更换代码 tokenizer 通常不可行，因为 token id 与输入/输出 embedding 已绑定。更现实的路径包括继续使用原 tokenizer 做代码微调、只增加少量经过训练的新 token，或在从头/大规模继续预训练时重新设计词表。是否值得重训要比较节省的训练 token 与 embedding 扩容、数据重编码和兼容性成本。

## 面试回答要点

回答时强调代码的三个独特约束：格式可能决定语义，标识符和符号长尾极重，输入经常混合多种语言与结构。理想 tokenizer 要无损覆盖，同时高效编码缩进、换行、运算符和可复用的标识符子片段；最终用压缩率、往返正确性和代码任务质量共同评估。
