# 01. RAG 是什么，主要解决什么问题？

## 结论先行

RAG（Retrieval-Augmented Generation，检索增强生成）是在生成答案前，从外部知识源检索与问题相关的证据，并把证据与问题一起交给生成模型。它主要解决参数知识**难以及时更新、难以覆盖私有数据、来源不可核验**的问题；它能提高回答的可更新性和可追溯性，但不保证自动消除幻觉。

## 最小工作流程

一个最小 RAG 有离线和在线两条链路。

离线索引：

```text
文档 -> 解析/清洗 -> 切块 -> 生成 embedding 或倒排项
     -> 写入向量库/搜索引擎，同时保存原文、来源、版本和权限元数据
```

在线查询：

```text
用户问题 -> 查询理解/改写 -> 召回候选 -> 重排/过滤
        -> 组装带引用的上下文 -> LLM 生成 -> 校验/返回证据
```

用概率形式可以把它理解为对候选文档 $z$ 边缘化：

$$
p(y\mid x)\approx\sum_{z\in \operatorname{TopK}(x)}p_\eta(z\mid x)\,p_\theta(y\mid x,z)
$$

$p_\eta$ 是检索器为问题 $x$ 找证据 $z$ 的能力，$p_\theta$ 是生成器基于问题和证据生成答案 $y$ 的能力。生产系统未必真的计算完整概率和，但这个分解揭示了两个独立故障面：**证据没找对**，或者**证据找对但模型没忠实使用**。

## RAG 主要解决的三类问题

### 1. 知识新鲜度

模型参数中的知识冻结在训练数据与更新时间内。产品价格、内部制度、库存和文档会持续变化；RAG 可以更新索引而不必每次重新训练大模型，并通过版本和时间元数据优先检索最新证据。

### 2. 私有与长尾知识

企业手册、工单、个人文档和专有数据库不适合全部写入公共基础模型参数。RAG 在请求时按用户身份检索授权内容，使同一个生成模型服务不同租户和知识域。

### 3. 引用与审计

如果系统保留文档 id、页码、chunk offset 和版本，答案可以附带可点击来源，人工能够核验。参数记忆通常无法可靠说明某个事实来自哪份文档。

## RAG 没有自动解决什么

检索到文本不等于答案正确：

- 切块可能把问题与答案拆开；
- embedding 可能召回语义相近但事实不相关的内容；
- top-k 可能漏掉关键证据，或塞入大量冲突噪声；
- reranker 和 metadata filter 可能配置错误；
- 文档本身可能过期、互相矛盾或被投毒；
- LLM 可能忽略证据、错误归因，或在证据不足时用参数记忆补写。

因此“加一个向量数据库”不等于建成 RAG。生产系统必须分别评估索引、召回、重排、上下文和生成，并允许在证据不足时明确拒答。

## RAG 与微调的边界

RAG 主要给模型提供**事实和证据**；微调更适合改变**行为、格式、语气、任务技能或稳定决策边界**。如果希望模型掌握公司最新报销规则并引用原文，优先 RAG；如果希望它始终按固定 JSON schema 回答，可能需要提示、约束解码或微调。

两者可以组合：微调模型让它更会提出检索查询、阅读证据和正确引用，RAG 负责提供最新知识。不要把频繁变化的事实硬塞进权重，也不要期望检索自动教会模型一项复杂新技能。

## 与直接塞入长上下文的区别

长上下文可以省去索引和召回，但需要把候选文档全部放进 prompt，成本、延迟和注意力干扰会随长度增加。RAG 用检索先缩小证据集合，更适合大知识库、频繁查询和权限过滤；若候选材料很少且每次都必须整体推理，直接长上下文可能更简单。

## 一个具体例子

用户问“当前差旅报销的酒店上限是多少？”系统应先用用户部门、城市、出差日期等 metadata 过滤，再召回有效版本的制度条款，重排后把条款和文档版本交给模型。最终答案应引用原文，并在不同条款冲突时说明冲突，而不是仅凭向量相似度选一段后给出无条件结论。

这个例子说明检索相关性之外还需要权限、时间有效性和来源优先级。

## 面试回答要点

先给出“检索外部证据再生成”的定义，然后说明它解决知识新鲜度、私有知识和可追溯性。接着画出 ingest—retrieve—rerank—assemble—generate 链路，最后强调 RAG 仍可能因召回、证据质量和生成忠实度失败，需要分阶段评估和证据不足时拒答。
