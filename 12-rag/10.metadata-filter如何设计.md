# 10. metadata filter 如何设计？

## 结论先行

metadata filter 用结构化条件缩小检索空间，既服务相关性，也承载租户、ACL、版本和时间等安全约束。设计原则是：字段在摄取时规范化并可版本化；强安全条件尽量下推到搜索引擎执行；区分硬过滤与软排序；记录实际生效的 filter 和候选数量，避免过滤过严时静默返回错误或跨权内容。

## 字段与语义

典型字段包括 `tenant_id`、文档/用户 ACL、语言、产品、地区、文档类型、有效起止时间、版本、source authority、document_id 与 parent_id。枚举值要有 canonical form，例如“上海/Shanghai/SH”映射到同一代码；时间统一时区并明确区间开闭。多值 ACL 需要引擎支持集合包含/相交，而不是把数组转成一串不可控文本。

## 硬过滤与软约束

租户和权限是硬条件，不满足绝不能进入候选；“更偏好最新”“优先官方来源”通常是排序特征，因为严格只取最新可能漏掉仍有效的历史条款。用户问“2024 年政策”时，query parser 应把时间意图转成 `valid_from <= query_date < valid_to`，而不是只用文档更新时间。解析置信度低时可保留候选并请求澄清，不能凭猜测加过窄 filter。

## pre-filter 与 post-filter

pre-filter 在 ANN/BM25 搜索中只遍历合法集合，安全且不让非法结果占 top-k；但过滤后集合很小或索引算法不支持时，召回/延迟行为可能变化。post-filter 先召回再删除实现简单，却可能 top-100 全是无权文档，最终合法候选为零，并有泄漏面。安全 ACL 不应只依赖 post-filter；必要时用分区索引、bitmap 或 filter-aware ANN。

## 具体例子

查询“我的报销额度”至少带 `(tenant=A) AND (user groups intersects acl) AND (effective_at=出差日期)`，然后语义召回。若业务只知道“华东”，可以把地区作为软 boost 或扩展上海、江苏等集合，而不是错误地精确等于一个不存在的字段值。

## 工程与常见误区

字段变更需要 schema/index version 和回填；缓存 key 必须包含规范化 filter 与权限版本。记录 filter 前后候选数、零结果率与解析来源。不要把 metadata 原样拼入自然语言 prompt 当作过滤，也不要让 LLM 自己决定访问权限。

## 面试回答要点

按 schema 规范化、硬/软条件、下推执行、可观测与版本缓存五点回答，强调 ACL filter 是授权边界而非相关性小技巧。
