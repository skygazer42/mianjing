# 13. parent-child retrieval 和 contextual chunking 有什么用？

## 结论先行

两者都解决“小 chunk 好检索、但缺上下文”的矛盾。parent-child 用较小 child 建索引和命中，用 `parent_id` 返回较大的段落/章节供模型阅读；contextual chunking 在每个 chunk 前补充由文档全局信息生成或抽取的简短语境，使脱离原文后仍知道主体、章节和指代。它们可以组合，但会增加存储、生成和重复上下文成本。

## Parent-child 数据流

摄取时先按章节生成 parent，再在 parent 内切 child：

```text
document -> parent(section) -> child(chunk) -> embedding(child)
```

在线对 child 向量召回和 rerank，选中后按 `parent_id` 拉取 parent，或只扩展前后 sentence window。多个命中 child 属于同一 parent 时合并，避免同一章节重复占 token。parent 必须保留版本、ACL 与 offset；child 不能引用一个权限更宽或已更新的 parent。

## Contextual chunking

原 chunk “该限制自批准之日起生效”缺少“该限制”指什么。可从标题路径、文档摘要和邻段生成前缀：“《供应商管理办法》/风险审批章节；该段说明高风险供应商额度限制”。索引文本可用 `context + chunk`，返回给用户的引用仍绑定原文，并明确合成 context 不是权威原文。优先使用确定性标题/实体抽取，LLM 生成 context 要防止编造。

## 具体例子

产品手册的错误码 `E42` child 适合精确召回，但解决步骤跨整个“电源故障”小节。系统可用 child 命中，再返回父小节；若不同产品都含 E42，context 前缀加入产品型号可降低混淆。直接把所有 child 变成大 chunk 会降低 embedding 主题纯度。

## 工程取舍

parent 太大会把大量无关文本送入 prompt；太小仍丢定义。可让 reranker读取 child+标题，最终按 token budget选择 parent 或邻窗。context 生成增加离线成本，文档更新时需要重算；版本写入索引，避免新 parent 配旧 child。

## 常见误区与面试要点

overlap 只是复制边界文本，不能替代结构化 parent；contextual chunk 不是让 LLM在线自由总结并当证据。面试应强调“检索粒度与阅读粒度分离”、parent 去重及合成上下文的可信边界。
