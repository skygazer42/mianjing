# 18. embedding 模型升级后，索引如何迁移？

## 结论先行

不同 embedding 模型、版本或维度产生不同向量空间，旧文档向量与新 query 向量不能混搜。安全迁移应把模型、预处理、切块和 ANN 参数作为新的 `index_version`，离线回填新索引，增量期间双写，校验完整性与质量后灰度双读/切流，保留可快速回滚的旧索引，最后再回收。

## 版本边界

版本至少包含 model artifact/hash、query/document prefix、tokenization、normalization、向量维度/dtype、distance metric、chunker 和索引参数。即使模型名称相同，只要 pooling 或 normalize 逻辑改变，空间也可能不兼容。缓存 key 和 prefix/result cache 同样要带 embedding/index version。

## 迁移步骤

```text
冻结迁移范围与基线
 -> 建新索引/新 vector field
 -> 全量 backfill（幂等、可断点）
 -> 新增/修改/删除事件同时写旧、新版本
 -> 对账文档数、chunk hash、ACL、删除墓碑
 -> shadow query 双读并比较 recall/latency
 -> 小流量 canary，逐级切换
 -> 观察期内保留旧版一键回滚
 -> 停旧写、按保留策略回收
```

回填期间某文档发生更新时，要用 source version/事件序号防止旧 backfill 覆盖新内容。删除必须双写 tombstone，不能让新索引复活已撤销数据。

## 评估与具体例子

在固定 gold queries 上比较 Recall@k、MRR/nDCG、rerank 后证据 rank、端到端答案/引用，以及分桶回归；系统侧比较编码 P95、索引内存、build/search 延迟。shadow traffic 只比较结果不返回用户，可以发现真实长尾；canary 要按 tenant/请求稳定分桶避免同会话版本跳动。

## 工程取舍

全量双索引会短期占两倍向量空间，可分 shard 回填，但不能把新旧向量混进同一 ANN 图。若 chunker 同时升级，chunk id 与引用 offset 也变化，最好拆开实验或明确这是联合迁移，便于归因。

## 常见误区与面试要点

“只重算 query embedding”完全错误；“新模型榜单更高就直接切”缺少领域回归。回答应突出双写、对账、shadow/canary、回滚与删除一致性。
