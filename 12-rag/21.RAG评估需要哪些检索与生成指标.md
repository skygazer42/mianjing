# 21. RAG 评估需要哪些检索、生成与端到端指标？

## 结论先行

RAG 必须分层评估：检索指标回答“正确证据是否进入候选及排在何处”，上下文指标回答“最终 prompt 是否包含充分、无冲突的证据”，生成指标回答“答案是否正确且忠实引用”，系统指标回答“在目标延迟、成本和可靠性下能否运行”。只看最终回答分数无法定位修复点，只看 Recall@k 也不能保证模型用了证据。

## 检索与重排指标

对有 gold evidence 的 query，常用：

$$
\operatorname{Recall@k}=\frac{|TopK\cap R|}{|R|},\qquad
\operatorname{MRR}=\frac1{|Q|}\sum_q\frac1{rank_q}
$$

其中 $rank_q$ 是第一个相关结果的名次；没有相关结果被召回时，该 query 的 reciprocal rank 记为 0。多相关文档可用 nDCG@k 衡量位置与分级相关性；Precision@k、HitRate@k、zero-result rate、每路召回贡献和 filter 后候选数也重要。重排要比较 before/after 的 gold rank、nDCG 增益及额外 P95。对于多跳问题，应测所有必需证据是否齐全，而非命中任意一篇就算成功。没有 gold relevant evidence 的无答案 query 不应被硬记为 Recall=1，而应单独评价误召回与拒答。

## 上下文与生成指标

上下文层看 evidence coverage、重复率、冲突率、进入 prompt 的 gold 比例和 token efficiency。生成层区分 answer correctness/relevance、faithfulness（claim 是否被上下文支持）、citation precision/recall、拒答 precision/recall、格式与安全合规。faithful 但引用错误知识库的答案仍可能不正确，因此 source quality 要单独审计。

## 端到端与系统指标

端到端按任务测 exact match、F1、业务成功率、人工 preference 或关键字段正确率，并保留 `LLM-only`、long-context、retrieval-only 等基线。系统侧记录 ingest freshness、索引覆盖、P50/P95/P99（rewrite/retrieve/rerank/generate 分段）、TTFT、错误/超时率、输入输出 token、搜索/模型成本、缓存命中和峰值并发。

## 分桶与消融

按单事实、多证据、多跳、无答案、时间版本、权限、表格、语言、长尾实体分桶；平均分可能掩盖高风险类别。依次关闭 rewrite、dense、BM25、rerank、parent expansion，做 paired significance/置信区间，确认组件真实贡献。

## 常见误区与面试要点

LLM judge 单分不是完整体系，用户点赞也受展示偏差。面试应画出 retrieval→context→generation→system 四层，每层给指标和对应故障。
