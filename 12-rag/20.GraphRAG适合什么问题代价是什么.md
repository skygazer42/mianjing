# 20. GraphRAG 适合什么问题，代价是什么？

## 结论先行

GraphRAG 适合答案依赖跨文档实体关系、社区/主题结构或全局总结，而单次向量 top-k 难覆盖完整证据的任务。它通常先从语料抽取实体、关系与来源，构建图和社区摘要，查询时做实体定位、邻域/路径检索或全局社区汇总。代价是昂贵且易错的抽取、实体消歧、图更新和复杂评估；简单 FAQ 不应为此增加整套图系统。

## 典型链路

```text
文档/段落
 -> 实体、关系、claim 抽取
 -> entity resolution / 去重
 -> 边与原文证据绑定
 -> 图构建、社区检测、分层摘要
 -> query 实体链接与路由
 -> local neighborhood / path / global community 检索
 -> 原文证据回填、生成与引用
```

Local search 回答“某实体与谁、通过什么关系连接”；global search 汇总多个社区报告回答“整个语料有哪些主要风险主题”。社区摘要是派生内容，最终高风险 claim 仍应回到原文 span 核验。

## 具体例子

分析数千份公司公告中的供应链风险：向量检索可能只返回与查询最相似的几份，漏掉通过共同供应商连接的间接风险。图把公司、供应商、地区、事件作为节点，关系边带公告来源；查询可先找目标公司的二跳邻域，再召回相关原文。若只是查单份手册的退货期限，普通 hybrid RAG 更简单可靠。

## 主要成本

LLM 抽取会漏关系、混淆同名实体并产生伪边；entity resolution 需要规则、embedding 与人工校正；社区划分和摘要随增量数据可能漂移，局部更新不总能保持全局一致。图存储、遍历与文本索引要维护双重版本，ACL 还必须沿节点、边和源文档传播，不能因为聚合摘要而泄权。

## 评估与误区

除了最终答案，还要测实体链接准确率、边 precision/recall、路径证据完整性、社区摘要忠实度、更新延迟和查询成本。GraphRAG 不是“用了图数据库”这个标签，也不必等于某个框架 API；关键是图结构是否真正对应问题需求。

## 面试回答要点

说明 local/global 两类问题、离线图构建与原文回填，再主动指出抽取误差、消歧、更新、ACL 和成本。

2. 增量数据到来时社区摘要怎样更新？
3. GraphRAG 与多跳文本检索如何做消融比较？
