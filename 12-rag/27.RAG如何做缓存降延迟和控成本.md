# 27. RAG 如何做缓存、降低延迟并控制成本？

## 结论先行

RAG 可在 query embedding、检索候选、rerank、文档/解析、组装上下文和最终答案多层缓存，但越靠后越依赖用户、ACL、对话和知识版本，复用风险越高。优化应先做阶段 profile，再用并行召回、批处理、级联模型和 token budget 降本；缓存键必须包含所有影响结果的版本与权限，不能为命中率牺牲新鲜度和隔离。

## 分层缓存

- **embedding cache**：key 为规范化 query + embedding model/prefix/version；其数学结果不依赖 ACL，但 query 本身可能敏感，跨租户复用只能发生在明确允许的同一安全域，并遵守加密、保留期和侧信道策略。
- **retrieval cache**：还需 tenant/ACL digest、filters、index version、top-k 与 retriever 配置。
- **rerank cache**：加入候选 id+version、reranker version。
- **context/prefix cache**：加入模板、模型/adapter、证据顺序与完整 token 序列。
- **answer cache**：最严格，加入对话状态、采样、引用/知识版本，且高时效/个性化问题往往不应缓存。

TTL 不能替代事件失效；文档、ACL 或索引更新应通过 dependency key/invalidation 删除相关项。防 cache stampede 可 singleflight、随机 TTL 和 stale-while-revalidate，但安全撤权绝不能返回 stale。

## 延迟与成本模型

总延迟近似 `rewrite + max(parallel retrievers) + fusion + rerank + generation` 加排队。BM25/dense 并行；简单 query 可跳过 rewrite/LLM rerank，难 query 才升级；embedding/rerank 批处理；先大候选、小上下文；用 parent expansion替代盲目大 chunk。生成成本约与输入/输出 token 和模型价格相关，应记录每阶段 token 与每个成功答案成本。

## 具体例子

高频公共产品手册问题可缓存 query embedding 和授权后的 prefix blocks；但“我的订单状态”结果实时且用户专属，只缓存 schema/embedding，不缓存检索或答案。若 ACL group 改变，旧 retrieval cache 即使 TTL 未到也必须失效。

## 评估与误区

同时看 P50/P95、cache hit tokens/requests、stale response、质量、成本和尾部。语义 answer cache 把“相似”用户问题视为同一可能改变金额/时间条件，风险高于精确 key；应有限域、阈值校准并重新授权/验证。

## 面试回答要点

按层说明 key、版本和安全性，再给并行/级联/token budget，强调缓存命中不是唯一目标。
