# 08. reranker 为什么有效，应该放在哪里？

## 结论先行

初级 retriever 为了在百万级文档上低延迟搜索，通常用双塔独立编码 query 与 chunk，交互能力受限；reranker 在几十到几百个候选上联合读取 query—document，可做细粒度 token 交互、识别否定、数字、条件和真正答案相关性，所以常显著改善前几名精度。它应放在高召回候选融合/过滤之后、上下文组装之前。

## 模型机制

双塔分数是 $s(q,d)=f(q)^Tg(d)$，文档向量可预计算；cross-encoder 把 `[query; document]` 一起输入模型，输出相关性 $r(q,d)$，每对都需一次前向，不能直接对全库运行。也有 late-interaction、轻量分类器或 LLM listwise rerank，处在速度与交互能力之间。

## 在线数据流

```text
query/ACL filter
 -> BM25 + dense 各取候选
 -> 融合、去重（如 100 条）
 -> reranker 打分（保留 10 条）
 -> parent/邻段扩展与 token budget 组装
 -> generation
```

ACL 最好在召回前或检索内下推，rerank 不能成为权限补救。parent expansion 通常在 rerank 后进行，因为用小 child 判断相关性更精确；但 reranker 输入可附标题、表头和必要上下文，避免片段语义残缺。

## 具体例子

查询“试用期员工是否有年假”，dense 候选可能把“正式员工年假”和“试用期病假”都排前。cross-encoder 能联合识别“试用期+年假”两个条件，将真正条款提到首位。对数字/日期问题，还应把文档版本和 metadata 纳入排序特征，单纯语义 reranker 可能偏爱过期但措辞相同的段落。

## 工程取舍

候选数越大 recall 越高但 rerank 成本近似线性增长；可批处理、截断、两阶段级联或对简单查询跳过。截断文档可能丢答案，应以 chunk 为单位并保留结构。离线看 nDCG/MRR、gold evidence rank 提升，线上同时看 P95、输入 token 和端到端正确率。缓存 rerank 结果时 key 必须包含 query normalization、候选版本、ACL 和模型版本。

## 常见误区与面试要点

reranker 不能找回候选池外的证据；LLM rerank 也不必然更准且可能受文档提示注入。面试先解释双塔效率与交叉编码精度，再给出链路位置、候选规模和评估。
