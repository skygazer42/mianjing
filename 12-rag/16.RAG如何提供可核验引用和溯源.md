# 16. RAG 如何提供可核验引用和溯源？

## 结论先行

可核验引用需要从摄取阶段保存不可变来源与文本 offset，到在线阶段为进入 prompt 的证据分配受控 citation id，再在生成后验证“引用存在、引用片段确实支持相邻 claim”。让模型自由生成 URL 或页码不叫溯源；引用正确性至少包含 citation validity、precision、coverage 与版本一致性。

## 数据模型

每个 chunk 应保存 `document_id`、source URI、content/version hash、page/section、start/end offset、采集时间、ACL 和 parent 关系。解析 PDF 时保留页码与阅读顺序；OCR 文档最好保存 bounding box 以便高亮。文档更新后创建新版本，而不是覆盖原 span 后仍复用旧引用。

## 在线数据流

上下文组装为每段生成短 id，如 `[S1]`，服务端维护 `S1 -> immutable source record` 映射。提示模型在每个事实 claim 后选择已有 id，不能生成新 id。输出后解析 citation，检查 id 是否在本次授权上下文；再做 claim segmentation，用 NLI/LLM judge/规则判断引用片段是否蕴含 claim，并统计无引用的重要陈述。

## 指标

引用精度：被引用证据中真正支持 claim 的比例；引用召回/coverage：需要证据的 claims 中获得充分支持的比例；source correctness：URI、页码和版本是否指向实际文本；answer faithfulness：答案是否超出证据。一个答案可能 citation id 全合法，却引用了“相关但不支持结论”的段落，因此只测 URL 可点击不够。

## 具体例子

答案“酒店上限为 800 元，适用于所有城市 [S2]”，而 S2 只写“上海一线城市为 800 元”，数字被支持但范围被扩大。claim-level 检查应判部分不支持，并要求改成限定上海或补充其他证据。若两个有效版本冲突，应同时引用并说明日期，不应静默选一个。

## 工程与安全

前端跳转前再次做权限检查，不能因引用 URL 泄漏用户无权文档；日志可存 id/hash，敏感原文按策略脱敏。文档删除后引用页面应明确“已撤回”，审计系统可按保留政策访问历史快照。

## 面试回答要点

说清 ingest offset—prompt id—claim citation—post validation—UI auth 全链路，并区分引用合法与引用支持。
