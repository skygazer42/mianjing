# 23. 如何区分召回失败、重排失败和生成失败？

## 结论先行

归因需要一次请求的全链路 trace 与 gold/人工确认的证据。最简单的判定树是：gold 是否在索引且可被授权检索；是否出现在初召候选；是否在 rerank/组装后仍进入 prompt；若已进入，最终 claim 是否忠实使用。依次对应摄取/过滤、召回、重排/组装和生成失败。没有中间产物，只看答案无法可靠归因。

## 判定流程

1. **Corpus/ingest gate**：按 document version、ACL、as-of time 检查 gold 是否存在、解析文本是否完整。不存在是数据/索引失败。
2. **Recall gate**：在较大深度（如各路 top-100/1000）查看 gold。完全没有，检查 query rewrite、BM25/dense、ANN、filter；有但很靠后属于召回排序弱。
3. **Rerank gate**：gold 在候选却被 reranker 降出预算，是重排失败；若 rerank 后仍高但 parent expansion/去重/token budget 删除，则是组装失败。
4. **Generation gate**：gold span 已清晰进入 prompt，模型仍给错、忽略条件或引用不支持，是生成/提示/模型能力问题。

## Counterfactual 实验

把 gold evidence 强制注入原 prompt：答案恢复说明上游检索/组装主因，仍失败说明生成或任务本身困难。把 generator 固定，替换候选/重排做 replay；或固定 gold context 比较不同模型。此类 oracle experiment 能估计“perfect retrieval 上限”，比盲调组件更快。

## 具体例子

查询现行政策，BM25 top-100 有正确 2026 条款，dense 无；融合后正确条款在 12，reranker 把措辞相近的 2024 条款排 1，context 只取 5 条，因此是 rerank/版本特征失败，不应先换 generator。如果正确条款已在 `[S1]`，模型却把“上限”说成“固定补贴”，则是生成语义失真。

## 可观测字段

保存原/改写 query、filters、index/model version、各路候选 rank/score、fusion/rerank 顺序、删除 reason、最终 prompt ids、输出 claims/citations 与阶段耗时。敏感原文可用受控 trace id/hash并设置保留期。

## 常见误区与面试要点

最终答案正确也可能检索错误、靠参数记忆碰巧答对；最终错误也可能是知识库本身错误。面试给判定树和 gold injection counterfactual 即可体现工程归因。
