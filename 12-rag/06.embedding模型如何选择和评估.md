# 06. embedding 模型如何选择和评估？

## 结论先行

embedding 选型不能只看公开榜单，应先满足语言、领域、query/document 输入格式、最大长度、向量维度、许可证与部署约束，再在自己的查询—证据集上评估召回。最终选择看“端到端质量提升是否值得编码延迟、索引空间和迁移成本”，而不是单独追求更大模型或更高维度。

## 相似度与训练目标

常见双塔输出 query 向量 $q$ 与文档向量 $d$。若向量做 L2 normalization，cosine 与 dot product 排序等价：

$$
\cos(q,d)=\frac{q^Td}{\|q\|\|d\|},\qquad \hat q^T\hat d=\cos(q,d)
$$

若模型未要求归一化，直接 normalize 可能改变它训练时利用向量范数的语义；索引的 metric 必须与模型卡/训练目标一致。许多检索模型要求为 query、passage 添加不同 instruction/prefix，漏掉会显著掉点。文档长度超过编码上限时必须切块，不能把被截断的向量当完整文档表示。

## 离线评估

准备真实 query、相关 chunk/doc id 及多相关标注，测 Recall@k、MRR、nDCG 与按意图分桶结果。hard negatives 应包含同主题但答案错误、旧版本、相邻产品等高相似干扰；只用随机负例会高估质量。还需评估中文/英文、缩写、数字、实体、长 query、OCR 噪声与领域术语。若系统有 hybrid/rerank，应分别测 dense-only 和端到端增量，确认 embedding 的提升没有被后级抵消。

## 在线与系统评估

记录 query embedding P50/P95、批处理吞吐、向量字节、ANN build/search 延迟、索引驻留内存和每百万文档成本。更高维向量通常增加存储和距离计算；可比较降维、量化后 Recall 损失。线上用受控流量看证据点击/采纳、答案正确率与失败 query，而不是仅看 cosine 平均值。

## 具体例子与工程取舍

企业中英文知识库可能需要多语言模型；代码检索则要验证符号、API 名和自然语言到代码的跨模态训练。若新模型 Recall@20 从 86% 到 88%，但向量维翻四倍、P95 超 SLO，reranker 或 hybrid 可能是更经济的提升。模型升级必须新建独立 vector field/index，不能混合不同向量空间做近邻。

## 常见误区与面试要点

公开 benchmark 高不等于领域强；维度大不等于语义更丰富；cosine 阈值不能跨模型沿用。面试应回答约束筛选、领域 gold set、分层指标、延迟/容量和迁移五步。
