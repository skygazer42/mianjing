# 29. Agentic RAG 和迭代检索是什么？

## 结论先行

传统 RAG 多是固定的一次 query→retrieve→generate；Agentic RAG 让模型/规划器根据当前证据选择数据源、改写或分解查询、迭代检索、调用 SQL/图/网页等工具，并在证据充分后停止。它适合路径未知、多跳和异构数据任务，但引入非确定规划、循环、成本、工具安全和难评估问题；简单单事实查询应保留快速固定路径。

## 状态机而非自由循环

可靠实现维护显式 state：原问题、已确认 claims/evidence、未解决 subgoals、visited queries/docs、工具结果、预算和 stop reason。一次循环可表示：

```text
observe evidence -> assess gaps -> choose allowed action
-> validate action -> execute tool -> normalize/provenance
-> update state -> sufficient? answer : continue
```

planner 输出结构化 action，由 policy/controller 校验 allowlist、参数、ACL、超时和副作用。证据文本不得直接获得工具指令权限，否则间接 prompt injection 能驱动 agent。

## 迭代检索例子

问题“本季度销量下降最大的产品，其负责人最近提交了什么风险说明？”第一步 SQL 找产品与负责人；第二步用负责人/产品过滤文档检索风险说明；第三步核对时间与来源并合成。若 SQL 已无数据，agent 应停止并说明缺失，不应生成虚假负责人继续搜索。

## 停止与预算

设最大 steps、总检索候选、输入 token、wall-clock 与费用；连续无新证据、重复 query、置信度不足或所有必需 slots 已填触发停止。可用 deterministic router 将大多数 query 走单步 RAG，仅复杂度分类命中时启用 agent；失败时降级为部分答案/澄清，而不是无限重试。

## 评估与可观测

除了最终正确率，测 plan success、每步 evidence gain、tool selection/argument accuracy、无效/重复调用率、步数/成本、停止正确性与攻击成功率。trace 记录每个 action 的原因、输入输出 provenance 和版本，支持固定工具响应 replay；否则模型随机性使回归难定位。

## 常见误区与面试要点

Agentic 不等于把所有组件交给一个 LLM自由发挥，也不必然优于精心设计的多跳 DAG。面试回答显式状态、受控工具、证据充分性、预算停止和简单路径降级。
