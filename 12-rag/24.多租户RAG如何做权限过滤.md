# 24. 多租户 RAG 如何做权限过滤？

## 结论先行

多租户 RAG 的授权边界必须在数据摄取、索引、检索、缓存、生成引用和日志全链路一致。请求先由可信身份系统得到 tenant/user/groups，再将不可被用户篡改的 ACL filter 下推到每个数据源与 retriever；不能先跨租户召回再靠 prompt 或 LLM “不要泄漏”过滤。默认拒绝、权限变更可快速失效、全程可审计是底线。

## 数据与请求模型

文档/chunk 至少带 `tenant_id`、resource id、允许/拒绝主体或继承的 ACL version；parent、child、摘要、embedding 和图边必须继承相同或更严格权限。在线从服务端认证 token 解析主体，授权服务生成受签名/内部 filter：

```text
tenant_id = T
AND (visibility = public_to_T OR acl intersects user_groups)
AND not revoked
```

用户自然语言中的“我是管理员”不能改变 filter。多源检索每一路都执行授权，SQL 要行级策略，图遍历每个节点/边都要检查，不能只校验起点。

## 索引布局选择

高隔离要求可每租户独立 index/namespace，安全简单但小租户资源利用率低、运维多；共享索引加 filter 资源高效，但必须证明引擎 pre-filter 和缓存隔离正确。大租户可独立 shard，小租户共享分区。无论布局，非法候选都不应进入 reranker/LLM，因为模型或日志本身可能泄漏。

## 缓存与引用

result/retrieval/prefix cache key 包含 tenant、主体权限摘要、ACL/index version；共享公共块必须属于相同安全域。权限撤销事件应让相关 cache、搜索快照和派生摘要失效。点击引用时再次授权，防止用户转发过期 URL；trace 和评测样本也按原权限脱敏。

## 测试与威胁模型

建立 canary 文档：租户 A 的独特 secret 在 B 的 dense/BM25/top-k、rewrite、prefix 命中、引用和日志中都不得出现。测试组变更、parent 合并、去重、embedding 迁移、备份恢复与 fail-open；任何授权服务超时应 fail-closed。

## 常见误区与面试要点

post-filter 可能让无权文档占满 top-k，既漏合法证据又扩大泄漏面。面试按 identity→ACL metadata→下推检索→缓存 key→二次引用授权→审计测试回答。
