# 29. Embedding 服务如何做缓存、版本管理、批处理和一致性校验？

## 向量协议与版本

一个可用的版本号不能只写模型名称，应覆盖 checkpoint 哈希、tokenizer/normalizer、最大长度和截断侧、指令模板、pooling、归一化/降维、输出 dtype 与维度。缓存 key 至少由规范化后的输入字节、完整协议版本和输入角色组成；query 与 document 若使用不同前缀，不能共用缓存。

模型一旦升级，旧库向量与新查询向量通常不在同一坐标系，即使维度相同也不能混用。安全发布应新建索引、双写/回填、用 golden query 验证，再原子切换“编码服务版本 + 索引版本”。回滚也必须成对进行。

## 动态批处理

GPU 编码吞吐依赖 batch，但不同长度混批会产生 padding 浪费。服务可在短时间窗口聚合请求，按长度 bucket，并设置最大 token budget 而非只限制样本数；同时用最大等待时间守住 p95/p99。长文本应单独队列，避免 head-of-line blocking。OOM 时降级 batch 或切分请求，但不能悄悄改变 truncation 语义。

缓存适合重复文档/查询，但要权衡输入隐私、容量和失效。文档离线编码可内容寻址；在线 query 命中率低时，过度缓存可能得不偿失。若输入包含用户敏感数据，应遵循保留策略并避免在 key/log 中存明文。

## 一致性与可观测性

维护 golden corpus，校验单条与批量、CPU/GPU、不同副本输出的 cosine/逐元素误差；记录模型版本、token 数、截断标志、范数、非有限比例、batch token 利用率和延迟。量化或编译内核允许小数值差异，应以排序重合率和任务容差判断，而非要求 bitwise 一致。

接口应返回 version、dimension、normalized 等元数据或由强 schema 约束。索引写入前验证维度、有限值和预期范数，拒绝错误向量，防止静默污染。幂等回填需记录内容哈希和编码版本。

面试回答可用“协议哈希做缓存键、token-budget 动态批、模型与索引绑定切换、golden vectors 做回归”四点串起完整工程方案。
