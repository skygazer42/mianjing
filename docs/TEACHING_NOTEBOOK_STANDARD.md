# 案例驱动 Notebook 标准

本仓库的 Notebook 首先是中文教学材料，其次才是可执行测试。断言只能证明实现满足若干不变量，不能替代输入展示、过程观察、结果比较和原因解释。

## 每本 Notebook 必须回答什么

1. **面试问题与回答主线**：先用 5–8 句话给出可以直接复述的结论，再说明后续代码会验证哪几个关键判断。
2. **真实案例**：选择一个有业务语义的具体场景，给出可读字段和至少 5 条样本。可以使用仓库内置的小型脱敏数据、无需下载的公开数据集，或结构与真实系统一致的离线事件；必须说明数据来源、简化项和不能外推的边界。
3. **输入预览**：运行代码后应直接看到原始记录、张量形状、请求、文档、图结构或事件流，而不是只看到变量名。
4. **可比较 Baseline**：先实现最简单的方案并展示结果，再进入主要算法。不能只说“更好”，必须给出同一数据、同一指标下的对照。
5. **核心实现与中间过程**：保留 NumPy、PyTorch 或标准库的底层实现，并输出最能解释机制的中间量，例如 BM25 分项、梯度、路由分数、KV 占用、状态迁移、检索排名或搜索树访问次数。
6. **结果表或图**：至少输出一张可读表格、曲线、矩阵、事件账本或逐样本对照；小型文本表可以用格式化 `print`，数值趋势优先使用 Matplotlib。
7. **结果解读**：紧跟输出解释“看到了什么、为什么、何时会失败”，不能让读者自行猜测变量含义。
8. **失败案例与修正**：故意构造一个边界或反例，先展示错误行为，再展示门禁、算法或参数调整后的变化。
9. **生产差距**：明确教学数据规模、硬件、并发、安全、监控、版本与真实组件替换点。
10. **最小回归测试**：断言集中放在最后一个代码单元，通常 3–8 条，只保护最关键的不变量。

## 可执行验收

- 至少 6 个代码单元、4 次 `print`/`display` 调用和 3 个带可见结果的输出单元。
- Markdown 必须包含“真实案例”“Baseline/基线”“结果解读”“失败案例”四个明确小节。
- `assert` 不超过 8 条，且只能出现在最后一个代码单元；不得用几十条断言承载实验过程。
- 每个有效代码物理行都必须带同行中文注释；空行、纯注释和多行字符串正文不计入代码行。
- 一行只写一条 Python 语句，不用分号压缩教学代码。
- 所有代码单元从空内核顺序执行，保存确定性的小型输出，不保存异常、秘密、真实 PII 或超大二进制结果。
- 代码应展示关键机制；不能调用一站式 Trainer、搜索引擎、Agent 框架或现成网络架构来替代面试问题本身。

## “真实”的含义

真实不等于伪造线上规模，也不要求每本都联网下载数据。一个合格案例应具有真实字段、真实决策目标和真实失败语义，例如：

- 搜索：商品标题、查询、库存、ACL、点击相关性与 nDCG，而不是无语义的 `doc1/doc2`。
- LLM 训练：可读 prompt/chosen/rejected 与 loss、margin、pair accuracy 曲线，而不是裸 token 整数和最终布尔值。
- Serving：请求到达时间、prompt/decode token、deadline、KV block、取消事件与延迟分位数，而不是只断言状态枚举。
- Agent：用户意图、工具 schema、审批票据、动作参数、事件账本和权威回读，而不是只断言 `status == ok`。
- CV/图学习：可显示的图像或图结构、预测与错误样本，而不是只验证张量 shape。

受控小数据用于解释机制，输出必须明确标注“教学实验”，不能冒充线上收益或基础模型泛化。
