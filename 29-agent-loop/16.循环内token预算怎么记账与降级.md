# 循环内 token 预算怎么记账与逼近上限时降级？

## 结论先行

循环每步都消耗 token（prompt + 模型输出 + 回喂的观察），必须在**状态里显式记账**剩余预算（题 06），并在逼近上限时**主动降级**，而不是硬撞上限被 API 截断或报错。记账方式：每步估算消耗、从预算累减，把「已用/剩余」作为状态字段。降级策略（逼近阈值时按序启用）：压缩历史（题 12）、缩短每步输出、跳过可选步骤、提前收敛给出当前最佳结果。关键点有二：预算是循环状态的一部分而非控制器局部变量（崩溃恢复后仍要正确续算，题 05/06）；降级是主动的、可观测的决策，能在 trace 里看到「因预算触发了压缩」。反面是不记账，直到某步超出上下文窗口才崩溃，或被静默截断丢掉关键信息，事后无法解释为什么答案突然变差。

## 真实案例

一个 token 预算为 100 的多步循环，每步基础消耗随历史增长而变大。Notebook 对比不记账（历史累积到某步突然超预算、被迫失败）与记账+降级（剩余预算低于水位线时压缩历史、降低每步消耗，安全完成全部步骤）。数据为教学消耗模型，不代表真实 token 计费。

## 工程取舍与常见坑

- **预算入状态**：只存控制器局部变量的预算在恢复后会丢，无法正确续算（呼应题 06）。
- **降级要分级**：先压缩历史、再缩短输出、最后提前收敛，而不是一步跳到放弃。
- **消耗要估算而非事后才知道**：每步先估 prompt+预期输出，超预算的步应提前降级或跳过。
- **降级必须可观测**：trace 要记录「第 K 步因预算触发压缩」，否则质量下降无法归因（呼应题 26）。

## 延伸追问

「怎么定这个降级阈值？」答：用回归任务集（题 30）扫不同阈值，观察「完成率 vs 平均预算占用」曲线，选在完成率不塌的前提下最省的阈值；阈值太高会频繁无谓降级、太低会来不及降级就撞墙。
