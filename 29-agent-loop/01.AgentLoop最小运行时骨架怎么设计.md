# Agent Loop 最小运行时骨架怎么设计？

## 结论先行

最小骨架是**一个显式状态机加一个确定性控制器**，而不是「反复问模型直到它说 done」的裸 `while`。把一个 step 拆成固定阶段：观察 `observe` → 决策 `decide` → 动作 `act` → 校验 `check` → 推进或停止 `advance/stop`。模型只在 `decide` 阶段提议一个**结构化动作**，其余阶段全部由确定性外壳掌管：注入规范化后的观察、校验动作是否合法、执行并**回读**结果、以不可变方式更新状态、评估停止信号。骨架必须**内置三类停止信号**——完成判定、步数/预算上限、连续错误上限——否则一定会不终止或原地打转。每步产出一条可追溯的账本记录（step、phase、action、observation、状态摘要），这是后续回放、评测和线上排障的地基。

## 真实案例

客服退款处理循环。事件字段：`request_id`、`order_id`、`amount_requested`、订单权威状态（`paid/refunded/unknown`）。每一步：观察订单当前状态 → 决策下一个动作（`lookup_order` / `verify_amount` / `issue_refund` / `finish`）→ 执行 → 回读订单状态。Notebook 用 4 条脱敏退款事件，对比「裸 while 无终止控制」的 baseline 与「五阶段状态机 + 三类停止信号」的正确实现，并展示模型永不吐 `finish` 时骨架如何靠步数上限安全收尾。教学数据为结构化离线事件，不代表真实退款成功率。

## 工程取舍与常见坑

- **最大的坑是把控制流交给模型**：让模型自己决定循环几次、何时停。这会不终止、会打转、且无法回放。正确边界是「模型提议、外壳裁决」——循环的推进与停止永远是确定性代码的职责。
- **step 不要写成有副作用的大函数**。把「纯决策/纯状态转移」与「有副作用的执行」分开：`decide` 和 `reduce`（状态转移）保持纯函数，只有 `act` 碰外部世界。纯的部分才能单测和确定性回放（见题 08）。
- **停止信号要分层且有优先级**（见题 19）：完成判定优先，其次超预算/超时，最后连续错误熔断；任何一个触发都必须能干净退出并给出部分结果。
- **状态在步间不可变演进**：每步产出新状态而非原地修改，既避免隐藏耦合，也让每步都能被快照、比较和回放。

## 延伸追问

「如果模型一直不输出 `finish` 动作怎么办？」答：这正是为什么骨架层必须有**独立于模型**的步数/预算硬上限和无进展检测（见题 18）；超限时按策略返回已完成的部分结果或升级人工，而不是继续烧钱空转。还应记录「因何种信号停止」，离线统计四类停止各自占比来校准上限。
