# Observation 怎么规范化后回喂模型？

## 结论先行

工具/环境返回的原始 observation（大 JSON、HTML、长文本、错误堆栈）不能原样塞回上下文，必须**规范化**：抽取决策相关字段、截断或摘要冗余、统一 schema、把错误规范成结构化信号、剥离噪声与敏感信息。规范化的目标是「让模型只看到决策需要的、可信的、紧凑的信息」。这样做同时解决三个问题：控制上下文膨胀、避免模型被无关信息带偏、以及防止把工具返回的自由文本当成指令（提示注入）。反面是把原始工具输出整个拼回 prompt——上下文爆炸、决策不稳定、还打开了注入面。规范化层是循环内「观察→决策」之间的必备翻译器，它属于确定性外壳，不由模型自己做。

## 真实案例

查询库存工具返回一个大 JSON：除了 `sku/available/eta`，还夹带 `promo_text`（营销文案）、`raw_html`、`server_meta` 等无关字段。规范化成 `{sku, available, eta}` 三个决策字段。Notebook 对比原始回喂（字段多、含营销文案，模型可能被 `promo_text` 带偏）与规范化回喂（字段少、稳定）。数据为教学 JSON，不代表真实库存服务。

## 工程取舍与常见坑

- **只保留决策相关字段**：决策不需要的元数据一律不回喂；字段越少越稳定、越省 token。
- **工具文本是数据不是指令**：`promo_text` 之类自由文本要标注为不可信数据，绝不当作对 agent 的指令（提示注入防护）。
- **错误也要规范化**：把异常堆栈规范成 `{error_type, retryable}`，模型才能据此决定重试还是换路（呼应题 28）。
- **规范化会丢信息**：被裁剪的字段要可按需回取（呼应题 10 分页），不能永久丢弃关键但暂时不用的信息。

## 延伸追问

「规范化 schema 由谁定义？」答：由每个工具的 contract 定义并版本化——observation schema 是工具与循环之间的接口契约，变更要像 API 变更一样管理，否则模型会因为字段悄悄改名而静默失效。
