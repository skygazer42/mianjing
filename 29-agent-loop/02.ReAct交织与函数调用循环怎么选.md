# ReAct 式 Thought–Action–Observation 交织与直接函数调用循环怎么选？

## 结论先行

两种循环的核心差别是「模型每步要不要显式产出自然语言推理」。ReAct 让模型每步先写 Thought（为什么这么做）再给 Action，环境返回 Observation 拼回上下文进入下一步；直接函数调用循环省去 Thought，模型直接输出结构化 tool call，靠工具结果驱动。ReAct 的 Thought 提升多跳推理质量和可解释/可审计性，但更费 token、更容易「想得对做得错」，而且 Thought 只是文本、不是承诺；函数调用循环更省、更易用 schema 约束、更适合高并发，但丢失了中间推理痕迹，复杂多跳任务上更易走捷径出错。选择取决于任务是否需要显式多跳推理、是否要审计推理链、以及成本与延迟预算。最重要的边界：无论哪种，都以 Action 与 Observation 为事实，**绝不把 Thought 当作已发生的事实或已完成的动作**。

## 真实案例

多跳问答：先查「某产品所属团队」，再查「该团队负责人」，最后合成答案。ReAct 轨迹里每步有 Thought（"我还不知道团队，先查产品归属"）；函数调用轨迹里只有 tool call 序列。Notebook 用一个 4 条记录的离线知识表，对比两种循环在同一问题上的步数、token 粗估，并构造一个「Thought 说要查负责人、Action 却查了产品」的不一致失败案例。教学数据为离线小表，不代表真实模型推理能力。

## 工程取舍与常见坑

- **别把 Thought 当事实**：模型在 Thought 里声称「已确认金额无误」不等于真的校验过；只有 Action 的 Observation 能作数（呼应题 20 完成判定）。
- **ReAct 更贵也更容易发散**：每步多出的自然语言会累积上下文、放大漂移；需要配合停止信号（题 19）和打转检测（题 18）。
- **函数调用循环要用严格 schema 约束动作空间**（题 17），否则「省了 Thought」的同时也失去了纠偏的中间信号。
- **可解释性有真实价值但不免费**：只有当推理链会被审计或用于多跳纠错时，Thought 的 token 成本才划算。

## 延伸追问

「能不能既要 ReAct 的推理又要函数调用的省钱？」答：可以做混合——默认函数调用，只在检测到不确定/多跳/失败重试时临时开启 Thought；但要用同一任务集对比开销与收益（题 29 成本模型、题 30 发布门禁），不能凭感觉默认全开 Thought。
