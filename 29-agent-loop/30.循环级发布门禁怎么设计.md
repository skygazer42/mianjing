# 循环级发布门禁：固定任务集怎么评测一次 loop 改动的回归？

## 结论先行

改动循环逻辑（prompt、停止条件、策略、预算）后，**不能凭一次 demo 判断好坏**，必须用**固定任务集**做回归评测：一组带期望结果的任务，用改动前（baseline）和改动后（candidate）的循环各跑一遍，比较成功率、平均步数、成本等指标，只有**不回归**（成功率不下降、成本不超阈值）才放行。发布门禁 = 固定任务集 + 指标阈值 + 「通过才发布」。这是整个专题的收口：它把前面的机制串起来——用确定性重放（题 27）保证可比、用 trace（题 26）采集每步指标、用终止信号统计（题 19）分析停止分布、用成本模型（题 29）核算开销。关键是任务集固定、指标可比、改动前后在**同一任务集**上对比。反面是改完跑一个例子看着对就上线，结果在其它任务上悄悄回归了却毫不知情。

## 真实案例

一个循环有 baseline 和 candidate（改了停止阈值）两个版本。在 4 个带期望答案的任务上评测：candidate 成功率更高、平均步数持平。按门禁规则（成功率不降且平均步数不超阈值）判断放行；再展示一个成功率下降的坏版本被门禁拦截。Notebook 对比三个版本的门禁结论。数据为教学任务集，不代表真实评测。

## 工程取舍与常见坑

- **同集对比**：baseline 和 candidate 必须跑同一个固定任务集，否则指标不可比。
- **多指标而非单指标**：成功率、步数、成本一起看，别只优化成功率而放任成本翻倍。
- **门禁要能拦截回归**：规则必须能让「成功率下降」的版本无法通过，否则门禁形同虚设。
- **任务集要防过拟合**：固定集之外留独立集，避免专门针对固定集调参（真实评测的 holdout）。

## 延伸追问

「任务集多大合适、多久更新？」答：大到能覆盖主要场景和已知失败模式、小到能频繁跑；发现新的线上失败就把它固化进任务集（回归用例只增不删），并定期用独立 holdout 检查是否对固定集过拟合。
