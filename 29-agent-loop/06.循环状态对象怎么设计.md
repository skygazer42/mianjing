# 循环状态对象怎么设计：goal/history/scratchpad/step/budget？

## 结论先行

循环状态对象是整条循环的**唯一真相源**，最小 schema 应包含：`goal`（任务规格/目标）、`history`（已发生的步与观察账本，即事实）、`scratchpad`（工作记忆/中间结论，即推测）、`step`（已推进步数）、`budget`（剩余预算）、`status/done`（终止标记）。四条设计原则：(1) **不可变演进**——每步产出新状态便于快照与回放；(2) **可序列化**——整个状态能 dump/load，支持持久化、迁移和确定性重放；(3) **事实与推测分离**——`history`/回读是事实，`scratchpad` 是模型推测，不能混，否则会把幻觉当证据；(4) **预算显式在状态里**——步数和预算是状态字段而非控制器局部变量，这样任何时刻都能判断还能不能继续。反面是把状态散落在多个可变全局变量或闭包里，结果无法快照、无法重放、无法单测。

## 真实案例

客服 agent 的循环状态：`goal`=处理某工单，`history`=已执行动作与回读，`scratchpad`=对用户意图的当前判断，`step`/`budget`=预算记账。Notebook 对比「散落在全局变量的状态」与「集中的不可变状态对象」：后者能 `json` 序列化、快照、在两步之间做 diff，前者做不到。数据为教学状态，不代表真实工单系统。

## 工程取舍与常见坑

- **可序列化是硬约束**：状态里塞入不可序列化对象（连接、锁、闭包）会让持久化和重放失效；这些应放在外壳，不进状态。
- **事实与推测别混**：把 `scratchpad` 的推测写进 `history` 会让后续步骤把猜测当证据（呼应题 14 context 中毒）。
- **预算入状态**：预算若只存在控制器局部变量里，崩溃恢复后就丢了，无法正确续算（呼应题 16）。
- **别把大对象整个塞进状态**：`history` 会膨胀，需要窗口或摘要（题 11、12），状态只留引用或摘要。

## 延伸追问

「state 里 history 越来越大怎么办？」答：state 存「结构化摘要 + 最近窗口 + 可寻址的完整历史引用」，而不是把所有原始观察都内联进去；这样既保持可序列化，又不让单个状态对象无限膨胀。
