# 循环级 trace：每步记录什么才能回放与因果定位？

## 结论先行

循环级 trace 要为每一步记录**足以支持回放和因果定位**的结构化信息：`step_id`、输入观察、模型提议的动作、执行结果、状态变化（前后状态签名）、本步消耗、时间戳，以及**这一步读了哪些 history 条目**（provenance，题 14）。关键是记**结构化元数据和因果链**，而不是记原始 prompt 全文、秘密或 PII。有了这些，才能做三件事：确定性回放（题 27）、定位第一处出错的步（因果定位）、成本归因（题 29）。这与「智能代理」专题的 trace 分层评分不同——那是给整条轨迹打分，这里是**为单个循环的每一步留下可回放、可归因的最小记录**。反面是只记最终结果或散落的 print 日志：出错了只知道「最后错了」，既无法回放，也无法定位是哪一步、因为读了什么错误观察而出错。

## 真实案例

一个 3 步循环，第 1 步（0 基）读了一条来自不可信来源的错误观察（值 999，本应约 20）导致最终结果被污染。有结构化 trace 时，能从「最终结果错误」反向定位到那一步及其读取的观察；无 trace 只知道结果错了、不知哪一步。Notebook 对比无 trace（只有最终结果）与有 trace（定位到第一处出错步及其读取的来源与值）。数据为教学循环，不代表真实系统。

## 工程取舍与常见坑

- **记结构化元数据，不记原文/秘密**：记 `step_id`、动作、状态签名、消耗，而不是完整 prompt 或凭据（隐私与体积）。
- **记 provenance**：每步读了哪些 history 条目/来源，是回滚（题 14）和因果定位的前提。
- **记前后状态签名**：签名变化定位「哪一步真正改了状态」，无变化的步是 stall（题 18）。
- **trace 本身有成本**：采样率、字段裁剪要权衡，但回放/归因所需的最小字段不能省。

## 延伸追问

「trace 怎么支持定位第一处因果错误？」答：从失败的最终状态沿 provenance 回溯——找到产出错误结论的步，再看它读了哪些观察、哪条观察是错的，逐步上溯到第一处引入错误的步；没有 provenance 就只能在整条 trace 里猜。
