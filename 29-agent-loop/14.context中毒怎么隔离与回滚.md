# Context 中毒：一条错误观察污染后续决策，怎么隔离与回滚？

## 结论先行

context 中毒指一条错误的观察——工具返回了脏数据、模型的一个幻觉被写进 history、或一次提示注入——进入上下文后，污染了后续所有基于它的决策。三层防护：(1) **入库校验与可信标注**——观察进入 history 前做合法性校验并标注来源可信度，低可信数据不能直接驱动不可逆动作；(2) **来源可追溯（provenance）**——每个关键事实记录它来自哪个观察/工具/步，发现某来源不可信时，能定位并回滚由它派生的所有下游决策；(3) **事实与推测隔离**——推测不能自动升格为事实（呼应题 13）。回滚机制：给每个 history 条目记 `source`，一旦某条目被标记中毒，就重算或丢弃依赖它的下游步骤。反面是所有观察一视同仁写进 history，一条脏数据既无法定位也无法回滚，污染永久留存。

## 真实案例

库存工具因 bug 返回了错误的 `available=999`（真实为 0），agent 基于它向用户承诺「立即发货」。随后发现该来源不可信。Notebook 给 history 条目带 `source` 和 `trust`，把这条脏观察标记为中毒后，回滚依赖它的「承诺发货」动作；对比无 provenance 时无法定位该承诺来自哪条观察。数据为教学事件，不代表真实库存系统。

## 工程取舍与常见坑

- **入库即标注可信度**：来源、时间、校验结果要和观察一起存，事后才追溯不到。
- **不可逆动作要更高门槛**：低可信观察可用于只读推理，但不能直接触发发货/退款等副作用（呼应题 01）。
- **回滚要沿 provenance 传播**：中毒条目的所有下游派生都要重算，而不是只删这一条。
- **注入也是中毒**：工具/文档里的自由文本要当数据不当指令（呼应题 09），否则注入等价于往 context 里投毒。

## 延伸追问

「怎么在不重跑整条循环的情况下回滚？」答：靠 provenance 图——只重算依赖被污染条目的下游步骤，未依赖它的步骤保留；这需要每步记录它读了哪些 history 条目（呼应题 26 trace），否则只能整条重放（题 27）。
