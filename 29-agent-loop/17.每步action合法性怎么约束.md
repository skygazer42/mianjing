# 每步 action 合法性怎么用结构化输出/受控解码约束？

## 结论先行

模型每步提议的动作必须落在**合法动作空间**内——合法的工具名、符合 schema 的参数、满足当前状态的前置条件——不能把模型吐出的任意自由文本直接当动作执行。三道关卡：(1) **结构化输出**用 schema 约束动作格式（action name 属于 allowed set、params 匹配 schema）；(2) **受控解码/生成后校验**，非法动作拒绝并要求重新提议或走兜底；(3) **前置条件检查**，动作在当前状态下是否可执行（比如未建表就不能写入，呼应题 03）。核心边界：合法性由确定性外壳校验，模型只是提议者，外壳是裁决者。反面是直接执行模型输出的字符串——会调用不存在的工具、用缺失/错误的参数、或触发越权动作，且失败发生在真正执行时、代价最大。

## 真实案例

一个退款 agent 的合法动作是 `{lookup, refund, finish}`，`refund` 需要 `amount` 参数。模型偶尔会提议不存在的 `cancel_all`，或提议 `refund` 却漏了 `amount`。Notebook 用一个 action schema 校验器逐条校验模型提议，对比无校验（执行非法动作导致越权/缺参退款）与有校验（拒绝非法动作并兜底为追问）。数据为教学动作，不代表真实工具集。

## 工程取舍与常见坑

- **allowlist 而非 blocklist**：只允许已知合法的动作名，未知一律拒绝，别试图枚举所有非法情况。
- **参数 schema 要校验类型和必填**：`refund` 缺 `amount` 属于非法，不能带着 `None` 去执行。
- **前置条件也是合法性**：动作格式对但在当前状态不可执行（如重复 finish）也应拒绝。
- **拒绝要有兜底路径**：非法提议不是直接崩溃，而是要求重提或降级为安全动作（如追问）。

## 延伸追问

「结构化输出已经约束了格式，为什么还要生成后校验？」答：schema 约束能降低非法率但不能保证 100%（尤其参数语义、前置条件），受控解码约束格式、运行时校验兜住语义和状态前置——两者是纵深防御，不是二选一。
