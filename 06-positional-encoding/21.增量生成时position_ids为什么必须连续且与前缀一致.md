# 21. 增量生成时 position_ids 为什么必须连续且与前缀一致？

## 核心原因

增量生成把前缀先处理，再一次输入一个新 token。新 token 的位置必须等于其在完整序列中的位置；否则它的绝对位置向量、RoPE 角度或相对 bias 与“一次性整段前向”不同，attention score 会漂移。正确实现应使逐步生成的最后位置 logits 与相同完整 token 序列前向在数值容差内一致。

## 位置计算

若有效前缀长度为 \(L\)，且 BOS 占位置 0，则首个新增 token 通常使用 \(L\)，下一步 \(L+1\)。这里的 \(L\) 是有效语义前缀长度，不是带 padding 的张量宽度。Left-padded batch 中每条请求长度不同，应从 attention mask 的有效计数或显式 offset 计算，不能统一使用 batch 最大长度。

带 soft prompt/prefix tuning 时还要区分“物理前缀状态数”和 tokenizer token 数：若虚拟 token 参与位置，后续 offset 要包含它们；若架构为虚拟前缀定义独立位置，则按原模型约定。对截断滑窗，同一个新 token 使用全局递增位置还是窗口内重置，也必须与训练和位置缩放设计一致。

## 常见错误

- 每个 decode step 都把新 token position 重置为 0；
- 用输入张量长度而非有效 mask 长度，左 padding 导致整体偏移；
- BOS/EOS/chat template 在服务层和模型层被重复添加，造成 off-by-one；
- RoPE scaling 在预填充与解码使用不同配置；
- 批内请求完成后压缩/重排，但 position offset 没随请求一起搬移。

## 验证

构造短序列，比较 full forward 每个位置 logits 与 token-by-token 结果；再覆盖不同左 padding、不同前缀长、批重排和跨越原长度边界。记录每步 token id、position id 和有效长度，通常比只看生成文本更容易定位。

面试回答要说明位置连续性是模型数学等价的要求，而非缓存 API 的形式限制。本题只涉及位置协议；KV 状态如何存储和压缩属于另一工程主题。
