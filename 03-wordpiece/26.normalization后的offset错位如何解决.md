# 26. Normalization 后的 offset 错位如何解决？

## 结论

解决方法不是事后按字符串搜索 token，而是在 normalization 过程中维护“输出位置到原始区间”的对齐映射，随后让 pre-tokenization 和 WordPiece 切分继承、合并这些区间。API 还必须固定 offset 使用 byte、code point 还是 UTF-16 unit。

## 对齐机制

Normalizer 的每个操作都更新 alignment：字符保留是一对一，lowercase 可能一对多，去重音是删除，NFKC 可能多对一或一对多。BasicTokenizer 输出片段时携带规范化区间，再投影到原文；WordPiece 对片段的子串范围进一步切分。若一个规范化片段来自多个原字符，最终 start/end 通常取覆盖它们的最小包围区间。

## 具体例子

德语 “İ” lowercase 可能展开成 i 加组合点；法语 é 去重音后成为 e；连字兼容字符经 NFKC 可能展开为多个字母。token 的规范化长度与原文长度均不等，使用 token.replace("##","") 的长度累加必然错。emoji 在 JavaScript 中占两个 UTF-16 code units，在 Python code point 口径常为一个。

## 工程取舍与误区

包围区间无法表达不连续来源，复杂编辑可能需要 richer alignment，而大多数 NER API 只提供 start/end。slow tokenizer 往往没有可靠 offsets，应优先使用能传播 alignment 的 fast 实现。标注投影要定义重叠策略：只标首子词、复制到全部子词或使用 ignore_index。所有客户端必须转换到同一索引单位。

## 面试回答要点

- 对齐信息必须随 normalization 前向传播，不能事后猜。
- 说明一对多、多对一和删除三类操作。
- ## 不属于原文，special token 通常无原始跨度。
- 用组合字符和 emoji 做跨语言单测。

## 延伸追问

若一个原字符展开为多个规范化字符，多个 wordpiece 可以共享或重叠同一原文区间，这是合法的；消费方不能假设 offsets 严格首尾相接。反过来，删除重音后可能有原文位置不被任何 token 覆盖。接口文档应说明这种情况，标注回写采用重叠而非长度相等原则。
