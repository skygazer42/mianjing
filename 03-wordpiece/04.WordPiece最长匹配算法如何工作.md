# 04. WordPiece 最长匹配算法如何工作？

## 结论

经典 WordPiece 编码对每个预分词词执行从左到右的 longest-match-first：在当前位置尝试能覆盖最远终点的词表项，词首使用普通形式，后续使用 ## 形式；匹配后移动指针，直到覆盖完整词。任一位置无法匹配时，通常整词输出 [UNK]。

## 伪代码

~~~text
start = 0; pieces = []
while start < len(word):
    end = len(word); found = none
    while end > start:
        s = word[start:end]
        if start > 0: s = "##" + s
        if s in vocab: found = s; break
        end -= 1
    if found is none: return ["[UNK]"]
    pieces.append(found); start = end
return pieces
~~~

实际实现通常先检查词长上限，以防超长输入造成过多尝试。

## 具体例子

词表含 {a, ab, ##bc, ##c}，输入 abc。词首先尝试 abc，失败后命中 ab；位置 2 再命中 ##c，输出 [ab, ##c]。若词表还含 a 和 ##bc，贪心仍选更长的 ab，而不会比较 [a, ##bc] 的全局分数。由此可见最长匹配是局部确定规则，不是 Viterbi 概率最优路径。

## 工程取舍与误区

逐个缩短字符串并做哈希查询的朴素复杂度可能接近 \(O(n^2)\)，substring 分配还会放大常数；Trie、failure links 或 LinMaxMatch 可做到更接近线性。最大词长阈值常直接返回 [UNK]，不同库默认值可能不同。Unicode 字符索引与 UTF-8 byte 索引需统一，否则切片可能破坏多字节字符。

## 面试回答要点

- 单词级处理、从左到右、每步最长、续接加 ##。
- 任一步失败时经典行为是整个词 [UNK]。
- 它不搜索全局最优概率切分。
- 工程优化可用 Trie，安全上要限制单词长度。

## 延伸追问

最长匹配的正确性测试应构造一个反例：较长首片段存在，但较短首片段能接上更长后缀，确认实现仍选择前者；这证明它不是全局最少 token 或概率最优。还要测试中途失败时是否整体 [UNK]、最大词长边界和真实 Unicode 切片。部署若改用 Trie，必须与朴素版本逐词对拍 IDs 和 offsets，而不仅比较 decode。

此外要明确预分词边界：算法只在一个 basic token 内搜索，绝不会为了命中更长词表项跨过空格或标点片段。若业务改变边界，必须重新评估所有最长匹配结果，并把这种变化视为 tokenizer 新版本。
