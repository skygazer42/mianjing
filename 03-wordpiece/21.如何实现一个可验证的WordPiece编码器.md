# 21. 如何实现一个可验证的 WordPiece 编码器？

## 结论

先实现清晰的参考版本，再做 Trie 优化。参考版本应接受已经预分词的单词、vocab、continuation prefix、UNK 和最大词长，严格从左到右做最长匹配；任何位置失败都按目标规范返回 [UNK]。随后用官方 tokenizer 的 golden corpus 验证 token 和 ID 完全一致。

## 参考实现要点

遍历 start，从 len(word) 向 start 缩短 end；start>0 时给候选加 ##；首个 vocab 命中就是最长候选。命中后保存 token 并令 start=end；若 end 退到 start 仍未命中，标记失败并返回单个 [UNK]。在进入循环前检查 code point 长度是否超过 max_input_chars_per_word。映射 ID 时不得用哈希迭代顺序生成，而应读取稳定 vocab 序号。

## 测试用例

至少覆盖：完整词命中；首词+多个续接；最长候选与更短完整路径竞争；中途缺字符导致整词 UNK；空词；标点已独立；多字节 Unicode；长度恰好等于和超过上限；词表中同时有 a 与 ##a。再把 BasicTokenizer、special tokens 和 post-processing 分层测试，避免错误归因。

## 工程取舍与误区

不要一开始就把 normalization、正则、Trie 和 batching 混在一个函数中，否则难定位差异。优化版可用双 Trie 或带状态节点，避免 substring 分配；但每次改写都应与参考版本进行 property-based 对拍。decode 不是 encode 的简单逆函数，需单独实现 continuation 拼接、标点空格和 special token 策略。

## 面试回答要点

- 先定义兼容规范，再写朴素正确版本和测试。
- 关键语义是 longest、## 状态、整词失败和长度上限。
- 优化版必须与参考版逐样本对拍。
- 最终集成还需验证 normalization、offset、IDs 与 special tokens。

## 延伸追问

参考版可以对所有长度不超过六的小字符串穷举 vocab 组合，验证 MaxMatch 的输出符合定义；优化版再与其 property-based 对拍。错误信息也应区分词长超限、当前位置无候选和词表 ID 缺失。这样不仅能证明正常样例可跑，还能保证失败语义与目标 BERT 实现一致。

保存最小失败样例能让后续任何优化都重复验证，防止性能改进悄悄改变模型输入。
