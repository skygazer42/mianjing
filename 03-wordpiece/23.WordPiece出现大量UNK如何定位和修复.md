# 23. WordPiece 出现大量 [UNK] 如何定位和修复？

## 结论

先定位 [UNK] 出现在哪个 basic token、哪个字符位置以及经过何种 normalization，而不是直接扩大词表。常见根因是基础 alphabet 缺失、训练/推理前处理不一致、错误的 continuation prefix、词长上限、特殊 token 配置或乱码。修复必须评估与旧 checkpoint 的兼容成本。

## 排查路径

记录原始 code point、规范化结果、BasicTokenizer 输出；对失败词逐步运行 MaxMatch，输出最后成功 start 与尝试的最短字符候选。检查该字符在词首和 ## 续接形式是否存在，检查 max_input_chars_per_word，比较 tokenizer 文件 hash 和库版本。按语言、Unicode script、来源和请求版本聚合 [UNK]，可迅速识别新语种或数据管线漂移。

## 修复选择

配置错误应恢复与训练一致的 normalizer/pre-tokenizer。新字符确实未覆盖时，可对新模型扩大基础 alphabet、采用 byte fallback 或更适合开放输入的 tokenizer。已有模型若追加 token，需要扩展 embedding 并继续训练；只把未知字符映射到一个新 ID 而模型未学过没有意义。上游乱码应在数据质量层修复。

## 工程取舍与误区

整体 [UNK] 率可能很低，却集中破坏用户名、药名或低资源语言，要看业务关键分组。把所有 Unicode 字符加入 vocab 会挤占容量且仍有组合序列问题。更强的 NFKC/去重音可降低未知，但可能改变安全与语义。线上临时把 [UNK] 拆成字符 IDs 若这些 ID 不存在，同样无法兼容。

## 面试回答要点

- 找到失败 basic token 与第一个不可匹配位置。
- 检查 alphabet、## 状态、前处理、长度上限和版本。
- 区分配置回归、数据损坏和真实覆盖不足。
- 改词表必须配合模型参数适配，不能只改 tokenizer。

## 延伸追问

建议建立未知字符榜单：展示 code point、Unicode 名称、脚本、来源字段、basic token 长度和出现次数，再判断是新语言、乱码还是攻击流量。修复后不仅看 [UNK] 下降，也要确认 token 数、decode 和旧通用集质量没有回归；更强 normalization 可能只是把未知信息悄悄折叠掉。
