# 07. Lowercase 和去重音如何影响 WordPiece？

## 结论

Lowercase 与 strip accents 在 WordPiece 查词表之前改变输入表面形式。它们能合并大小写和重音变体、提高频次共享并降低 [UNK]，但会丢失区分信息、破坏严格可逆性，并使 token offset 对齐更复杂；配置必须与预训练 checkpoint 完全匹配。

## 核心原理

uncased BERT 通常把 “Apple” 与 “apple” 都映射为 lowercase 形式；去重音可能先做 Unicode NFD 分解，再移除 Mn 类组合标记，使 “é” 变成 e。这样一个词表项覆盖多种写法，有限容量可用于更多子词。cased 模型则保留这些差异，以学习专名、缩写和句法大小写信号。

## 具体例子

“US” 与 “us” 在 uncased 管线中变成相同 token，分类任务可能受益于共享，也可能失去国家缩写信息。“résumé” 变成 “resume” 后更容易命中常见片段，但生成或实体回写无法从 token 恢复重音。土耳其语 I/İ/ı 等大小写规则还说明通用 Unicode lower 并非所有语言都语义中立。

## 工程取舍与误区

不能根据模型名字猜配置，应读取 tokenizer 配置并用官方 golden 样例验证。库升级可能改变 Unicode 数据版本或 accent 行为。offset mapping 应保留 normalized-to-original 对齐，不能按规范化字符串长度直接索引原文。安全过滤与模型若使用不同 normalization，可能产生同形异义或绕过风险。

## 面试回答要点

- 收益是共享与覆盖，代价是信息丢失与不可逆。
- 配置是 checkpoint ABI，cased/uncased 不能随意互换。
- 举 US/us、résumé、土耳其语 I 的例子说明任务和语言依赖。
- 评估应同时看 [UNK]/长度和需要大小写、重音的下游任务。

## 延伸追问

面试中可补充：special token 和 never_split 通常应在 lowercase 前被保护，否则 [MASK] 可能变成普通 “[mask]” 字符串并失去控制 ID。上线回归要包含 cased 专名、组合与预组合重音、土耳其语和希腊语大小写，比较 normalized text、IDs 和原文 offsets 三层结果。

如果任务同时需要检索召回和原文展示，可以让模型使用规范化文本，却在业务侧保留原字符串与对齐信息；不要指望 decoder 重建已删除特征。这个架构把建模共享与展示保真分开，也让信息损失成为显式产品选择。
