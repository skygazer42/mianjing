# 28. 超长单词为什么可能造成 WordPiece 性能问题？

## 结论

BasicTokenizer 若把超长无空格串视为一个词，朴素 MaxMatch 会反复尝试大量前缀，造成平方级扫描和临时字符串分配。经典实现常设置 max_input_chars_per_word，超过阈值直接 [UNK]；生产系统还应在更早阶段限制字节数和 CPU 预算。

## 风险原理

正常词长度几十以内，朴素算法的坏复杂度不明显；攻击者却可发送数十万字符的随机串，使每个长候选都不在 vocab，end 一次次递减。即使用 Trie，输入遍历、Unicode 解码和缓存高基数键仍消耗资源。整体 [UNK] 虽只输出一个 ID，得到它之前可能已经花费大量 CPU。

## 防护措施

在 pre-tokenizer 前限制原始 bytes 和 code points；对单 basic token 设置合理上限，超限选择拒绝、受控切块或 [UNK]；使用 Trie/线性 MaxMatch、避免 substring 复制；设置请求 token 与时间预算并支持取消。对 URL、DNA 序列等合法长串，可配置专门预分词规则，而不是无限提高全局上限。

## 工程取舍与误区

直接 [UNK] 虽快但丢失所有内容，检索或安全任务可能不可接受；切块会改变旧 checkpoint 的输入分布。缓存超长随机词会造成 cache pollution，应限制键长度并采用 admission policy。字符数上限要明确是 code point 还是 UTF-16 unit，避免各平台差异。安全测试需包含重复字符、随机 Unicode 与正则最坏输入。

## 面试回答要点

- 正常平均长度不能代表对抗最坏情况。
- 算法优化、长度边界和资源预算要同时做。
- max chars 参数影响输出语义，必须跨端一致。
- 对合法长串应按业务设计专门策略。

## 延伸追问

基准应测总字符相同但边界不同的两组输入：许多正常短词与一个超长无空格词。二者若耗时差几个数量级，就说明 MaxMatch 或正则存在坏路径。长度拒绝应在昂贵 substring 构造前发生，并记录拒绝原因；截断还要避免切断 UTF-16 surrogate 或 UTF-8 多字节序列。
