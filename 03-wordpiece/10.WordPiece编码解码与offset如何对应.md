# 10. WordPiece 编码、解码与 offset 如何对应？

## 结论

编码经历规范化、BasicTokenizer 切片和 WordPiece 子切分；解码通常移除 ## 并按标点/空白规则重组，因此未必严格恢复原文。可靠 offset 必须从每个规范化字符追踪到原文区间，再把子词跨度投影回去，不能用 token 展示字符串长度倒推。

## 核心流程

输入先产生 normalized text 及 alignment，pre-tokenizer 输出带原始区间的词，MaxMatch 将每个词的区间细分为 wordpieces。## 只是内部边界标记，不占原始字符。特殊 token 如 [CLS]、[SEP] 通常没有真实原文跨度，可用 (0,0) 或单独 mask 表示，具体以 API 契约为准。

## 具体例子

“Café!” 若 lowercase 且去重音，模型看到 “cafe !”，可能输出 [ca, ##fe, !]。##fe 的原文跨度覆盖 “fé”，而展示长度含两个额外井号，显然不能直接相加。解码可能得到 “cafe!” 而不是原始 “Café!”，这是 normalization 的预期信息损失，不是 WordPiece merge 出错。

## 工程取舍与误区

offset 单位可能是 UTF-8 byte、Unicode code point 或 UTF-16 code unit；含 emoji 时三者差异明显。fast tokenizer 与 slow tokenizer 的 offset 能力和边界规则可能不同。NER 标签投影常用首子词继承标签、后续子词忽略或复制策略，这属于任务数据处理，不是 tokenizer 固有答案。测试要覆盖组合字符、CJK、emoji、特殊 token 和空字符串。

## 面试回答要点

- ## 不占原文 offset，normalization 才是主要对齐难点。
- decode 常返回规范化文本，不保证 round trip。
- 明确 offset 单位和特殊 token 语义。
- 标注任务应显式保存 word_ids/offsets，而不是靠字符串搜索。

## 延伸追问

NER 数据对齐可先用 word_ids 把每个 subword 关联到原词：首片段继承 B 标签，后续片段按标注规范改为 I 或设为 ignore_index。这个选择影响 loss 和评测，必须写在数据管线中。跨端校验要特别加入一个 emoji 和组合重音，因为 UTF-16、code point 与 UTF-8 byte 三种 offset 会立即暴露契约不一致。

还应验证截断后的跨度：若一个词的部分 subword 被截掉，标签和 word_id 不能错误保留完整词假象。批量 padding 生成的特殊位置也没有原文区间，应通过 special_tokens_mask 区分，而不是把零长度 offset 当成原文开头实体。
