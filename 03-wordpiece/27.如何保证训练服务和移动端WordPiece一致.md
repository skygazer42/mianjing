# 27. 如何保证训练、服务和移动端 WordPiece 一致？

## 结论

把 tokenizer 当作跨语言 ABI：完整冻结 vocab、normalizer、BasicTokenizer、continuation prefix、special/post-processing、长度阈值和 Unicode 行为，并为每个模型制品记录 hash。所有实现必须通过同一 conformance corpus 的 tokens、IDs、offsets 和 decode 测试。

## 制品与契约

仅分发 vocab.txt 不够，还需 do_lower_case、strip_accents、tokenize_chinese_chars、never_split、unk token、max chars per word、special IDs、[CLS]/[SEP] 模板和 truncation side。若平台使用不同库，最好生成单一 tokenizer JSON 或调用同一原生核心；否则明确 Unicode 版本、正则语义和 offset 单位。

## 验证样例

测试集应包含大小写、重音组合形式、CJK 扩展字、emoji、控制符、连续空格、标点、真实 “##”、超长词、空输入和特殊 token 表面串。断言不仅是 decode 文本，还要精确匹配 ID 顺序、attention mask、token type IDs 和 offsets。移动端还要验证 UTF-16 字符串接口到内部 code point 的转换。

## 工程取舍与误区

服务升级 tokenizer 库可能改变边界行为，必须像模型升级一样灰度。缓存键要包含 tokenizer hash，避免新旧结果串用。不能用“同样叫 bert-base vocab”判断兼容，文件可能被重排或配置不同。发现差异时按 normalized text→basic tokens→wordpieces→IDs 找第一处分叉。

## 面试回答要点

- 完整配置和模型成对版本化。
- conformance corpus 覆盖正常、Unicode 边界与恶意输入。
- 精确 ID 一致是底线，decode 一致不够。
- 跨平台特别关注 Unicode 索引与 normalization 版本。

## 延伸追问

部署门禁可让模型 manifest 同时记录 vocab 和完整 tokenizer 配置哈希，加载时校验 vocab_size、UNK/CLS/SEP/PAD ID。移动端测试不只跑几个英文句子，还要包含预组合与组合重音、CJK 扩展字、emoji、连续空白、控制符、超长词和用户输入的特殊串。每条都断言 normalized text、basic tokens、pieces、IDs、offsets、decode；任何一层差异都阻止发布。缓存、量化模型包和热更新也必须以该联合版本为键，避免旧分词结果流入新模型。

灰度期间可让客户端上报 tokenizer 版本、输入长度和 token 数的匿名统计，服务端按版本发现异常膨胀；但不能上传敏感原文。若移动端不能及时升级，服务协议应明确支持的模型-tokenizer 版本矩阵，而不是静默兼容未知组合。
