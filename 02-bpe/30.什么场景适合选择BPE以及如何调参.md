# 30. 什么场景适合选择 BPE，以及如何调参？

## 结论

BPE 适合需要成熟生态、确定性编码、较快训练推理、开放词表和可解释 merge 的通用 LLM、代码或多语言场景。若非常看重概率化多切分和 subword sampling，可优先评估 Unigram；若要兼容既有 BERT 生态，则通常保留 WordPiece。选择应以部署工作负载和联合模型实验为准。

## 关键参数

先选基础 alphabet：受控单语言可用字符，多语言开放输入常用 bytes。再确定 normalization 与 pre-tokenizer，它们往往比 merge 超参影响更大。词表大小通过序列长度收益与 \(Vd\) 参数成本曲线确定；min frequency 防止极稀有 pair 占词表；语料温度采样控制语言公平；BPE-dropout 只在需要子词正则化时启用并单独调概率。

## 场景化决策

通用生成模型重视无 OOV、可逆空格与工具链，byte-level BPE 很稳妥。代码模型需保留格式并针对标识符和长串评估。边缘小模型的 embedding 占比高，可能适合较小词表；长上下文系统对序列压缩收益更敏感，却仍需考虑 softmax。强规范化分类模型与精确文本生成模型的管线选择也不同。

## 调参与误区

建立 8k/16k/32k/64k 等候选，在同一独立语料上按语言和领域比较平均及 P99 token 长度、词表频次健康度、编码吞吐；随后用固定总参数或固定算力训练代理模型。不能认为 GPT 使用 BPE 就说明任何项目都应照搬其 regex 和词表大小，也不能只挑让某份 benchmark token 最少的配置。

## 面试回答要点

- 先按兼容性和功能选算法族，再按预算调词表和语料。
- byte/character、pre-tokenizer、vocab size、采样是四个核心旋钮。
- 给出模型参数、序列成本、长尾覆盖三方权衡。
- 上线前冻结完整制品并用真实请求做成本与质量灰度。

## 延伸追问

最终推荐书可写成决策表：既有 checkpoint 兼容性是硬约束；开放 Unicode 和可逆性决定是否用 byte 底座；序列成本与矩阵参数决定 vocab；多切分正则化需求决定是否考虑 Unigram。任何结论都附代表性数据和小模型证据，才是工程上可落地的选择。
