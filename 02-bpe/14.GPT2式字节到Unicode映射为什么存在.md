# 14. GPT-2 式字节到 Unicode 映射为什么存在？

## 结论

GPT-2 风格 tokenizer 为 256 个 byte 建立到 256 个可打印 Unicode 字符的可逆一一映射，主要是为了让词表和 merges 能以普通文本安全保存，并复用按 Unicode 字符操作的 BPE 代码。它没有改变底层信息仍是 byte，也不是 Unicode normalization。

## 核心原理

控制字节、空白和某些不可打印值不适合直接写入 vocab 文本。实现先保留一批可见字符作为对应值，再为剩余 byte 分配额外 Unicode code point，形成双射 \(g:\{0,\ldots,255\}\to U\)。编码时 UTF-8 bytes 逐个经过 \(g\)，BPE 在映射字符序列上合并；解码时把 token 字符串展开，经 \(g^{-1}\) 得到原 bytes，再做 UTF-8 decode。

## 具体例子

空格 byte 0x20 可能显示为一个特殊可见符号，所以词表里常看到带类似 “Ġ” 前缀的 token；它表达的是前导空格，而不是原文真的含该字母。换行、制表符也可能出现对应的展示字符。检查 token 时若直接打印表面值，容易误判文本被插入奇怪字符，正确做法是通过 tokenizer 的 decoder 查看还原结果。

## 工程取舍与误区

并非所有 byte-level BPE 都采用同一张映射表；有的 JSON 模型直接保存 byte 序列，有的使用不同转义。复制 vocab/merges 却换了 byte encoder 会让每个非 ASCII token 的含义错位。实现还要保证映射是一一对应且版本固定，禁止对映射后的符号做 lowercase、NFC 等处理，否则双射被破坏。该映射也不会自动处理特殊 token，它们通常走单独匹配路径。

## 面试回答要点

- 目的：文本化序列化、安全展示和复用字符 BPE 实现。
- 数学性质是 256 byte 到 256 code point 的双射。
- 映射字符是内部代理符号，不等于原文字符。
- 完整兼容性需要同时一致的映射表、预分词、merges、vocab 与 decoder。

## 延伸追问

可让候选人解释如何验证双射：256 个输入 byte 的映射结果必须互异，逆映射后逐项等于原值；再对随机 byte 串做 encode/decode 性质测试。任何 normalization 都必须发生在 byte 映射之前，映射后的代理 code point 不能再按自然语言字符清洗。
