# 28. 代码场景的 BPE 应该重点优化什么？

## 结论

代码 BPE 除了一般文本压缩，还要保留空格、换行、缩进和运算符，合理处理 camelCase、snake_case、长标识符、数字与字符串，并控制自动生成哈希或 base64 的 token 膨胀。优化目标应覆盖语法结构、编辑补全时延和跨语言泛化。

## 语料与边界

训练语料要按编程语言、仓库和文件去重，避免同一 vendored 库支配频次；许可证与隐私也要治理。预分词不应像自然语言那样折叠空白。可以让常见运算符、缩进模式、关键字和命名片段形成 token，同时避免把具体 API key、提交哈希或整个版本号学进词表。跨文件相同模板需去重，train/test 要按仓库隔离防泄漏。

## 具体例子

“get_user_id” 若下划线和词根均可复用，能支持未见组合；若整个项目私有函数名被合为单 token，频次低且无泛化价值。Python 四空格与换行承载块结构，丢失会改变程序；C++ 的 “::”“->” 和 JavaScript 的 “=>” 是高价值片段。长十六进制串最好按受控长度分块，避免每个随机组合成为候选。

## 工程取舍与误区

平均 tokens/line 会被空行和短语法行误导，应按语言报告 tokens/byte、标识符 fertility、长文件 P99、补全 prefix 编码时延和代码模型 loss。词表过度针对主流语言会损害小众语言或配置文件。把所有关键字强制 added token 也未必好，因为它会扩大词表且破坏带前后缀的自然组合。

## 面试回答要点

- 格式是语义，不能随意 normalise 空白和大小写。
- 语法运算符、标识符构词和随机长串是三类重点。
- 语料应仓库级去重和隔离，避免泄漏与频次偏置。
- 最终以真实代码模型和补全工作负载验证，而非只看压缩率。

## 延伸追问

一个实用消融是分别保留与折叠缩进、分别限制与不限数字片段，再观察语法错误率和补全延迟。还应按仓库而非文件随机切 train/test，防止相同代码复制让 tokenizer 和语言模型指标虚高。对密钥、邮箱等敏感长串不得因高频泄漏而形成完整词表项。
