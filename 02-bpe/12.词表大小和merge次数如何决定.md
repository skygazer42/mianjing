# 12. BPE 的词表大小和 merge 次数如何决定？

## 结论

若初始基础符号数为 \(A\)、特殊或保留 token 数为 \(S\)、成功创建的新 token 数为 \(M\)，理想情况下最终词表约为 \(V=A+S+M\)。工程上应从模型参数预算、序列长度收益、语料覆盖和下游验证共同选择 \(V\)，不能只按“越大 token 越少”判断。

## 参数与成本

embedding 参数量为 \(Vd\)，其中 \(d\) 是隐藏维度；若输出投影不与输入 embedding 共享，相关参数接近 \(2Vd\)。词表增大通常降低平均序列长度，减少 Transformer 中间层时间步，却增加 embedding/softmax 的参数、显存与通信。对大词表，输出 logits 的形状仍包含 \(V\)，训练和解码阶段可能成为明显成本。

## 具体例子

基础 byte alphabet 为 256，特殊 token 为 20，执行 31,724 个有效 merge，可得到约 32,000 词表。若从 32k 增至 64k，只把平均序列长度从 100 降到 95，却在 \(d=4096\) 时多出约 1.31 亿个 embedding 参数，那么收益可能不划算；若面向中文和代码，长度从 160 降到 100，则更大的词表可能值得。

## 工程选择与误区

merge 次数不一定等于请求次数：候选频次低于阈值、无法继续合并、重复表面 token、added token 和库的词表计数约定都会造成差异。应绘制 vocabulary size 与 fertility、每字节 token 数、P95/P99 长度、UNK/byte fallback 比例的曲线，并在相同模型训练预算上做小规模消融。语料语言配比不平衡时，统一增大词表可能只让高资源语言继续吞占容量。

## 面试回答要点

- 给出 \(V\approx A+S+M\) 并指出实现例外。
- 同时讨论序列计算与 embedding/softmax 成本。
- 用收益曲线的拐点选词表，而非照搬其他模型的 32k 或 50k。
- 模型规模、参数共享、多语言覆盖和硬件均会改变最优点。

## 延伸追问

若面试官给出固定总参数，应从 Transformer 主干中扣除随词表增长的矩阵参数，而不能保持主干不变。还要测输出 softmax 或采样核，因为词表扩大即使缩短了序列，也可能让每一步 logits 计算变慢。最终比较应固定训练 token、算力或总参数中的至少一种公平预算。
