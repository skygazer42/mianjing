# 13. Byte-level BPE 如何处理 UTF-8 文本？

## 结论

Byte-level BPE 先把规范化或原始字符串编码成 UTF-8 字节，再把每个字节视为基础符号，随后在预分词片段内部按已学 merge rank 合并。因为任意合法字符串都能表示为字节序列，基础覆盖只需 256 项；解码时展开 token 字节串、连接并执行 UTF-8 解码。

## 数据流程

完整链路通常是：文本 → 特殊 token 识别 → 正则预分词 → UTF-8 bytes → 可打印字节映射或整数符号 → BPE merges → token IDs。训练时在同一种表示上统计 pair。词表中较长 token 本质上都对应一段 bytes，并不要求每个中间 token 单独构成合法 UTF-8 字符；只有所有输出 token 拼接后才需要整体成为合法文本。

## 具体例子

“你”的 UTF-8 是十六进制 E4 BD A0。训练初期它是三个基础 byte token；语料充分时可能先学 E4+BD，再学 (E4BD)+A0。若 “你好” 高频，还可能继续把两个汉字的六字节序列合并。emoji、组合字符和未见过的脚本即使没有 merge，也能退回字节，区别只在 token 数。

## 工程取舍与误区

一些库将每个 byte 双射到可打印 Unicode 字符，以便 vocab/merges 使用文本文件保存；这些“字符”只是容器表示，不能按普通 Unicode 语义处理。若错误地对映射后字符串再次 UTF-8 编码，会产生双重编码。offset 需明确按原字符串字符还是 byte 计数。decode 对截断序列可能遇到不完整多字节字符：流式系统应缓存尾部字节，不能随意 replacement decode。

## 面试回答要点

- 256 字节提供完备底座，merge 提供压缩。
- token 边界可以落在 Unicode 字符内部，但拼接后字节可恢复。
- byte-to-Unicode 映射是序列化技巧，不是再次做语言字符分词。
- 多语言优势是无 OOV，代价是低资源脚本可能 token 膨胀。

## 延伸追问

边界测试可以把一个多字节字符拆在网络 chunk 之间，确认流式 UTF-8 decoder 会缓存不完整尾字节；还应测试单个 token 本身对应非法 UTF-8 前缀时，只有与后续 token 拼接后才解码。若实现逐 token 调用 UTF-8 decode，合法文本也可能被错误替换成乱码。
