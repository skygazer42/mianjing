# 20. Normalization 变化为什么会让 BPE 模型失效？

## 结论

BPE 学到的是“规范化后符号序列”的频率与合并路径。训练和推理若在大小写、Unicode 形式、重音、空白或控制字符处理上不同，输入基础符号和边界就变了，即使 vocab 与 merges 文件完全相同，也会得到不同 token IDs，严重时产生 OOV 或 token 膨胀。

## 核心原理

Unicode 中肉眼相同的 “é” 可表示为单个 U+00E9，也可表示为 e 加组合重音。若训练使用 NFC 而推理不做，byte 序列和字符序列都不同，已学 merge 无法命中。lowercase 会合并大小写统计，NFKC 可能把兼容字符折叠，strip 或空白折叠会删除可恢复信息。BPE 并不理解这些形式等价，它只匹配精确符号对。

## 具体例子

训练时 “HTTPServer” 被保留大小写，并学出常见代码 token；线上先 lowercase 成 “httpserver”，原 merge 可能全部失效。训练时中文全角数字经 NFKC 变半角，而推理漏掉该步骤，也会退化成字节片段。更危险的是安全过滤在 normalization 前检查、模型在 normalization 后解释，攻击者可能用兼容字符绕过规则。

## 工程取舍与常见误区

规范化越强，统计共享和序列压缩可能越好，但原文信息与精确 offset 越难保留。生成、代码、法律原文常需要保留大小写和空白；检索或分类可能接受更强折叠。应把完整 tokenizer JSON 与哈希作为模型制品部署，做 golden corpus 的 tokens/IDs/offsets/round-trip 回归。只对比 vocab 文件 hash 不能保证一致。

## 面试回答要点

- normalization 位于 BPE 之前，改变训练分布和 merge 命中。
- 举组合字符、大小写、全角半角的精确例子。
- 一致性不仅是质量问题，也是模型兼容和安全边界问题。
- 方案不是“永远不规范化”，而是按任务选择并冻结配置。

## 延伸追问

上线防线可以让模型配置记录 tokenizer SHA-256，服务启动时强校验；CI 则选择规范等价但字节不同的 Unicode 对、大小写、全角半角和空白组合做 golden IDs。这样既能发现配置漂移，也能明确哪些差异是产品有意折叠、哪些属于不可接受的信息损失。
