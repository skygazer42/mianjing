# 09. BPE 解码为什么通常可逆，又可能不严格可逆？

## 结论

merge 本身只是把相邻底层符号拼接起来，只要每个 token 保存对应字节串，逆向拼接就能恢复原始字节；但完整 tokenizer 还包含 normalization、空白处理、预分词和非法字节策略，这些步骤可能丢失信息。因此应区分“BPE 模型可展开”和“端到端 tokenize-decode 严格还原原字符串”。

## 核心原理

byte-level BPE 的 token 可视为字节串。对 IDs 依次查表并连接，得到原 UTF-8 字节，再严格解码即可恢复文本。字符 BPE 加词尾标记时，解码会把标记替换成空格；若原始文本有连续空格、制表符或换行，而训练前只用了 split，它们已经无法恢复。lowercase、去重音、NFKC 等规范化也属于多对一映射。

## 具体例子

输入 “Café  ” 若先做 lowercase 和去重音，模型实际看到 “cafe”；解码最多得到规范化字符串，不可能重建大写、重音和两个尾随空格。相反，如果输入直接转换成 UTF-8 字节，空格和重音字节都保留，且 added/special token 的处理不吞掉原文本，则 round trip 可以严格相等。特殊 token 还可能被 decode 配置选择性跳过。

## 工程取舍与常见误区

可逆性测试应明确目标：比较原字符串、规范化后字符串，还是原始字节。遇到代理字符或非法 UTF-8 时，errors=replace 会引入替换字符，errors=ignore 会丢字节；日志和安全场景可能要求 byte fallback 或专门的字节转义。offset mapping 也不能简单按 token 字符串长度推导，因为规范化前后的 code point、UTF-8 byte 与 UTF-16 索引各不相同。

## 面试回答要点

- BPE merge 是可展开的，信息丢失通常来自外围管线。
- 举大小写、Unicode 规范化和连续空格三个例子。
- 特殊 token 是否参与 decode、是否跳过也会影响 round trip。
- 工程验收应覆盖多语言、emoji、组合字符、控制符和异常字节。

## 延伸追问

面试中若被问“可逆的最低条件”，可以回答：底层符号到 bytes 的映射必须单射，拼接顺序必须保留，所有前处理也必须可逆且特殊 token 不吞原文。只要任一 normalization 是多对一，严格 round trip 就不成立，但仍可把“恢复规范化文本”定义为清晰且可测试的契约。
