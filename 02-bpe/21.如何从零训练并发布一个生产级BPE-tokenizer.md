# 21. 如何从零训练并发布一个生产级 BPE tokenizer？

## 结论

生产流程不只是调用 train：需要先定义覆盖目标和兼容契约，清洗并按场景采样语料，冻结 normalization/pre-tokenization，训练与评估 BPE，分配特殊 token，最后把完整配置、版本、数据指纹和回归样例作为不可分割的模型制品发布。

## 实施步骤

第一，统计目标语言、代码、数字、emoji 与领域文本比例，去重并移除敏感或损坏数据。第二，确定 byte 还是字符底座、Unicode 规范化、空格与数字边界。第三，在代表性样本上扫描多个 vocab size、min frequency，训练确定性 merge。第四，预留 BOS/EOS/PAD/UNK 与应用控制 token，锁定 ID。第五，用独立评测集比较 fertility、byte fallback、P95 长度、往返解码、offset 和吞吐。第六，与小模型联合做下游消融。

## 发布契约

制品至少包含 tokenizer 主配置、vocab、ordered merges、added/special tokens、normalizer、pre-tokenizer、post-processor、decoder 和版本元数据。CI 使用 golden corpus 比较精确 ID 序列，并在 Python/Rust/服务实现间做交叉测试。服务启动时校验 tokenizer hash 与模型配置中的 vocab size、special IDs，避免拿错文件仍能“正常运行”。

## 工程取舍与误区

只优化平均 token 数会牺牲低资源语言和攻击输入的尾部成本；只看 tokenizer 指标又可能忽略 embedding 扩大后的模型预算。训练语料不应直接等于语言模型全量语料，合理的平衡采样能防止高资源域垄断词表。上线后 tokenizer 应视为模型 ABI，任何 ID 或前处理变化都要新版本和模型适配，不能原地覆盖。

## 面试回答要点

- 从需求、数据、训练、离线评测、联合实验、制品化六阶段回答。
- 明确 tokenizer 与 checkpoint 必须成对版本化。
- golden tests 要覆盖多语言、空白、异常 Unicode、特殊 token 和超长输入。
- 可追问如何灰度比较新旧 tokenizer 的成本与质量。

## 延伸追问

灰度时可在不影响用户结果的影子流量中同时编码新旧版本，记录 token 数变化、超长截断比例、语言分组 P99 与 CPU 时延；随后用离线新模型比较质量。因为旧模型不能直接消费新 IDs，线上 A/B 必须将 tokenizer 与对应 checkpoint 作为整体实验单元。
