# 24. BPE 训练与推理分词不一致如何排查？

## 结论

应沿管线逐层比较，而不是直接怀疑 merge 算法：原始字节、normalization 结果、特殊 token 匹配、预分词片段、byte 映射、逐轮 merge、token 字符串、ID 和 post-processing。找到第一处分叉，通常就能定位配置缺失、版本差异或边界处理 bug。

## 排查步骤

先锁定同一输入的 UTF-8 十六进制，排除不可见字符。输出 normalization 前后 code point；记录每个预分词片段与原文 offset；确认 added token 是否优先匹配。随后对单个片段用参考实现打印当前 pair 与 rank，逐步重放 merges。最后比较 vocab token→ID、BOS/EOS 注入、truncation 和 padding。对两个运行环境记录库版本、模型文件 hash、regex 引擎和 locale。

## 常见根因

常见问题包括 NFC/NFKC 或 lowercase 不一致；正则 Unicode 类别语义不同；byte-to-Unicode 表不同；merges 文件顺序被排序；JSON 读取时丢掉前导空格；特殊 token 只在一端注册；一个实现从左到右处理重叠，另一个错误并行处理；新版本修复了 pre-tokenizer 行为但服务未同步。

## 工程防线

建立几十到几百条高信息量 golden corpus，断言规范化文本、tokens、IDs、offsets 与 decode。跨语言绑定调用同一原生核心或共享 conformance suite。日志中不要直接记录敏感原文，可记录输入 hash、长度、token 数、tokenizer hash 和经脱敏的首个分叉。不能只检查最终 decode 相同，因为不同 ID 序列也能解码为相同文本，却会让模型语义完全不同。

## 面试回答要点

- 使用“找第一处分叉”的分层法。
- vocab/merges 一致仍不够，外围配置必须一致。
- 最重要的部署防线是模型-tokenizer 配对 hash 与 golden tests。
- 最终 IDs 一致比肉眼 token 或 decode 一致更严格。

## 延伸追问

若差异只在特定平台出现，可把失败样本最小化到一个 code point 或一个边界，并输出其 UTF-8 十六进制，排除终端显示误导。对 merge 实现则用小词和有限规则逐步重放，确认重叠替换方向、rank 并列和缓存键；这种最小反例应加入永久回归集。
