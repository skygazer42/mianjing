# 26. 特殊 token 与普通 BPE 合并应如何协调？

## 结论

特殊 token 通常不应被拆成普通字符或参与 BPE merge，而应在规范化/预分词的明确阶段作为原子整体识别，再分配固定 ID。系统必须定义允许哪些特殊串、是否接受用户文本直接触发、匹配优先级及解码行为，否则容易出现训练错位和提示注入边界问题。

## 处理流程

一种常见顺序是先扫描 registered special/added tokens，将其区间隔离；普通区间再做 normalization、pre-tokenization 和 BPE。另一实现可能先 normalize，但必须保证训练与服务一致。BOS、EOS、PAD 常由 post-processor 根据任务模板注入，并非原文匹配；控制消息边界的 token 则由 chat template 生成。所有 special IDs 必须与模型配置、loss mask 和生成停止条件一致。

## 具体例子

若 “<eos>” 未注册，它可能被切为 “< + e + os + >”，模型不会看到真正 EOS ID。若允许任意用户输入字符串 “<eos>” 自动映射为 EOS，用户就可能提前终止或伪造角色边界。安全做法是调用编码 API 时明确 special token policy：普通用户内容按文本处理，可信模板层才能插入控制 ID。

## 工程取舍与误区

added token 的匹配常采用最长优先，并可配置是否吸收左右空白；这些行为不是 BPE merge 文件能表达的。新增 special token 后必须扩展模型矩阵，除非复用预留 ID。PAD 与 EOS 是否共享要结合 attention mask 和 loss mask，不能照搬别的模型。decode(skip_special_tokens=True) 便于展示，却会掩盖 round-trip 与调试信息。

## 面试回答要点

- 特殊 token 是管线控制符，通常在 BPE 外原子处理。
- 区分原文匹配、模板注入和 post-processing。
- ID、mask、stop 条件与 chat template 必须共同版本化。
- 对不可信输入要防止表面字符串直接升级为控制 token。

## 延伸追问

测试应区分三种输入：模板 API 显式注入控制 ID、普通用户文本恰好包含相同表面串、以及串被拆在流式 chunk 边界。三者的权限和编码结果必须有明确契约。若 added token 支持 lstrip/rstrip，还要测试它是否意外吞掉换行或代码缩进。
