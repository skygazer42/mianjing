# 29. 如何防御 token 膨胀和分词拒绝服务？

## 结论

攻击者可输入缺少高层 merge 的罕见 Unicode、超长无空格串、重复边界模式或触发正则最坏路径的文本，使少量可见字符产生大量 token 或消耗异常 CPU。防御应覆盖输入字节、规范化后长度、单片段长度、token 数、token/byte 比与编码时间，而不是只限制字符数。

## 风险原理

byte-level BPE 虽无 OOV，但一个四字节 emoji 最坏可变成四个 token，复杂组合字符还可能让肉眼长度与字节长度严重偏离。朴素 \(O(L^2)\) 合并在超长预分词片段上会放大 CPU；带灾难性回溯的 regex 可能在 BPE 前就阻塞。请求在分词后才发现超过上下文，前面的 CPU 和内存已被消耗。

## 防护措施

使用线性或有界 regex 引擎，设置原始 bytes、Unicode code points、单片段 bytes 和最终 token 上限；在编码过程中增量检查预算并支持取消。对 token/byte 比、P99 编码时延、拒绝原因和语言分组监控。服务侧在进入昂贵模型队列前完成配额扣减，并限制并发。对已知合法长文提供受控分块，而非全局放宽。

## 工程取舍与误区

简单截断原始 byte 可能切断 UTF-8，简单截断 token 又可能移除协议尾部或安全提示；应由上层定义保留头尾的策略。Normalization 可能扩张字符串，例如兼容分解，限制要在前后都检查。缓存对重复攻击有帮助但也可能被高基数输入撑爆，需容量和键长度限制。无 UNK 绝不等于抗攻击。

## 面试回答要点

- 字符限制不能代表 token 或 CPU 限制。
- 防御分三层：线性实现、全过程预算、可观测与限流。
- 测试包含长无空格、组合字符、随机 bytes、重复 pair 和特殊 token 前缀。
- 拒绝或截断策略必须与提示模板和业务语义协调。

## 延伸追问

容量规划可同时设软硬阈值：软阈值记录并降级，硬阈值在模型排队前拒绝。监控 token/byte 比的语言基线，避免把正常的多字节低资源语言误报为攻击。安全回归还应验证 tokenizer 超时能够取消，而不是后台线程继续占满 CPU。
