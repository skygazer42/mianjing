# 27. 流式 BPE 编码和 offset mapping 有哪些难点？

## 结论

BPE 决策依赖相邻符号，任意切块边界可能截断一个 UTF-8 字符、预分词片段或可跨边界的 merge，所以不能对网络 chunk 独立编码后简单拼接。offset mapping 又要跨 normalization 与 byte 映射追踪来源，必须明确索引单位并保存对齐关系。

## 流式难点

假设词 “tokenization” 被拆到两个 chunk，单独编码 “token” 和 “ization” 可能错过覆盖完整片段的 merge，结果与一次性编码不同。可靠方案是在确定的预分词边界才提交结果，保留最后一个未闭合片段；UTF-8 decoder 还要缓存不完整多字节尾巴。若预分词正则允许跨长范围匹配，最坏需要限制片段长度或设计可增量状态机。

## Offset 对齐

token 表面可能经过 NFC、大小写折叠、byte-to-Unicode 映射，长度不能直接映射到原文。实现应让 normalizer 返回规范化字符到原区间的映射，pre-tokenizer 继承区间，BPE token 再聚合底层 byte/字符跨度。API 要说明 offset 是 UTF-8 byte、Unicode code point 还是 UTF-16 code unit，否则 Python、JavaScript 和 JVM 客户端会出现偏差。

## 工程取舍与误区

为降低延迟过早输出 token，后续字节到来时可能需要撤回并重新合并，这会破坏下游流式消费契约。多数系统选择只对完整输入编码，或在稳定边界增量提交。normalized text 中新增或删除字符时，一个 token 可能对应不连续原文区间，简单 start/end 只是包围范围。NER、标注回写等任务必须通过测试明确这种语义。

## 面试回答要点

- chunk 边界不等于 tokenizer 安全边界。
- 需缓存 UTF-8 尾字节和未闭合预分词片段。
- offset 单位与 normalization 对齐必须写进接口契约。
- 用整句参考结果验证流式拼接结果完全一致。

## 延伸追问

若业务必须极低延迟，可定义“稳定前缀”：只有当 pre-tokenizer 已确认某边界不会被未来字符延长时才提交其 tokens，末尾片段留在缓冲区。该协议需要规定 flush 行为和最大缓冲长度，并用任意 chunk 划分做性质测试，保证最终 IDs 与一次性编码完全相同。
