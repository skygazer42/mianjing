# 18. Prefill 和逐 token 解码时 attention 的计算形状有何不同？

## Prefill

模型一次处理长度 \(L\) 的提示。每层 Q、K、V 都含 \(L\) 个位置，score 形状 \([B,H_q,L,L]\)（GQA 中 K/V 存储头数较少，但计算按 query heads 分组）。Causal 情况只用下三角，渐进复杂度仍 \(O(L^2d)\)。矩阵较大，GPU GEMM/Flash kernel 并行度高，往往计算受限。

## 逐 token 解码

每步只有新 query，\(L_q=1\)，它与长度 \(L_k\) 的有效前缀 keys 比较，score 为 \([B,H_q,1,L_k]\)，单步算术约 \(O(L_kd)\)。矩阵变成细长向量运算，读取历史 K/V 的带宽、调度和 batch 大小更关键。MQA/GQA 通过减少 KV heads 降低读取量，但每个 query head 仍产生自己的 score。

若不复用前缀 K/V、每步重算整段，成本会极高；这里只说明计算形状，具体 KV-cache 管理、分页与淘汰属于独立主题。

## Mask 和位置

Prefill 使用完整 causal 三角加 padding/segment mask；单 token decode 时没有“query 内部未来”，但要屏蔽前缀 PAD，并为新 token 使用连续 position id。某些 kernel 的 causal alignment 在 \(L_q\ne L_k\) 时有上/下对齐差异，不能把方阵三角 mask 机械切一行。

## 性能判断

分别测 time-to-first-token（含 prefill）和 inter-token latency/throughput。长 prompt 重点优化 FlashAttention、分块与算力；decode 重点看 KV 带宽、GQA/MQA、batching 和融合小 kernel。平均总吞吐会掩盖两阶段瓶颈。

面试回答应报出 \(L\times L\) 与 \(1\times L\) 的 score 形状，解释计算受限与带宽受限的转变，并指出 GQA 主要帮助解码 KV 读带宽。
