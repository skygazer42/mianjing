# 21. Transformer 的训练、prefill 与 decode 计算形态为何不同？

## 结论

三者使用同一组模型权重，却处在不同的计算形态。训练已知整段输入和标签，可在序列维并行，包含前向、保存/重算激活和反向；prefill 只做前向，但一次处理整段提示并建立中间状态；decode 每步通常只有一个新 token，需要反复执行小批量矩阵计算并读取历史状态，因而更容易受显存带宽与调度开销限制。

## 计算特征

训练阶段长度 (S) 的 causal attention 虽不能看未来，但下三角各 query 的结果可同时计算。大矩阵 GEMM 容易提高 GPU 利用率，代价是激活和 attention 中间量占显存。prefill 同样有较大的 `[B,S,d]` 矩阵，通常计算密集；其端到端指标主要关联首 token 延迟（TTFT），长 prompt 下 attention 的 (S^2) 项与权重读取都重要。

decode 在第 (t) 步只处理新 query `[B,1,d]`，与此前位置交互。权重每步都要经过各层，而每 token 可用于矩阵乘的工作量较小，批量不足时难以摊销读取几十 GB 权重的成本。服务端通过动态/连续批处理将多个请求的 decode 步拼在一起提高算术强度，但会引入调度和尾延迟权衡。

## 粗略判断

训练吞吐常用 tokens/s 或模型 FLOPs 利用率；prefill 看 TTFT、prompt tokens/s；decode 看 time per output token、inter-token latency 和并发吞吐。只报一个“推理 QPS”会掩盖 prompt/输出长度分布。相同总 token 数下，1000-token prefill 与逐步生成 1000 token 的运行时间也不会相同，因为前者是少量大算子，后者是大量串行小算子。

## 工程取舍与误区

量化权重通常显著帮助内存带宽受限的 decode，对计算密集 prefill 的收益取决于量化内核；FlashAttention 对长序列训练/prefill很关键，但不能消除自回归步间依赖。KV cache 的形状、分页和容量规划属于缓存专题。

## 面试回答要点

用“序列并行大 GEMM—一次提示前向—逐 token 带宽受限”概括三阶段，再对应 TTFT 与 TPOT 指标，避免误说 causal mask 导致训练也必须逐 token 执行。
