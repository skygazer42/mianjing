# 02. MoE 为什么参数很多，但计算量不会同比例增加？

## 结论先行

因为 MoE 使用**条件计算**：模型保存全部 experts 的参数，但 router 对每个 token 只执行其中 top-k 个。当 expert 数量 $E$ 增大而激活数 $k$ 保持不变时，总参数近似随 $E$ 增长，专家计算却主要随 $k$ 增长。不过路由、通信、padding 和负载不均会让真实 FLOPs 与延迟高于这个理想估算。

## 用公式拆开三个口径

设每个 expert 是两层 FFN，输入/输出维度 $d$、中间维度 $d_{ff}$，忽略 bias 和 gated FFN 的常数差异，单专家参数约为：

$$
P_e\approx 2dd_{ff}
$$

若一层有 $E$ 个 routed experts，每 token 选择 $k$ 个，则：

$$
P_{expert,total}\approx E P_e
$$

$$
P_{expert,active/token}\approx kP_e
$$

专家前向乘加量也主要与 $kP_e$ 同阶，而不是 $EP_e$。因此必须分别报告：

- **total parameters**：checkpoint 中所有参数；
- **active parameters**：某 token 一次前向实际经过的参数；
- **FLOPs/token**：还要包含 attention、shared expert、router 和其他 dense 层。

“激活参数”并非严格的性能单位，同一参数可能参与不同形状和复用次数的运算；它只是便于解释稀疏性的近似口径。

## 一个数字例子

假设 dense 模型某层只有一个 1B 参数 FFN。MoE 将它换成 64 个同尺寸 expert，每 token 选 2 个：

```text
专家总参数：64B
专家激活参数：约 2B / token
```

总参数是原 dense FFN 的 64 倍，理想专家计算约是 2 倍而非 64 倍。如果改成 64 个更窄的 expert，使单个 expert 只有 dense FFN 的一半，那么激活 2 个的理论专家 FLOPs可接近原 dense 层，同时获得约 32 倍的专家总容量。

真实模型还包含每层 dense attention、embedding、norm，以及可能始终激活的 shared experts。因此不能拿 `top-k / expert-count` 直接乘整个模型总参数来声称“实际只用了多少参数”。

## 为什么理论稀疏不等于等比例加速

### 1. dispatch 与 combine

expert parallel 下，token 先按路由结果发往持有目标 expert 的设备，计算后再发回原设备和原序列位置，通常形成两次 all-to-all。通信字节、同步等待和重排 kernel 都不是专家矩阵乘法 FLOPs，却会进入延迟。

### 2. 负载不均与 capacity

如果某专家收到很多 token，其他 GPU 做完后仍要等待最慢设备。容量受限实现可能丢弃溢出 token；padding 实现会把每个 expert 补到固定容量，执行无效计算；dropless 实现虽然不丢 token，但矩阵形状不规则、尾延迟更难控制。

### 3. 小矩阵与低利用率

Dense FFN 可以把大量 token 合并成规则 GEMM。MoE 把它拆成多个不同大小的 expert batch；低并发时每个 expert 只有少量 token，GPU 难以饱和，实际每 FLOP 成本更高。

### 4. 参数存储与带宽

没被当前 token 激活的 expert 不做乘法，但其权重仍要驻留在集群内或从更慢存储加载。MoE 节省计算不等于按激活比例节省 checkpoint、显存和参数通信。

## 如何公平比较 MoE 与 Dense

训练论文常比较等 FLOPs/token 或等训练计算预算下的 loss；部署则应固定质量目标、硬件、batch、输入输出长度和延迟 SLO，再测：

- tokens/s、TTFT、TPOT 与 P95/P99；
- 设备利用率、all-to-all 时间占比和跨节点流量；
- expert token 直方图、最大/平均负载比、padding 或 drop 比例；
- 总权重显存、激活显存和并发容量；
- 能耗与每百万 token 成本。

只比较理论 FLOPs 会忽略 MoE 最关键的系统代价。

## 面试回答要点

先写 $E$ 个专家、top-k 激活：总专家参数 $EP_e$，单 token 专家激活约 $kP_e$。再说明完整计算还包括 dense 部分。最后指出三项偏差：all-to-all 通信、路由负载不均、小 expert batch 的硬件利用率，所以“参数不同比例增加”成立，但“不同比例增加的 FLOPs”不保证同等比例的墙钟加速。
