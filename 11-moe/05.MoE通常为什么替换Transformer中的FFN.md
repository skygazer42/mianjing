# 05. MoE 通常为什么替换 Transformer 中的 FFN？

## 结论先行

Transformer 的 FFN 对每个 token 独立执行、参数占比大、接口形状固定，最适合替换成一组可并行的专家；attention 则负责 token 间交互，其 QK 配对、mask 和全局依赖更难按 token 独立分桶。将 FFN 专家化能显著增加参数容量，同时保持 attention 作为稳定的共享通信骨架。

## 从计算图理解

Dense FFN 对每个位置 \(x_t\) 独立计算，例如 SwiGLU：

\[
FFN(x_t)=W_o\big(\operatorname{SiLU}(W_gx_t)\odot W_ux_t\big).
\]

MoE 只需把它换成

\[
MoE(x_t)=\sum_{e\in TopK(x_t)}g_{t,e}FFN_e(x_t).
\]

不同 token 在进入 FFN 前可按 expert 排序成多个微批，各 expert 仍执行规则 GEMM，输出再还原顺序。FFN 不依赖同一序列其他位置，所以 dispatch 不改变语义依赖；残差接口仍是 \([B,L,d]\)。

Attention 的输出 \(A_{ij}\) 同时依赖 query \(i\) 与 key \(j\)。若把 attention 按专家路由，必须定义 token 对该进哪个专家、跨专家如何交互、mask 如何保持，稀疏路由可能直接切断长程关系。并非不能做 attention experts，但系统和建模复杂度明显更高。

## 系统与训练取舍

FFN 常占 block 参数和 FLOPs 的大头，复制它能用较少激活计算换大量总参数；attention、norm 和 embedding 继续 dense，所有 token 仍共享一条信息通道，有助于专家之间交换上下文。通常不是每层都设 MoE：间隔插入可降低 all-to-all 次数、权重显存和路由不稳定，具体频率由质量—成本消融决定。

## 常见误区

“MoE 层只包含专家”不完整：它还包含 router、dispatch/combine、容量策略，可能另有 shared expert。FFN 专家也不是天然领域模块，它们处理的是已上下文化 token 状态。把所有 FFN 层全部替换并不必然更强，通信可能成为瓶颈。

面试时应回答“token-wise 独立、参数占比高、GEMM 接口规则、attention 保留共享交互”四点，再说明可隔层使用。
