# 22. batch 和并发如何影响专家负载与延迟？

## 基本关系

Batch/并发增大提供更多token assignments，按大数定律每个expert更接近期望负载，也能形成更大的expert GEMM和all-to-all消息，提高吞吐。但请求路由相关、序列长度不同且热门expert存在时，平均更平滑不代表尾部消失；等待凑batch还会直接增加排队延迟。

## 数量例子

64 experts、top-1、一个decode step只有16个token时，许多experts为空，非空expert也常只有1个token；权重加载和kernel launch难摊销。若continuous batch有1024个token，均匀时每expert约16个，grouped GEMM更有效。但若40%流量都路由到某expert，它会收到约410个，成为straggler并撑高整个step P99。

## 动态batch与尾延迟

服务可按时间窗聚合请求、按长度或预计expert路由分桶，并设token budget而非只设请求数。时间窗太大提升吞吐却损TTFT/TPOT。不同expert完成时间不一，combine往往等待所有选中路径；top-2时一个慢expert就拖住token。

请求之间也可能相关：同一活动突发大量代码/某语言请求，负载方差远高于独立同分布假设。容量应依据真实burst和P99而不是均匀二项模型。

## 优化与监控

Continuous batching、热门expert复制、负载感知路由、按拓扑放置可缓解；但改变路由可能影响质量和确定性。监控每step token/expert直方图、expert batch size、空expert比例、最大/平均、排队时间、最慢expert与P99，并按prefill/decode分开。

面试回答应说明“大batch改善均衡与GEMM，但增加排队且无法消除相关热点”，再用decode小batch例子和P99指标落地。
