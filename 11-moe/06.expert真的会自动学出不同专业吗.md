# 06. expert 真的会自动学出不同专业吗？

## 结论先行

Expert 可能形成统计上的专业化，但不会保证自动对应“代码专家、中文专家、数学专家”等人类领域。路由和专家共同优化任务损失，最容易利用的分工可能是 token 频率、词形、位置、语法、数据来源或隐藏状态簇；负载均衡还会刻意把相似 token 分散。专业化必须通过干预和指标验证，不能只凭几个路由样例命名。

## 专业化如何产生

某类 token 早期略偏向 expert \(e\)，该 expert 便收到更多这类梯度，能力增强后 router 更愿意继续选择它，形成正反馈。Top-k 的稀疏性让未选专家得不到该 token 的任务梯度，更强化分工。但负载辅助损失、router noise、shared expert 和容量溢出又会打破纯语义聚类。

可从互信息角度测量 expert id 与语言、任务、token 类型、层位置等标签的关系；也可比较各 expert 被选择的分布、激活探针和梯度相似度。真正证据应包含因果消融：屏蔽/替换某 expert 后，哪些数据切片的 loss 特异性上升；仅看“某专家中文 token 多”可能只是训练语料频率或 tokenizer 造成。

## 层间差异与例子

早层 expert 可能按字符形态、标点和局部句法分工，中后层更可能按抽象语义或任务状态分工。同一个“python”token 在代码和自然语言上下文中隐藏状态不同，可能路由到不同专家，说明专家处理的是上下文化状态而非词表 id。

## 工程取舍与误区

过强专业化会使领域流量突增时单个专家过载，也降低容错；完全均匀且专家输出高度相似则浪费参数。最佳状态不是路由越可解释越好，而是在质量、负载、鲁棒性之间平衡。专家编号可交换，重训后“expert 7”没有固定语义。

面试回答应说清“优化诱导的统计分工，不是预设职业”，并给出分布统计加专家消融的验证方法。
