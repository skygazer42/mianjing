# 18. speculative decoding 如何与 KV Cache 协同？

## 结论

speculative decoding 让便宜 draft 模型先提出多个候选 token，再由 target 模型一次前向并行验证。两个模型各有自己的 KV Cache；target 对候选 chunk 会临时写入多个位置，只提交被接受的前缀，拒绝点之后的缓存必须回滚或标记无效。收益来自每次昂贵 target 调用接受多个 token。

## 一轮流程

1. draft 基于自己的 cache 自回归生成 (k) 个候选，并追加 draft KV。
2. target 从已确认前缀出发，一次处理候选 chunk，使用块内 causal mask，产生验证概率并暂存 (k) 个位置的 target KV。
3. 按算法接受前 (a\le k) 个 token，可能再从 target 分布采一个纠正 token。
4. target 有效长度只前进已提交数量；未接受 slot 回滚/覆盖。draft cache 也要回到确认序列并用纠正 token 对齐。

## 分配策略

可预留临时 blocks，验证后将接受部分 commit；若拒绝落在块中间，保留有效前缀并调整尾块长度即可，未用槽将来覆盖。block table 更新与采样状态必须原子化，不能先暴露新长度再决定接受。并发调度还需为最坏 (k) 个临时 token 留容量。

## 性能边界

若接受率低，draft 计算、target 多 token验证和回滚开销可能得不偿失；若 target 的 prefill-like verification kernel高效且一次接受多个 token，能降低 target 串行步数。KV 容量会短时包含 tentative tokens，吞吐规划不能只按最终 accepted tokens。

## 正确性与面试要点

speculative 算法应保持 target 分布不变（在相应采样规则下），cache 优化不能改变接受逻辑。测试无 speculation 与开启后的分布/固定随机结果、各种拒绝位置和跨 block。回答重点是“双 cache、临时写、接受 commit、拒绝 rollback”。
