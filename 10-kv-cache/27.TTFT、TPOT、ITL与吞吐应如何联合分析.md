# 27. TTFT、TPOT、ITL 与吞吐应如何联合分析？

## 结论

LLM 服务不能只看 requests/s。TTFT（time to first token）主要覆盖排队和 prefill；TPOT 常表示除首 token 外的平均每输出 token 时间；ITL（inter-token latency）描述相邻流式 token 间隔及其分布；吞吐可按 input/output/total tokens/s 报告。它们受 prompt/output 长度和并发强烈影响，必须联合给出。

## 指标关系

对输出 (N) 个 token，若定义一致，用户完成时间可粗略写为

\[
T_{e2e}\approx TTFT+(N-1)\cdot TPOT.
\]

但平均 TPOT 会掩盖抖动，交互体验更关心 p95/p99 ITL；chunked prefill 插队、cache block分配、抢占或网络 collective 都可能造成个别大间隔。吞吐提高常靠增大 continuous batch，却让每轮更长，从而恶化 ITL。

## KV Cache 的作用

prefix cache 命中减少 prefill，主要改善 TTFT；GQA/量化降低每步读取字节，通常改善 TPOT和容量；分页提高可接纳并发、减少 OOM，不保证单请求 kernel 更快；offload 扩容量却可能产生 ITL stall。把每项优化映射到指标，才能解释结果。

## 正确压测

固定并报告模型、硬件、input/output 长度分布、到达过程、并发、采样方式与 SLO。闭环压测中客户端等待响应后再发请求，会因服务变慢自动降低负载，掩盖排队；容量评估更应使用可控开环到达率。分别给出冷/热 prefix、短/长上下文与分位数。

## 常见误区

将总 tokens/s 包含大量 prefill token，与只报 output tokens/s 的系统横比不公平；把 `1/TPOT` 称为单请求生成吞吐时，也不能等同全服务 output tokens/s。平均值无法反映尾延迟与饥饿。

## 面试回答要点

先定义再关联阶段，给出近似完成时间公式，最后说明吞吐—延迟权衡与负载条件。这样比说“KV Cache 降低延迟”更可验证。
