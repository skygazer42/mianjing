# 05. 如何推导 KV Cache 的显存占用公式？

## 结论

密集、无额外元数据时，KV Cache 字节数由“层数 × K/V 两份 × 缓存 token 数 × KV 头数 × head dimension × 每元素字节”相乘：

\[
M=2\,L\,N_{tokens}\,H_{kv}\,D_h\,b.
\]

若每个 batch 都填满长度 (S)，则 (N_{tokens}=B S)；变长分页服务应使用所有请求实际缓存 token 总数，而不是 `B*max_len`。

## 逐项理解

每个 token 在每层产生 `Hkv*Dh` 个 K 元素和同样多 V 元素，所以有因子 2。BF16/FP16 的 (b=2) bytes，FP8/INT8 主数据为 1 byte，INT4 为 0.5 byte；量化还要加每组 scale、可能的 zero-point 和对齐 padding。block table、引用计数和 allocator metadata 通常较小，但 block 内部未用槽位会形成内部碎片。

## 另一种写法

MHA 中 (H_{kv}D_h=d_{model})，因此每 token cache 为 (2Ld_{model}b)。GQA 中若 query heads 为 (H_q)，共享比 (g=H_q/H_{kv})，容量约为 MHA 的 (1/g)。这也说明参数总量相近的两个模型，KV 容量可能因层数、KV heads 和 head dim 不同而差很多。

## 具体例子

32 层、8 个 KV heads、head dim 128、BF16：每 token 为 `2*32*8*128*2 = 131072` bytes，即 128 KiB。单请求 4096 token 约 512 MiB；16 个都满长约 8 GiB，未含 block 浪费与运行 workspace。

## 工程取舍与误区

显存预算还要扣除权重、CUDA graph buffer、临时 attention workspace 和碎片，不能把 GPU 总显存全部给 KV。beam 的逻辑 token 可能共享前缀，不一定按 beam 数完整乘；prefix cache 也会以物理唯一块计数。

## 面试回答要点

现场先写通用公式，再代入 dtype 与 GQA；最后明确 MB/MiB 单位和额外开销。最常见错误是漏掉 K/V 的 2，或使用 query head 数高估 GQA。
