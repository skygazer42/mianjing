# 24. 张量并行下 KV Cache 如何分片？

## 结论

attention 做 head-parallel 张量并行时，通常把 query heads 和 KV heads 分到各 TP rank，每张卡只保存本地 attention 所需的 K/V 分片，避免复制完整 cache。输出投影前后再通过 collective 合并。GQA/MQA 的 KV heads 很少，可能无法均匀除以 TP 度，需要复制、重新分组或采用更复杂的分片。

## MHA 情况

若 `Hq=Hkv=32, TP=4`，每卡处理 8 个 Q/K/V heads，cache 容量约为单卡全量的 1/4。每卡本地 Q 只与本地 K/V heads做 attention，得到局部 head 输出；合并输出投影常配 row-parallel all-reduce/reduce-scatter。cache 不必在每个 decode step跨卡交换整段历史。

## GQA/MQA 难点

若 `Hq=32,Hkv=8,TP=4`，每卡 8 Q heads、2 KV heads，天然均匀。若 `Hkv=1,TP=8`，单 KV head不能按 head 轴分成 8 份而仍让每卡独立做完整点积；常见方案是在 ranks 复制该 KV head，物理 cache 总量因此高于公式按全局 `Hkv/TP` 的理想值，或切 head_dim 并增加 attention 通信，通常不划算。

## 分页与元数据

各 rank 可有相同逻辑 block table，但物理 block池和每块内容是本地 head 分片；分配/释放决策需一致，防止某 rank 成功、另一个失败。prefix cache key 全局一致，引用计数和 block id 可以本地对应而非数值完全相同。

## 容量与容错

预算应按每卡实际 KV heads（含复制）计算，最小剩余容量的 rank 决定可接纳 token。更改 TP world size 加载正在运行的 session 很困难，因为 cache layout需重新分片；通常只在请求边界伸缩。

## 面试回答要点

先讲 MHA 按 head 分片，再用 `Hkv<TP` 解释 MQA 复制难题。不要说张量并行一定把 KV 显存严格除以 TP，GQA 与物理布局可能打破理想倍率。
