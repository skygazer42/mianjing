# 29. KV Cache 常见正确性 bug 如何定位？

## 结论

KV Cache bug 常表现为首 token 正常、后续逐渐乱码，或 batch size 1 正常而并发串话。最有效方法是建立无 cache 的 full-forward 参考，与 cached 增量在每层、每位置逐步对齐，再针对 position、写入 slot、长度、block table 与 beam/speculative 状态做二分。

## 基线测试

固定 dropout 关闭与确定性采样。对短序列一次 full forward，记录每个位置 logits；再从相同 prompt 逐 token运行 cache 路径，对应位置 logits 应在 dtype 容差内一致。先在 FP32、batch 1、连续 cache 对齐，再依次打开 RoPE、GQA、分页、变长 batch、量化和融合 kernel，找到首次偏离的特性。

## 常见根因

- position off-by-one：新 token 使用 `len-1` 或因左 padding 取了列索引。
- K 写入前后 RoPE重复/漏应用，或历史与新 token base 不同。
- `seq_len` 先更新后取 slot，产生空洞；kernel读取了预留未写区域。
- block 边界 `//`、`%` 或 table row错，释放块过早被别的请求覆盖。
- GQA head mapping、K/V axis/stride 错；beam reorder只换 token未换 table。
- speculative拒绝后长度或尾块未回滚；量化 scale 对错 token/group。

## 隔离技巧

把其他请求物理块填入明显 sentinel，确认当前输出不受影响；在每个 block 边界前后生成；取消请求后立刻复用其块压测；对 K/V 写后做小范围 checksum，并记录 `(request,layer,logical_pos,physical_block,offset)`。发现第一个错误层比只看最终文本有效得多。

## 面试回答要点

回答成“full vs cached golden→逐特性开启→首个偏离层→状态映射日志”。常见误区是只降低 temperature观察文本，生成随机性会掩盖数值错误，应该直接比较 logits/KV。
