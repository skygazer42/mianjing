# 26. 多租户服务如何做 KV Cache 容量与隔离？

## 结论

多租户系统既要防一个租户的超长/高并发请求耗尽 KV 池，也要防 prefix/cache 元数据造成跨租户信息泄漏。应在 admission、block allocator、prefix namespace、优先级与监控五处实施配额和隔离，而不是只设单请求 `max_tokens`。

## 容量控制

可为租户设置最大并发 sequences、总 resident KV tokens、每请求上下文/输出上限和 prefill token rate；全局保留 emergency watermark，避免所有块分完后无法完成进行中的下一步。软配额允许空闲时借用，压力下按优先级回收；硬配额提供更强 SLA 隔离但降低总体利用率。

## prefix cache 安全

跨请求共享 prefix 前必须确认租户/权限策略。即便只按 token hash 查找，命中时序、驻留状态也可能构成侧信道；敏感场景应按 tenant 或安全域分 namespace，加盐哈希并校验完整 token 与模型配置。释放块时数学上无需清零，只要映射绝不越界，但合规要求可能要求安全擦除或加密。

## 调度公平

高优请求可低延迟，但需 aging/最低服务份额避免低优饥饿。超长 prefill 用 chunk budget限流，decode 用每轮份额；抢占时优先淘汰可重算的非活跃 prefix，而不是破坏正在生成的高价值会话。恶意取消/重试也要限速，防止 allocator 抖动。

## 可观测性

按租户记录 active/resident tokens、prefix hit tokens、block waste、queue time、preemption、OOM拒绝与 p99 TTFT/TPOT。总利用率正常可能掩盖单租户长尾，必须带租户与优先级维度。

## 面试回答要点

回答覆盖“token/block 配额、watermark、调度公平、prefix 命名空间、安全释放”，说明 KV Cache 不只是性能资源，也含由用户输入派生的敏感状态。
