# 25. 流水线与跨节点推理中 KV Cache 放在哪里？

## 结论

流水线并行把连续 Transformer 层放在不同 stage，因此每个 stage 只保存其本地层的 KV Cache；token 隐藏状态沿 stage 传递，历史 KV 不应每步跨节点搬来搬去。跨节点部署的核心是让 cache 与计算该层的权重共置，并让所有 stage 对请求生命周期、逻辑长度和调度顺序保持一致。

## 数据流

假设 40 层分 4 个 stage，每个保存 10 层权重与对应 cache。新 token 经 stage 0 计算/追加前 10 层 KV，传隐藏状态到 stage 1，依次完成。单 token传输的是 `[microbatch,d]` 激活，而非整个历史 cache；若把层计算迁移到另一节点，相关 cache 也必须迁移或重算。

## 调度与气泡

自回归 token 存在顺序依赖，但可用多个请求/micro-batch 填流水线。各 stage 必须以一致 sequence id 查自己的 block table；请求取消、beam reorder、speculative commit 需要控制面广播到所有 stage，释放操作要幂等。某 stage 显存较小或本地层 KV 更大，会成为全系统容量短板。

## 跨节点风险

网络抖动会放大每 token延迟，pipeline stage 太多会增加串行 hop。远程 KV store 更适合会话暂停、prefix cache 交换或故障恢复，不适合每层每 token同步读取全部历史。故障后只恢复权重不够，进行中请求的 cache 与采样状态也要恢复；很多系统选择终止/重算请求以简化一致性。

## 与 tensor parallel 组合

每个 stage 内可再用 TP 切 heads，形成 PP×TP；cache 先按层归 stage，再按 KV heads归 TP rank。容量公式需按各设备局部分片计算，不能只用全局总字节平均。

## 面试回答要点

一句话是“KV 跟层走、激活跨 stage、控制状态全局同步”。再讨论迁移/故障与最小容量 rank，能体现跨节点系统视角。
