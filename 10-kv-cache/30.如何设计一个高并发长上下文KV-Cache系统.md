# 30. 如何设计一个高并发长上下文 KV Cache 系统？

## 目标与结论

设计应从 SLO 与长度分布反推，而不是先堆优化名词。核心架构是：按模型结构精确计算每 token KV 字节；用固定块池与 block table管理变长序列；连续批处理统一 prefill/decode 调度；再按瓶颈加入 GQA、prefix cache、量化、chunked prefill、抢占/offload。所有优化必须由容量、TTFT、ITL 和质量指标闭环验证。

## 容量层

先从 GPU 显存扣权重、workspace、graph/通信 buffer 和安全水位，余量除以 (2LH_{kv}D_hb) 得物理 token budget。选择 block size并用线上长度分布模拟尾块碎片。allocator维护 free list、refcount和不可变共享块；每请求持有逻辑长度、block table、position与状态机。

## 调度层

admission 在运行前原子预留 prompt chunk/下一步所需块。iteration-level continuous batching移除完成请求、加入新请求；先保障 decode ITL，再用剩余 token budget安排 chunked prefill。压力下按 SLA选择等待、淘汰非活跃 prefix、recompute、swap或抢占，并用 aging防饥饿。

## 优化层

高重复系统提示词用严格 key 的 prefix caching与 COW；长上下文带宽瓶颈用原生 GQA kernel和经质量验证的 KV8/KV4；暂停会话可 offload，活跃全局 attention cache尽量留 GPU。TP 下按 KV heads分片，PP 下 cache 跟层共置。不要用物理 slot充当逻辑 position。

## 正确性与安全

建立 full=cached、batch=单请求、prefix hit=miss、speculative commit/rollback 的 golden tests；多租户按安全域隔离 prefix namespace和配额，取消/异常释放必须幂等。版本 key 包含模型、adapter、tokenizer/模板和位置配置。

## 观测与降级

监控 free/used/shared/wasted blocks、resident tokens、cache hit tokens、preemption/swap、TTFT/ITL/TPOT 分位数和量化质量回归。达到低水位时按明确顺序降级，而不是等 CUDA OOM。

## 面试回答要点

建议按“算容量→分页分配→持续调度→复用压缩→并行部署→测试监控”六步回答，并主动说明每种优化解决的是容量、带宽、计算还是调度中的哪一个瓶颈。
