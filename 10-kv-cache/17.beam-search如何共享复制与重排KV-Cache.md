# 17. beam search 如何共享、复制与重排 KV Cache？

## 结论

beam search 从同一前缀扩出多个候选。分叉前的 KV 完全相同，应共享而不是按 beam 数复制；分叉后的新 token 各自产生不同 KV，需要独立追加。每轮 top-k 选择会重排、复制或删除 beam，cache 的 block table 必须按 parent beam 索引同步更新。

## 状态演化

初始 prompt prefill 一份 cache。第一轮选出 (B) 个 token 时，可以让 (B) 条 beam 的 table 都引用公共完整前缀块；若尾块未满且各 beam 要写不同 token，触发 COW 或各自分配尾块。下一轮候选通常有 `B*vocab` 分数，选出的新 beam 记录 parent id，例如 `[2,0,2,1]`，新 tables 也应从对应 parent 派生，而非按当前位置原地假设一一对应。

## 共享与容量

理想物理占用约为“一份公共 prefix + 各分支独有 suffix”，而不是 `beam_size * total_length`。引用计数确保 parent 被多个孩子选中时块不被提前释放；未被选择的 beam 独有块及时回收。块级共享在分叉落于尾块中间时会有 COW 粒度浪费。

## 常见 bug

只重排 token/score 而没重排 cache 会让文本突然混入其他 beam；对 `past_key_values` 做物理 gather 虽正确却带来巨大拷贝；重复 parent 的 shallow copy 若共享可写尾块会互相覆盖。EOS beam 可保留为完成候选，不应继续无意义追加 cache。

## 与采样并发区别

返回多条独立采样也可共享 prompt，但分支无需每轮全局 top-k 重排，状态更简单。beam length penalty 只影响评分，不改变 cache token 顺序。

## 面试回答要点

用 parent 索引例子解释 table 重排，说明 prefix refcount 与尾块 COW。不要只回答“把 batch 扩成 beam_size 倍”，那是最直观但最浪费的实现。
