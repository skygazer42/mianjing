# 22. chunked prefill 如何平衡 TTFT 与 decode 延迟？

## 结论

chunked prefill 把一个长 prompt 的 prefill 拆成多个 token chunk，分多轮与已有请求的 decode token 混合执行。它避免一次长 prefill 独占 GPU、造成其他用户 inter-token latency 尖峰，并可让调度器按 token budget 填满每轮；代价是更多调度/内核开销，单请求 TTFT 未必降低。

## 工作方式

假设请求有 32k prompt，而每轮 prefill budget 为 2048 token。调度器连续处理 16 个 chunk，每个 chunk 读取此前 chunk 建立的 KV 作为前缀，并追加本 chunk KV；本 chunk 内各 query 需 causal，且可见所有已完成 prefix。与一次 full prefill 相比，数学结果应在容差内一致，不能把 chunk 当互相隔离样本。

## 与 decode 共调度

一轮可先保障活跃 decode 请求每个一个 token，再用剩余 token/计算预算填 prefill chunks。decode 对延迟敏感但单 token计算小，prefill 提供大矩阵提高利用率，二者混合可平衡吞吐与 ITL。若 prefill chunk 太大，仍会阻塞 decode；太小则 GEMM 低效、重复调度与 kernel launch 增多。

## cache 与 attention 成本

每完成一个 chunk 就提交其 KV blocks，取消请求时可释放。对第 (c) 块做 attention 仍要读取之前 prefix K/V，整体精确 attention FLOPs 不会神奇变线性；实现可用 prefix-aware/varlen kernel。容量调度需在执行前为整个 chunk 的新 KV 预留块，防止中途 OOM。

## 指标与选择

应同时画 TTFT、p50/p99 ITL、prefill tokens/s、decode tokens/s 随 chunk size 和并发的曲线。SLA 优先系统常选较小上限，离线吞吐可选更大 chunk。prefix cache 命中后只需对未命中 suffix 分块。

## 面试回答要点

说清“拆长 prompt、跨 chunk 复用 KV、与 decode 交错、chunk 大小权衡”。不要说 chunked prefill 必然降低该长请求 TTFT，它主要防止其他请求被头阻塞并改善全局调度。
