# 20. KV Cache offload 与分层存储如何设计？

## 结论

KV offload 把暂时不活跃或较冷的 cache 从 GPU 搬到 CPU pinned memory、其他 GPU、NVMe 或远端缓存，需要时再预取。它扩大可承载会话和 prefix 的总容量，但每个 decode token 都依赖所需历史 KV；若热路径频繁跨 PCIe/网络读取，延迟通常无法接受，因此关键是分层、预测和异步重叠。

## 哪些数据适合下沉

暂停/排队会话、低命中 prefix cache、即将被抢占的长请求适合整段 offload；正在每轮 decode 的请求需要每层扫描历史，通常应把其工作集留在 GPU。滑窗模型可让远古块不再被读取并直接淘汰，而全局 attention 即使旧块也可能每步需要，简单冷热假设更难成立。

## 成本模型

迁移时间近似 `bytes / effective_bandwidth + latency`。若一个请求有数 GB KV，经 PCIe 搬回可能比重新 prefill 短前缀慢；系统应比较 swap 与 recompute 成本。可以分 layer/blocks 预取，在计算前层时异步搬后层数据，但需要双缓冲并避免占满 PCIe 影响其他请求。

## 一致性与元数据

block 状态至少包含 GPU-resident、CPU-resident、in-flight 与 free；迁移中不能被重分配或同时写。block table 可保存层级位置，调度器在运行前确保所需块 ready。量化后再 offload可减带宽，但恢复时增加反量化；不同层级还要校验模型版本与租户权限。

## 适用目标

offload 常改善可接纳请求数、会话恢复和低优先级吞吐，不一定改善单请求 TPOT。必须监控 hit rate、迁移字节、stall 时间、recompute 时间和链路利用率，并设 admission 防止抖动式反复换入换出。

## 面试回答要点

从“热活跃留 GPU、冷/暂停下沉、预取重叠、swap vs recompute”回答，并指出全局 attention 的历史每步都可能是热数据，避免把它类比成普通不常访问页面过度简单化。
