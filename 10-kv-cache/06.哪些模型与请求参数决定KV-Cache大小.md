# 06. 哪些模型与请求参数决定 KV Cache 大小？

## 结论

KV Cache 容量由模型结构、精度/压缩策略和运行请求共同决定。模型侧关键是 attention 层数 (L)、KV heads (H_{kv})、head dimension (D_h)；请求侧关键是所有活跃及可复用前缀的实际 token 数；存储侧是每元素位宽、量化元数据、block 大小和复制/共享策略。

## 模型因素

层数线性增加 cache；hidden size 只有通过 `Hkv*Dh` 间接决定，不能看到 7B/70B 参数就直接推 cache。GQA/MQA 可让 (H_{kv}\ll H_q)，显著省容量。cross-attention 模型还可能缓存源端 K/V，且 self/cross cache 生命周期不同。滑窗 attention 层若实现上只保留窗口，可限制这些层长度；全局层仍需完整历史。

## 请求因素

对每个请求，缓存 token 包括 prompt、已生成但仍保留的 token，以及可能预留但未用的块槽。并发数与长度分布比单一 `max_seq_len` 更重要：100 个 1k 请求与 10 个 10k 请求 token 总数相同，但调度、碎片和 kernel 行为不同。beam/speculative 分支可能共享前缀、暂存候选或回滚，物理占用不能仅看最终输出长度。

## 系统因素

BF16 到 INT8 理想上主数据减半，但 group scales、对齐和热层保留高精度会降低实际比例。PagedAttention 的 block size 越大，page table 越小、访问更规整，却增加尾块内部碎片；block 越小则元数据和寻址开销更高。prefix cache 延长块生命周期，提升命中率同时挤占新请求容量。

## 容量规划

用 `可用于KV的字节 / 每物理token字节` 得到 token 容量，再乘安全系数而非直接承诺满载。根据线上 prompt/output 分位数模拟 admission、取消和缓存命中，观察 OOM 与尾延迟。

## 面试回答要点

按“模型—请求—存储/分配器”三层罗列，并强调物理唯一 token 与逻辑 token 的区别，比只背一条公式更全面。
