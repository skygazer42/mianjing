# 07. 增量追加 KV 时如何保证 causal attention 正确？

## 结论

增量 decode 的当前 query 只能读取该请求的历史 token 与当前 token，不能读未来预留槽、其他请求或已回滚候选。正确性依赖逻辑长度、block table、position id 和 mask 同步更新；物理内存里存在数据不代表它应当可见。

## 基本步骤

对请求当前有效长度 (t)：先为新 token 分配逻辑位置 (t) 对应槽，计算并写入 (k_t,v_t)，再令 query (q_t) 的可见 KV 长度为 (t+1)。在纯单 token decode 中，传给内核的 cache 只有前 (t+1) 项，causal 条件可由长度天然满足；在一次验证多个 speculative token 或 chunked decode 时，query 长度大于 1，块内仍需要三角 causal mask。

## 多请求隔离

paged kernel 必须按每请求 block table 取块，不能假定物理块连续。块被释放并复用前，旧数据无需清零即可保证数学安全，前提是长度和 table 绝不引用越界；安全隔离要求 allocator 也不能把同一可写块同时分给无共享关系的请求。

## position 与 RoPE

当前 token 的逻辑 position 通常为历史有效 token 数，但左 padding、共享 prefix、滑窗和多模态前缀可能改变规则。K 在写 cache 前按该 position 旋转；若 position 与长度错一位，mask 仍可能正确却生成退化。接受 speculative 前缀后应只提交被验证 token，拒绝部分的 cache slot 要回滚/覆盖。

## 测试与误区

比较 full forward 和逐步 cached logits；把其他请求 cache 填成极大随机数，确认本请求输出不变；测试 block 边界、取消复用、变长 batch 与多 token decode。常见错误是先把 `seq_len` 加一又用它作为写下标，造成空洞或错一位。

## 面试回答要点

按“写槽—可见长度—请求映射—position—提交/回滚”讲完整状态机，体现 cache 正确性不只是一个下三角 mask。
