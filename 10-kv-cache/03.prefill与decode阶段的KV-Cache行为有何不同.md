# 03. prefill 与 decode 阶段的 KV Cache 行为有何不同？

## 结论

prefill 一次处理整个 prompt，为每层批量生成并写入 (S) 个位置的 K/V；decode 每轮通常每请求处理一个新 token，只追加一个位置并读取既有全部缓存。前者以大矩阵、长序列 attention 为主，常偏计算密集；后者反复运行小矩阵并扫描缓存，常偏显存带宽与调度受限。

## prefill 路径

输入形状 `[B,S,d]`，各层同时计算所有 Q/K/V，在 causal mask 下得到所有 prompt 位置输出。虽然只需最终位置 logits 来开始生成，前层每个 prompt token 的隐藏状态都是后层 K/V 的输入，因此不能只算最后一个 token。写 cache 时通常批量分配足够 block，再把 K/V 按逻辑 token 映射到物理槽。

prefill 成本随 prompt 长度增长，标准 attention 有 (O(S^2d)) 项；FlashAttention 可减少中间 IO，却不消除二次 FLOPs。它主要影响 TTFT 和 prompt tokens/s。

## decode 路径

每个请求输入 `[1,d]`，产生当前层新 K/V，写入一个 slot；新 Q 对长度 (S+t) 的 cache 做 attention。不同请求长度不同，paged/varlen kernel 借 block table 与长度元数据读取。decode 逐 token 有数据依赖，服务通过连续批处理合并多个请求的当前步，提高吞吐。

## 调度冲突

长 prefill 会占用大量计算并阻塞已经在 decode 的请求，拉高 inter-token latency。chunked prefill 把 prompt 切块，与 decode token 交错调度；代价是多次调度、边界状态与可能稍低的纯 prefill 效率。

## 面试回答要点

从“批量写很多 KV vs 读历史并追加一个 KV”“计算密集 vs 带宽/调度密集”“TTFT vs TPOT”三组对比回答。不要说 KV Cache 只在 decode 才创建：prompt 的 cache 正是在 prefill 中建立。
