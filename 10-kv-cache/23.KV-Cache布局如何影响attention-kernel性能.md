# 23. KV Cache 布局如何影响 attention kernel 性能？

## 结论

decode 常受 KV 读取带宽限制，逻辑元素相同但物理轴顺序、block 大小、对齐和量化元数据布局会显著影响合并访存与向量化。优秀布局让同一 warp 访问连续 K/V、减少地址计算，并与 GQA、paged block 和目标 attention kernel 的 tile 匹配。

## 访问模式

对一个 query head，QK 阶段遍历历史 token并对 `head_dim` 做点积；随后以概率加权 V。若 `head_dim` 是最内层连续轴，向量 load 方便；某些内核为 K 点积采用转置/向量分块布局，而 V 保持 token-major。不能只看 shape，stride 才决定相邻线程是否读取相邻地址。

分页布局常见逻辑为 `[num_blocks, block_size, Hkv, Dh]`，也可能按 `[num_blocks,Hkv,Dh/x,block_size,x]` 重排以满足 16-byte/128-bit load。block size 需配 kernel tile：过小导致表查找频繁，过大加剧尾部浪费并可能降低调度灵活性。

## GQA 与量化

GQA 应让多个 Q heads复用同一 KV 读取，尽量通过共享内存/寄存器减少重复 HBM load；若内核为每个 Q head独立加载，理论缓存节省未完全转成带宽收益。量化 scale 最好与数据共同连续访问并融合反量化，per-token/per-channel 粒度会改变访存方向。

## 写入与读取取舍

prefill 写 cache 偏好连续批量 store，decode 读取偏好特定 tile；可在写入时直接转成 decode-optimal layout，避免每步转换，但会让 prefill 写复杂。K/V layout版本必须进入 checkpoint/runtime metadata，不能跨内核误解释同一 buffer。

## 评测与回答要点

用真实长度分布测 GB/s、TPOT、kernel occupancy 和地址查找开销，而不是只测峰值 FLOPs。回答时提到 shape、stride、对齐、GQA 复用与融合反量化，说明性能瓶颈在数据移动。
