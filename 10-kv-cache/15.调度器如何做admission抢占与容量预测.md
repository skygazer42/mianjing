# 15. 调度器如何做 admission、抢占与容量预测？

## 结论

在线推理调度器必须在执行前确认 cache 能容纳下一轮需要的物理块，并在容量紧张时选择等待、抢占、swap 或丢弃低价值缓存。只按当前已用 token admission 会过度乐观，完全按每请求最大输出预留又极度浪费，因此通常结合每轮安全分配、长度估计和优先级策略。

## admission

新请求至少需要 prompt prefill 的块和下一步 decode 空间。调度器可设总 token/block budget、最大并发序列和最大本轮计算 token。对输出长度未知，可使用用户 `max_tokens` 作为硬上限、历史分布作软预测，但仍要保证增长时有失败处理，不能让 GPU kernel 内直接 OOM。

## 抢占策略

容量不足时可：暂停请求但保留 cache；释放其 cache，稍后从 token 序列重算（recompute）；把块 swap 到 CPU/更慢层级；或优先淘汰可重新构建的 prefix cache。选择取决于 cache 大小、PCIe 带宽、已计算前缀成本和 SLA。重算短前缀可能比传输大量 KV 更快，长前缀则相反。

## 公平与优先级

策略可按到达时间、剩余长度估计、业务优先级或 deadline 排序。Shortest-job-first 提高平均延迟却可能饿死长请求；严格优先级会让低等级长期无服务。可加入 aging、每租户配额和最大连续占用轮数。

## 一致性状态机

只有在 block 分配成功后才能提交新 token 长度；失败时不得让 tokenizer 输出、position 或采样 RNG 前进。取消、异常和 speculative rollback 要幂等释放。监控 free blocks、reserved blocks、preemptions、recompute tokens、swap bytes 与 admission wait。

## 面试回答要点

把问题回答成“容量预测—原子预留—紧张时策略—公平—可观测性”。常见误区是把 max context 全量预分配当唯一安全方法，分页与迭代调度正是为了避免这种浪费。
