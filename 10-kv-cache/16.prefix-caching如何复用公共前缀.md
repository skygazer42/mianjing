# 16. prefix caching 如何复用公共前缀？

## 结论

prefix caching 把已经 prefill 的公共 token 前缀对应 KV blocks 保留下来；后续请求若 token 序列及所有影响隐藏状态的配置一致，可直接引用这些块，只对未命中 suffix 做 prefill。它降低重复 TTFT 与计算，但占用长期 KV 容量，需要可靠 key、块级匹配和淘汰策略。

## 命中条件

key 至少应覆盖完整 token ids（不是原始字符串）、模型与权重版本、LoRA/adapter、位置/scaling 配置、可能影响前向的模态输入及模板。相同文本若 tokenizer 版本或 chat template 不同，token 前缀就不同；相同 token 若 adapter 不同，各层 K/V也不同。随机采样参数不影响已确定前缀 hidden，可不进入 key，但模型前向相关参数必须进入。

## block 级哈希

通常按完整 block 建链式哈希：当前块 hash 包含前一块 hash 和本块 tokens，使只有从序列开头连续匹配的块才能复用。命中后请求 block table 指向已有只读物理块并增加 refcount；最后不满块可不缓存，或封存后用 COW 处理追加。

## 容量与淘汰

缓存块与活跃请求争同一显存池。可按 LRU/LFU、重算成本、租户配额或前缀长度决定淘汰，且只能回收 refcount 为 0 的非活跃 cache 条目。高命中系统提示词值得保留，低复用的长用户文档可能挤占更多并发。

## 安全与观测

多租户下不能让 hash 碰撞或权限错误导致跨租户内容复用/侧信道；可分命名空间并验证 token。监控 hit tokens 而不只 hit requests，因为命中 1 个 block 与 10k token 价值不同，还应统计节省 prefill 时间与缓存驻留字节。

## 面试回答要点

说清“token 级严格一致、完整配置 key、块引用共享、refcount、淘汰”，并强调它复用的是逐层 KV，不是直接复用最终答案。
