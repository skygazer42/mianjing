# 13. KV block table 与 copy-on-write 如何工作？

## 结论

block table 为每个请求记录“第几个逻辑 token block 存在哪个物理 block”。多个请求或 beam 可让表项指向同一只读前缀块，并用引用计数管理生命周期；当某分支要修改一个仍被共享的块时执行 copy-on-write（COW），复制后再写，既节省公共前缀又避免相互污染。

## 映射与引用计数

请求 A 的 table 可为 `[5,9,12]`，请求 B 与它共享前 32 token，table 为 `[5,9,21]`。物理块 5、9 的 refcount 是 2。A 完成时只把 refcount 减一，不能立刻回收；降到 0 才回 free list。table 顺序定义逻辑位置，物理编号无需递增。

## 为什么尾块需要 COW

若共享前缀长度恰好落在完整 block 边界，后续分支各分配新块即可。若共享结束在一个未填满 block 中，而 A、B 都要在该尾块追加不同 token，它们不能同时写共享块。写入前检查 refcount：大于 1 就分配新块、复制已有有效槽、更新当前请求表项并减少旧引用，再写新 token。

## 并发与一致性

分配、refcount、table 更新必须有清晰原子性或由单一调度线程串行化，GPU kernel 只能看到一个一致快照。speculative rollback、beam prune、请求取消都要按实际拥有的 table 条目递减引用；重复释放会让正在读取的请求遭遇 use-after-free，漏释放则形成显存泄漏。

## 哈希前缀缓存

跨请求复用常按 token block 的链式哈希查找，key 还需包含模型/adapter、位置与相关配置。命中只代表 token 内容匹配，最后一个部分块通常不进入全局可共享 cache，或需不可变封存，避免 COW 复杂度。

## 面试回答要点

画出两个 table 共享 `[5,9]` 的例子，解释 refcount 与尾块 COW，再说取消/回滚的生命周期。不要把 COW 说成每次读取都复制，它只在共享块发生写入时触发。
