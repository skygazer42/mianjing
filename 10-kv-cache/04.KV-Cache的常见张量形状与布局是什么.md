# 04. KV Cache 的常见张量形状与布局是什么？

## 结论

逻辑上单层 K 或 V 可表示为 `[batch, kv_heads, sequence, head_dim]`，整个模型再加 layer 维；实际内核也常用 `[batch, sequence, kv_heads, head_dim]` 或分页 `[num_blocks, block_size, kv_heads, head_dim]`。判断显存与正确性时看各维含义，不能依赖某个框架的固定排列。

## 各维定义

- `layers = L`：每个 attention layer 各有 K 与 V。
- `batch/sequence`：更准确说是所有活跃请求已缓存 token 的总和；分页后不一定有规则 batch 维。
- `kv_heads = H_kv`：MHA 等于 query heads，GQA/MQA 更少。
- `head_dim = D_h`：单个 K/V head 的通道数。
- 最前面的因子 2 表示 K、V 两份张量。

连续布局可概念化为 `[2,L,B,Hkv,S,Dh]`。分页布局把 `B,S` 映射成物理 block 与 block 内 offset，并用每请求 block table 恢复逻辑顺序。

## 布局为何重要

decode 内核遍历历史 token 并对 head_dim 向量做点积/加权，连续访问哪个轴会影响内存合并、向量化和 cache line 利用。把 K 以适合 QK 点积的向量块存储、V 以适合概率加权的布局存储，有些系统甚至让 K、V 采用不同排列。量化后还要附带 scale/zero-point 维度。

## 常见错误

Q heads 与 KV heads 混用会把 GQA 缓存高估或错误重复；transpose 后直接写非连续 view 可能打乱 token；beam reorder 只改 batch 索引却没同步 block table 会串请求。不同库输出的 `past_key_values` 层级和轴序不同，迁移时应打印 stride 而不只打印 shape。

## 面试回答要点

先给逻辑 `[L,2,B,Hkv,S,Dh]`，说明真实布局可换轴或分页，再解释 Hkv 而非 Hq 决定容量。能同时说出 shape 与 stride/访问模式，才是工程上完整的回答。
