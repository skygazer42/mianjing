# 11. 连续预分配 KV Cache 为什么会浪费和碎片化？

## 结论

若为每个请求按声明的最大长度预留一段连续 KV 空间，实际生成常远短于上限，未使用槽位造成内部浪费；若按需扩展连续数组，又可能需要搬迁或找不到足够大的连续区，造成外部碎片。请求长度不可预测、到达/结束异步，使传统连续分配难以同时做到高利用率与低延迟。

## 两种浪费

内部碎片是“已分配块内没用完”。例如每个请求上限 32k，实际只用 2k，预分配后约 94% 槽位闲置却不能给别人。外部碎片是总空闲量足够，但散落在很多小洞中，无法满足新的大连续段。若增长时像动态数组一样扩容复制，KV 数据按层和 token 很大，搬迁会消耗显存带宽并制造延迟尖峰。

## 为什么普通 batch tensor 不够

把变长请求 pad 到 batch 最大长度会使短请求为长请求买单，而且请求会在不同 decode iteration 完成，batch 形状不断变化。静态 tensor 适合离线同长度批处理，不适合在线连续批处理。输出上限也只是安全限制，不是可准确预知的实际长度。

## 分页思路

将物理 KV 池切成固定 token 数的 blocks，请求通过 block table 把逻辑块映射到任意物理块。增长只需再拿一块，无需整段连续；完成后逐块归还。内部浪费最多集中在每条序列最后一个未满 block，外部碎片基本转化成任意可用块问题。

## block 大小取舍

block 大则 table 小、寻址和 kernel 更规整，但平均尾部浪费接近半块，抢占/共享粒度粗；block 小则利用率高，却增加元数据、地址查找和内核碎片。应结合每 token KV 字节、长度分布和 kernel 支持压测。

## 面试回答要点

区分内部与外部碎片，说明长度未知与异步生命周期为何放大问题，再自然引出固定块分页。不要说分页完全没有浪费，它仍有尾块与元数据开销。
