# 14. continuous batching 如何提升 decode 吞吐？

## 结论

传统静态 batching 要等整批请求全部完成，短请求结束后其槽位空转；continuous batching 在每个或若干 decode iteration 边界移除已完成请求、插入新请求，让 GPU 始终聚合尽可能多的当前 token。它把 batch 从固定张量变为动态序列集合，显著提高 decode 权重读取和 kernel 启动的摊销效率。

## 迭代级调度

一轮中，每个 running 请求通常贡献一个新 token；调度器根据 cache 可用块、token budget 与优先级组成 batch，模型执行一次 forward，采样结果后更新各请求长度。EOS/取消请求立即释放或降级其块，新 arrival 可在下一轮进入 prefill 或 decode，而不必等待最长请求。

## 为什么提高吞吐

decode 单请求矩阵乘很小，读取同一层权重的成本占主导。把 (B) 个请求当前 token 合并，可让一次权重读取服务更多 token、提高 GEMM 尺寸和 GPU 利用率。Paged KV 允许每个请求长度、物理块位置不同，内核通过长度与 block table 做 ragged attention。

## 延迟取舍

追求大 batch 会延迟刚到请求并增加每轮执行时间，改善总 tokens/s 却可能恶化 TTFT/ITL。调度器常设置最大 batch tokens、decode 优先级或 SLA 队列；prefill 很长时采用 chunked prefill，避免一个请求占满整轮。公平性还要防止长请求或低优先级请求长期饥饿。

## 状态要求

每请求维护 sampling state、逻辑长度、block table、position、停止条件和随机数状态。batch 中的行顺序每轮可变，不能用固定 row index 绑定 cache；必须通过 request id/sequence id 映射。

## 面试回答要点

核心是“iteration-level 入队出队 + ragged cache + 合并当前 token”。不要把 continuous batching 等同于动态 batching：后者常只是在请求进入执行前短暂凑批，执行中未必能替换已完成序列。
