# 30. 长上下文 RoPE scaling 应如何评估与选型？

## 结论

选型不能只看目标长度是否“不报错”或单一 needle 命中率。需要同时衡量原长度质量、不同长度与位置的语言建模/检索能力、真实长文任务、训练成本和服务性能，再根据是否允许继续训练选择线性 PI、NTK-aware、YaRN、非均匀 scaling 等方案。

## 评估矩阵

长度轴至少覆盖原窗口内、刚越界、目标长度的 25%/50%/100%；位置轴把关键信息放在开头、中间、结尾并改变 query 位置；任务轴包含 token 加权 PPL、passkey/needle、多 needle 干扰、长文 QA/摘要、代码仓库理解和短对话回归。合成检索能验证寻址，却不能代表跨段推理和事实整合。

## 公平对比

固定同一 base checkpoint、长上下文微调 token、数据混合、优化步与 attention kernel。报告 scaling 的完整配置：原始最大长度、目标 factor、base、rotary dimension、attention factor 与库版本。若一种方法用了长训练而另一种零样本，结论应明确说明，不能只归因于算法名称。

## 系统指标

测 TTFT、prefill tokens/s、峰值显存、KV 容量与不同并发下 TPOT。RoPE scaling 本身不会降低 (S^2) prefill 计算或线性增长的 cache；能到 128k 的模型若服务只能容纳一个请求，业务价值可能有限。还要验证 fused kernel、tensor parallel 和 prefix cache 是否支持该 rope type。

## 选择原则

无继续训练预算时，优先尝试与原 checkpoint 生态验证充分且短程回归小的配置；可少量长微调时，PI/YaRN 等可系统适配；追求极端长度且有搜索预算时才考虑复杂非均匀方案。任何方案上线前都需 full/cached 一致性与真实数据压测。

## 面试回答要点

回答成“质量矩阵 + 公平控制 + 系统成本 + 训练预算”的决策流程。最常见误区是把 context window 当单一布尔能力，而它实际上是随长度、位置和任务连续退化的曲线。
