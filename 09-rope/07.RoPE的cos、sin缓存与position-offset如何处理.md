# 07. RoPE 的 cos、sin 缓存与 position offset 如何处理？

## 结论

cos/sin 只由位置、频率和 scaling 配置决定，与 batch 内容无关，因此可预计算或按需扩容缓存。真正容易出错的是 position offset：prefill 可从位置 0 开始批量取表，增量 decode 的新 token 必须使用其在逻辑序列中的真实位置，而不是当前输入张量长度 1 或物理缓存槽号。

## 构造流程

常见实现先计算

\[
\text{inv\_freq}_i=\Theta^{-2i/d_r},\quad
F_{m,i}=\text{position}_m\cdot\text{inv\_freq}_i,
\]

再生成 `cos(F)`、`sin(F)` 并按布局重复到 (d_r) 通道。缓存可存 `[max_seq,d_r]`，运行时用 `position_ids` gather；也可只缓存 inv_freq，针对当前 positions 动态生成，节省常驻内存但增加三角函数开销。

## 增量例子

prompt 有 100 个有效 token，则它们位置为 0—99，生成的第一个 token 对应 query/key 位置 100。即使 decode 输入形状是 `[B,1]`，也不能用位置 0。连续批处理时不同请求历史长度分别为 100、37，其新 token position 也分别为 100、37，需要向量化 position id，不能共享单一 offset。

## 工程陷阱

物理 paged cache 的 block/slot 位置不是逻辑 token 位置；滑窗淘汰旧块后，剩余 token 是否保留原位置取决于模型定义，不能因数组左移而自动减 position。scaling 配置、base 或 dtype 改变后，旧 cos/sin cache 必须失效。动态 NTK 若随当前长度改变频率，还涉及历史 K 是否用同一频率体系，需遵循具体实现。

## 精度与回答要点

position 与 inv_freq 的外积最好用 FP32，结果再 cast 到 Q/K dtype；超长上下文低精度 position 会丢整数分辨率。面试可用“prompt 100 → next position 100”的例子，再区分逻辑 position、张量索引和物理 cache slot。
