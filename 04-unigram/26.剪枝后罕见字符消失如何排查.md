# 26. 剪枝后罕见字符消失如何排查？

## 结论

首先确认字符是否在 normalization 后仍存在、是否进入 required_chars、character_coverage 是否排除它，以及剪枝器是否错误允许删除基础 piece。再检查模型转换是否遗漏 byte fallback 或把 user-defined/control piece 类型丢失。应定位第一处失去可达路径的阶段。

## 排查步骤

输出原始和规范化 code point；查看 seed vocab 是否含该字符及 piece 类型；在每轮剪枝 checkpoint 检查其状态与替代路径；对包含该字符的最小字符串构 lattice，确认起点到终点可达。若原生模型可编码而转换后的 fast tokenizer 不行，比较模型 proto/JSON 中 byte_fallback、unk_id、normalizer 和 added tokens。

## 常见根因

character_coverage 小于 1 导致低频尾部未设为 required；训练语料语言检测或采样漏掉目标脚本；NFKC 把字符映射成别的形式；批量剪枝 loss 近似 bug 删除唯一覆盖项；部署只加载 .vocab 未加载模型；版本不支持 byte fallback。乱码输入也可能让“同一字符”实际 bytes 不同。

## 修复与防线

对新模型提高覆盖或显式 required_chars，配置 byte fallback，并在剪枝中断言每个训练字符至少一条路径。旧模型不要原地改 piece ID；若必须扩词表，需要模型 embedding 适配。CI 用脚本分层的 coverage corpus 验证 unk、IDs 和 round-trip，线上监控未知 code point。

## 面试回答要点

- 按 normalization→seed→pruning→serialization→runtime 分层定位。
- required pieces 是不可剪约束。
- 原生与转换版差异常来自 fallback 和 piece 类型丢失。
- 修复覆盖也要遵守旧 checkpoint 兼容边界。

## 延伸追问与复习

训练器可在每轮剪枝后运行可达性不变量：对 required alphabet 的每个符号构造最小输入，Viterbi 终点必须可达；若 byte fallback 开启，256 个 byte piece 的类型与 ID 均存在。对真实语料可随机抽样重建 lattice，统计无路径数量必须为零。修复后应保留导致故障的 code point 和模型转换样例为 golden test，避免下次升级库又丢失 piece 类型。

如果字符仅在推理新数据出现而训练 required 集没有它，应走设计好的 UNK 或 byte 兜底，而不是在线临时分配 ID；临时 ID 没有已训练 embedding，会造成更隐蔽的错误。
