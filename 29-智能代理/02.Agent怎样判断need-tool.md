# Agent 怎样判断 need-tool？

## 结论先行

need-tool 不是“问题里有动词就调用 API”。先判断回答是否依赖外部、时效、私有或可验证状态；再检查是否存在已授权工具、参数是否足够、调用风险是否可接受。知识性解释通常 no-tool，库存、订单、余额、执行写操作通常 need-tool；当工具不可用时应说明不确定性或进入降级流程，而不是编造事实。分类器只给候选，确定性权限与 schema 校验才是最终门禁。

## 真实案例

客服助手处理 6 条电商请求：解释退货规则、查询物流、修改收货地址、问当前库存、写商品文案、取消订单。Notebook 以关键词基线和字段驱动判定比较，输出每条请求的时效性、私有性、写入风险与决策。

## 工程取舍与常见坑

只用关键词会把“如何取消订单”误判为真的取消；只看模型函数调用又会漏掉实时性。应把意图、是否需要权威数据、读写类型、授权和缺失参数分别建模。工具不可用时不能把缓存当成实时状态，必须带时间戳与可信度。

## 延伸追问

“能否用模型自评置信度？”可以作为特征，但要用带标签的调用成功、工具拒绝和用户纠错事件校准；阈值按写操作风险分层。
