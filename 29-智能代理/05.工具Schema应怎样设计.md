# 工具 Schema 应怎样设计？

## 结论先行

一个可执行工具契约至少描述名称、用途、输入类型、必填项、枚举/范围、输出结构、读写副作用、权限、幂等语义、超时和版本。Schema 是模型与服务之间的边界，不是提示词装饰；服务端必须依据 schema 校验并返回结构化错误。读写操作分开命名，危险动作要求确认令牌，返回值提供稳定 ID 和状态而不是只给自然语言。

## 真实案例

退款工具若只收 `amount`，模型可能把订单号放错字段，或发起超过可退额度的重复退款。Notebook 用 6 个退款请求比较“自由文本参数”的 baseline 和手写 schema 门禁，展示缺字段、枚举错误、金额范围和确认令牌。

## 工程取舍与常见坑

schema 太宽会把异常推给下游，太窄会使兼容性差。避免用一个万能 `execute(action, payload)` 承担不同副作用；避免把权限藏在描述文本。版本演进采用新增可选字段、弃用窗口与兼容测试。

## 延伸追问

“JSON Schema 通过就安全吗？”不安全：语法有效不代表业务有效，仍需库存、订单归属、额度、审批和幂等校验。
