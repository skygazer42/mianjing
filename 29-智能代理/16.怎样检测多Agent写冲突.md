# 怎样检测多 Agent 写冲突？

## 结论先行

写冲突不是两个 Agent 都写了这么简单，而是两个操作基于同一旧版本、修改相同资源或违反同一业务不变量。对资源更新使用版本号/ETag 的 compare-and-swap；对额度、库存等使用服务端条件更新；对跨资源动作使用串行化、事务或 Saga。冲突返回当前版本和可读 diff，Agent 只能重新读取后重新提议，不能盲目覆盖。

## 真实案例

库存 Agent 和促销 Agent 同时修改商品 P9 的可售数量。Notebook 用 6 次写入比较 last-write-wins baseline 与版本号 CAS，并展示冲突后权威回读再重试。

## 工程取舍与常见坑

last-write-wins 简单却会丢掉用户意图；长事务锁吞吐低。不能只在 Agent 进程内加锁，多个实例和人工后台仍会并发。冲突率应按资源类型和工作流记录，频繁冲突通常说明任务边界设计有问题。

## 延伸追问

“CAS 失败后是否总是重试？”不是。先回读、重新验证目标和权限；若写操作不可自动合并，要求人工选择。
